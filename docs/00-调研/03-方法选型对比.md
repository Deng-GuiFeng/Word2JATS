# 方法选型:几条路各有什么利弊,以及我最后为什么这么选

> 这篇把"有哪些做法、各自的取舍、我最终选了哪条、凭什么"讲清楚。
> 结论的依据来自前两篇(竞赛理解、数据与映射规格)和对 5 个样例、基线代码的实际查看,
> 最终定位与 `../01-设计/02-智能循环架构.md` 一致:**启发式打底,Agent 视觉闭环为质量核心**。

## 一、先说清楚难在哪

任务是:把一篇 Word 论文,自动变成符合 JATS 标准的 XML。难点有三个:

1. **Word 里只有排版,没有含义标记**。文件里记的是"这段是三号黑体居中",而不是"这段是标题";是"这段缩进两格",而不是"这是作者单位"。机器得自己看出每段到底是什么。
2. **同一个意思,排版花样百出**。我实际查了 5 个样例:有的用了语义化的样式名,有的样式名是乱码一样的代号,还有一篇 325 段**全是默认样式**、没有任何可利用的标记。靠固定套路必然栽跟头。
3. **公式、图片、表格、参考文献都得特殊处理**,而且形态不可预料。公式可能是 OMML(Office Math Markup Language,Word 内置的数学公式标记格式)、也可能整个是一张图;**表可能是真表(`<w:tbl>`)、可能整张是图片、还可能用制表符硬拼**;图片在 XML 里存不了,得抽出来单独存再引用;参考文献是一整段纯文字,要拆成作者、刊名、年份、页码。

第 3 点是关键:**真实投稿的"非常规形态"无法穷举**,这直接决定了选型——只靠死规则一定有啃不动的地方,而啃不动的恰恰常常是决定质量的部分。

## 二、几种做法,由简到繁

### 做法一:套固定模板 + 关键词猜(最省事)
- **怎么做**:假定 Word 用了固定样式名(比如就叫"标题""作者"),或靠关键词("Abstract""Keywords")定位各部分。委员会给的基线代码走的就是这条路。
- **好处**:几乎不花时间、不花钱,代码也简单。
- **坏处**:真实投稿的样式名根本不统一(见上面第 2 点),换一篇就大面积出错。基线代码我实际跑过,遇到带编号的标题、英文人名就把内容切错、甚至整篇正文丢失。
- **判断**:够不上拿奖,只能当反面教材。

### 做法二:看内容本身来判断(启发式规则,工作量大)
- **怎么做**:不信样式名,而是看每段文字自己的特征——它在不在正文开始之前(位置)、是不是加粗、有没有上标(格式)、是不是以"[1]"开头、是不是"Fig. 1"这种(文字规律);同时深入解析 Word 内部,处理公式、图片、真表格。
- **好处**:快(纯规则单篇亚秒级,见迭代日志 R0)、纯规则时不调模型不花钱、结果稳定可复现;换一篇没见过的论文也能出一版合规结果。
- **坏处**:规则要写得很周全,工作量大;**碰到语义模糊或非常规形态就力不从心**——到底哪段是作者、文献里哪一截是刊名、整张是图片的表、用制表符拼的表,死规则要么判错要么干脆做不了。
- **判断**:它是**便宜又稳的打底**,能把"大多数好啃的"快速搭出来;但它**不是质量的上限**,啃不动的那部分得交给别人。

### 做法三:整篇文档一次性丢给大模型(naive 用法)
- **怎么做**:把整篇 Word 直接交给大模型,让它一口气输出结构化结果。
- **好处**:省去写规则的功夫,语义理解上限高。
- **坏处**:慢、要花钱、**输出不稳定**(同一篇可能给出不同结果)、**会编造原文没有的内容**,而且无从核对对错。这次评分恰恰很看重"运行快、省资源、稳定"。
- **判断**:**不能这么用大模型**。把模型当黑盒一把梭,等于把质量赌在一次不可验证的生成上,风险太大。问题不在"该不该用大模型",而在"怎么用才既吃下难点、又不踩这些坑"。

### 做法四:Agent 视觉闭环(本作品的质量核心)
- **怎么做**:先用做法二跑出一版草稿;再把输入 Word **渲染成页面图**(人眼看到的真值),让本地多模态模型(VLM)**对着页面图独立核对我们产出的 XML**——清点页面上实际有几张表、几张图、几个公式、作者块长什么样,和 XML 一一对照。**能修的差异就就地修复**:漏表→看着图重建成标准 `<table-wrap>`、漏认或认错作者→重新补抽,另有专门修复器纠正章节层级、作者归属、后置声明拆分;修完再核对、**循环到收敛**为止。**唯独漏图、漏公式当前只检出并如实记录到 `agent-trace.json`、不自动补**——这是诚实标注的能力边界,不是假装已解决。对应代码 `src/word2jats/agent/`(render / inspect / outline / reconcile / repair / loop),CLI 加 `--agent`。
- **它怎么避开做法三的坑**:
  - **不是一把梭**:模型只在"草稿与页面对不上"的具体差异处定向出手,不重写已经对的部分,是纯增益。
  - **可核对**:真值来自渲染页(独立于被测系统),不是再跑一遍解析器自证,避免循环论证。
  - **可收敛、可留痕**:多轮迭代直到无可修复差异,每条差异和每次修复都进 `agent-trace.json`,能复查。
  - **成本可控**:页面只渲染、普查一次并缓存,所有模型调用按内容哈希落盘缓存,可复现、可秒级重放。
- **判断**:**这才是吃下"规则啃不动那部分"的正确方式,也是质量的来源**。它把大模型从"不可控的黑盒"变成"看着真值干活、还会自查自纠的工人"。

## 三、我的最终选型:做法二打底 + 做法四(Agent 视觉闭环)为质量核心

定位顺序不可颠倒(详见 `../01-设计/02-智能循环架构.md` §0):

- **做法二是热启动加速器,不是核心**:它先快速搭出一版合规草稿,给闭环一个好起点,少转几轮、省成本。(口径说明:`--llm off` 兜底档热启动是纯规则、零成本;而推荐的 `--llm local --agent` 档里,热启动阶段本身已用少量模型做参考文献结构化、看图重建表格,随后才进入视觉闭环——并非"所有模型调用都在闭环"。)
- **做法四是核心、是质量本体**:渲染→视觉核对→修复→收敛,专门吃下规则枚举不完的非常规形态。**质量从这里来。**
- **做法一、做法三都不取**:一是太弱,三是 naive 用法的风险全在评分软肋上。
- 还有一档**向后兼容兜底**:模型/渲染不可用时,退回纯草稿(`--llm off`),仍出合规 XML,**但质量降级**——这是底线,不是优势,更不当卖点宣传。

> 一句话:**便宜的大多数交给规则,难啃但决定质量的少数交给 Agent 视觉闭环。**

## 四、为什么这是赛题的最优解(对着评分与委员会偏好想)

比赛四项打分,从重到轻:工程是否扎实好用(最重)、有没有创新、是不是真能解决出版这件事、现场展示。委员会的偏好可以揣摩出两头:**既要工程扎实落地,又要看到 Agent 层面的真创新**。

- **只用做法一**:简单,拿不出手。
- **只用做法二**:工程扎实,但在非常规形态前有明显天花板,且创新性不足。
- **只用做法三**:看着新,但慢、贵、不稳、会编造,正好踩满评分最看重的软肋,工程不扎实。
- **做法二打底 + 做法四为核心**:打底这套保证了**快、稳、省、可复现**(工程扎实这头占住);视觉闭环这套提供了**看图自查自纠、收敛交付**的真 Agent 创新(创新这头占住),还实打实解决了图片表/制表符表这类"以前做不了"的硬骨头(真能落地这头占住)。**两头都要、且都给到了**——这是我判断委员会最可能认可的路子。

> 之所以核心必须是闭环而不是"再多写点规则":如果规则就能完美解决,这个比赛根本不会存在。
> 赛题考的正是用 LLM/Agent 吃下规则吃不下的部分。

## 五、各部分对应到代码

- 做法二(启发式打底):`src/word2jats/classify/`(判断每段是什么)+ `src/word2jats/parse/`(拆解 Word 内部);公式/图片/真表格在 `src/word2jats/build/` 下的 formulas / figures / tables。
- 做法四(Agent 视觉闭环,质量核心):`src/word2jats/agent/`——`render.py`(渲染页面图)、`inspect.py`(VLM 视觉普查)、`outline.py`(解析自家 XML 结构)、`reconcile.py`(视觉⟷XML 调和出差异)、`repair.py`(定向修复)、`loop.py`(多轮编排留痕);CLI 用 `--llm local --agent` 进入完整质量档。
- 向后兼容兜底:`--llm off`,纯做法二出草稿。
- 输出后自动用 JATS 标准校验:`src/word2jats/validate/`。
- 各档位实测结果(DTD 通过、各模块计数、表格重建)由现行三层评测产出(`PYTHONPATH=scripts .venv/bin/python -m eval.run --llm off` → `reports/eval/<tag>/`,口径见 `../03-评测/评测体系设计.md`);纯规则草稿的单篇耗时见迭代日志 R0。
