# 01 · 竞赛与任务

这篇讲清楚：这是个什么比赛、要解决的到底是什么问题、为什么这件事值得做、以及成败以什么衡量。读完你会知道这个项目的来龙去脉和它的边界。

## 这是个什么比赛

**学术期刊结构化技术创新大赛**，由**杭州电子科技大学计算机学院**与 **IMR Press（IMR 出版社）** 联合主办（据 [`报名海报.jpg`](../报名海报.jpg)）。IMR Press 是一家国际学术出版机构，本次竞赛的全部样例数据都来自它旗下的期刊——**所以 IMR Press 既是主办方，也是这个任务的真实业务背景和目标领域**。

比赛有两个选题，二选一：

- **选题一（本项目）**：面向学术出版的智能结构化转换——**从 Word 排版格式到 JATS 标准 XML 的语义映射与自动化生成**。
- 选题二：面向学术出版的智能排版引擎——从 JATS XML 到 PDF 版面的自动化生成（方向相反，本项目不涉及）。

本项目做的是选题一。

## 任务定义：Word → JATS，只加结构、不改内容

一句话，任务是把一篇学术论文的 **Word 投稿稿（`.docx`）** 自动转换成 **JATS 标准 XML**。

这里两个名词要先讲清（详见 [02-领域基础](02-领域基础.md)）：

- **docx**：Word 文档格式，作者投稿时用的就是它。它有内容，但结构是"排版出来的"、隐含的——一段文字是标题还是正文，往往只是字号加粗的差别，机器不容易直接判定。
- **JATS**：Journal Article Tag Suite，国际学术出版界通用的一套 XML 标准，用明确的标签把论文的每个部分标出来（题名、作者、单位、摘要、正文分节、图、表、公式、参考文献……）。出版、检索、长期保存都依赖这种结构化的全文。

关键限定词是**结构化技术**：这项任务**只把隐含的结构显式标出来，不改动任何内容**。作者写了什么，转换后就还是什么，一个字都不能增删改。这条"忠实"原则是整个任务的地基，也是它真正的难点所在（[03-数据与结构参考](03-数据与结构参考.md) 讲了为什么，[04-系统设计](04-系统设计.md) 讲了怎么保证）。

## 为什么需要这件事

学术出版有一条现实的流水线：作者用 Word 投稿 → 期刊编辑部审稿、加工 → 排版发表。而现代出版系统的检索、在线阅读、跨库交换、长期归档，都建立在**结构化的全文 XML**（也就是 JATS）之上，而不是 Word。于是从"作者的 Word 稿"到"出版级的 JATS XML"之间，天然存在一道转换工序。

这道工序目前很大程度上靠人工或半自动完成，既慢又贵，还容易出错。如果能让它自动化、且忠实可靠，就能实实在在地省下出版方的核心成本——这正是竞赛"聚焦企业核心业务痛点、真实场景落地"的初衷（据 [`报名海报.jpg`](../报名海报.jpg)）。所以这不是一道纯学术练习题，而是一个有明确业务价值的工程问题。

## 怎么评的

由行业专家和技术专家组成评审团，从多个维度加权打分。决赛评分细则（据竞赛《项目介绍》材料 [`学术期刊结构化技术创新大赛项目介绍.pptx`](../学术期刊结构化技术创新大赛项目介绍.pptx)）：

| 维度 | 权重 | 具体看什么 |
|---|---|---|
| **落地性** | **40%** | 代码规范、工程结构、运行效率、资源消耗、稳定性——**能不能真的用起来、够不够稳** |
| **创新性** | **30%** | 算法创新、模型设计、技术路线的新颖度——**方法有没有新意、是不是比常规做法更好** |
| **业务适用性** | **20%** | 问题解决的完整性、对出版场景的适配能力 |
| **展示度** | **10%** | 现场表现、答辩 PPT 质量、回答问题的准确性 |

可见**落地性（40%）是权重最大的一项**——评委很看重"这套东西工程上扎实、能真正投入使用"，其次才是方法的创新。这直接决定了本项目的取舍重心：先把转换做得稳定、完整、可交付，再谈方法的新意。

- **赛程**（2026 年）：报名（6 月初）→ 线上答疑 → **初赛作品提交（7 月 30 日前）** → 初赛评选（7/31–8/6）→ 决赛作品打磨（8/6–9/6）→ 决赛现场答辩（9 月中旬）。
- **交付物**：输入样例 Word + 输出样例 JATS XML + 可运行的程序代码，且**必须附运行说明文档**。初赛不要求功能 100% 完成，但必须能运行、产出可验证的输出；核心代码与算法必须原创。
- **激励**：一/二/三等奖分别 3000/2000/1000 元，另有企业实习绿色通道、决赛每队 500 元启动资金等。

> 主办方还提供了基线代码和 JATS 标准/排版规范文档作为起点（见 [`baseline-develop/`](../baseline-develop/)，一个用 Apache Tika 抽取文本、FreeMarker 套模板的 Java 项目）。它是"纯模板规则"路线的代表，也是我们方案要超越的对照物——为什么这条路线不够，见 [04-系统设计](04-系统设计.md)。

**一个重要的自我认知**：评审给的是上面那套多维加权的综合分，**不是**某个"缺陷数"。本项目内部用一套三层评测数出剩余缺陷条数（[06-评测与成绩](06-评测与成绩.md)），那是我们自建的、用来指导迭代的**代理指标**，不等于评委的分。把缺陷数当成唯一目标去死磨，反而会掉进过拟合的坑——这一点在 [06-评测与成绩](06-评测与成绩.md) 里会讲得很透。

## 难在哪

这个任务表面简单（"不就是格式转换吗"），真正的难在于两个要求同时成立、方向相反：

1. **判断结构要"看懂内容"**：真实投稿的 docx 样式名经常缺失或标错，"这段是标题还是正文""这条参考文献的作者到哪儿结束"这类判断，很多时候只能理解内容本身才做得出来。
2. **搬运内容要"一字不改"**：与此同时，正文的每个字、每处斜体上标都要原样保留，不能被"顺手优化"掉。

前者要聪明、要有语言理解力；后者要死板、要绝对忠实。再加上论文里还有整张表其实是图片、公式是特殊格式、参考文献著录五花八门等硬骨头。如何用一个方案同时满足这两条互相拉扯的要求，是这个项目的核心命题——答案在 [04-系统设计](04-系统设计.md)。
