# 架构设计

> 本文说明 word2jats 转换系统的整体架构、分层、模块和技术选型。设计目标紧扣竞赛评分（见 `../00-调研/01-竞赛理解.md`）。
>
> **先读 `02-智能循环架构.md`**：那是本作品质量核心（LLM 主导的核对/修复闭环）的权威说明，本文与它一致。

## 0. 一句话定位（先读，不可颠倒）

本系统的**核心是 LLM 主导的核对/修复闭环**：热启动先搭一版草稿，随后把渲染页（人眼真值）、docx 标题样式（权威层级信号）、源前置/后置区文本、当前 XML 一并作为证据交给 LLM，由它判断草稿哪里不忠实于源、该怎么改，就地修复并循环至收敛。修复由四个 LLM 主导修复器承担——**章节结构、作者归属、后置声明拆分、内容补全**（权威说明见 `02-智能循环架构.md`）。质量从这里来。

> **R15 重构的关键纠正**：把早期"**结构/层级问题查出却丢弃**"的旧白名单行为去掉了——章节层级、作者归属、声明改由 LLM 修复器（阶段 A/B/C）**实际修复**，不再"仅记录、不修"；内容补全阶段（D）目前实现了**作者、表格两类补全器**，漏图/漏式暂仅记录到 trace（尚无对应补全器），作为诚实的能力边界。系统的硬约束只有两条——① 最终 DTD 合法（赛题硬要求）、② 不编造源没有的内容（正确性底线，配**内容守恒校验**，改坏即回滚）；其余"改不改、怎么改"都交给 LLM 判断。

确定性管线（解析+分类+构建）是闭环之下的**热启动加速器**：先快速搭出一版 XML 草稿，给闭环一个好起点、省成本——是加速器，不是核心，更不是替代品。

`--llm off`（关掉模型仍出合规 XML）是**向后兼容兜底**，以质量下降为代价，是底线，不当卖点宣传。

## 1. 设计目标（紧扣评分项）

| 评分项 | 权重 | 架构如何回应 |
|----------|------|--------------|
| 落地性（工程是否扎实好用） | 40% | 分层清晰、模块化；独立 venv + 锁定依赖（结果可复现）；DTD 校验 + JATS4R 风格规则检查保证输出稳定；闭环全程留痕（`{article}.agent-trace.json`）可追溯、可重放；模型/渲染调用按内容哈希磁盘缓存，冷缓存后秒级；**两层评测**（可定义指标 + 每输出独立 subagent 逐字审查，对照外部权威标签、以忠实于源 docx 为真值，见 `../03-评测/01-评测报告.md`）确保质量可量化、缺陷可追。**优雅降级（`--llm off` 仍出合规 XML）是底线兜底，不是卖点** |
| 创新性 | 30% | **核心创新 = LLM 主导的核对/修复闭环**：四个 LLM 主导修复器（章节结构/作者归属/声明拆分/内容补全），据 docx 样式、渲染页（人眼真值）、源文本判断并就地修复，**去掉了早期"结构问题查出却丢弃"的白名单行为（章节/作者/声明改由 A/B/C 实际修复，内容补全已实现作者+表格两类）、守两条硬约束（DTD 合法 + 不编造）+ 内容守恒回滚**（非一次性流水线、非解析器自证）；其下深入解析 OOXML（OMML→MathML、还原伪表格）；参考文献按置信度选 element/mixed-citation |
| 业务适用性（能不能真正用于实际场景） | 20% | 覆盖全部功能模块；输出严格符合 JATS 1.3 + IMR 出版约定；图片单独存为外部文件。真实投稿里「无样式子标题 / 表是整张图片 / 作者归属错配 / 声明是无标题裸句」这类**死规则永远枚举不完**的情况，交给闭环据证据（渲染页 / docx 样式 / 源文本）让 LLM 判断补救 |
| 展示度 | 10% | 完整的中文文档；CLI 和日志清晰；闭环全过程留痕落盘 `{article-id}.agent-trace.json`（逐轮记录每个修复器看了什么、判断、是否生效）；评测产物归档 `reports/eval_l1_v2/`（Layer-1）与 `reports/eval_judge/`（Layer-2 judge） |

**核心原则**（来自调研，见 `../00-调研/02-数据与映射规格.md`）：
1. **忠实转换 docx 里的真实内容，绝不臆造编辑改动**——金标准里的人工编辑、外部补充信息，无法从输入推导出来。
2. **优先保证换没见过的文档也能处理**——评委会用新样例来测；正因为死规则枚举不完真实输入的花样，才需要让模型看着页面去核对、去补救。
3. **质量来自 LLM 主导的核对/修复闭环**——完整质量档是 `--llm local --agent`。`--llm off` 是向后兼容兜底（纯规则、秒级出合规 XML，但**质量降级**），是底线，不是「默认更优」。
4. **所有外部数据都可配置**——journal-meta 查表、DOI 占位或绕过、CrossRef 可选。

## 2. 总体架构：核心闭环 + 热启动管线

系统是两层结构，主次分明：上层是质量核心——LLM 主导的核对/修复闭环，下层是为它打底的确定性热启动管线；模型/渲染不可用时退回草稿。

```
╔══════════════════════════════════════════════════════════════════╗
║  核心层：LLM 主导的核对/修复闭环 (agent/)  ── 质量从这里来          ║
║  渲染输入 Word 为页面图(人眼真值) + VLM 逐页视觉普查(各一次,缓存)   ║
║  → 四个 LLM 主导修复器(看证据 → 判断 → 改 → 校验 → 留痕):           ║
║    A 章节结构(据 docx 样式重排层级)  B 作者归属(LLM 修单位;ORCID 等确定性)║
║    C 后置声明拆分(裸句→命名小节)     D 内容补全(漏表/漏作者,多轮)   ║
║  结构问题不再丢弃;两条硬约束(DTD 合法 + 不编造)+ 内容守恒,不过即回滚  ║
╚══════════════════════════════════════════════════════════════════╝
        ▲ 草稿(好起点)              │ 就地修复同一棵活的 article(lxml)树
        │                            ▼
┌──────────────────────────────────────────────────────────────────┐
│  热启动层：确定性管线 (加速器，不是核心)                           │
│  parse → classify → build → serialize → validate  ── 见 §2.1      │
└──────────────────────────────────────────────────────────────────┘
        │ LLM/渲染不可用时
        ▼
  优雅降级：跳过闭环，直接交草稿(合规 XML，但质量降级) ── 底线兜底
```

> 四修复器各修什么、凭什么证据、为什么「必须是闭环而不是写更全的规则」、修复能力的诚实边界，
> 详见 `02-智能循环架构.md`（以它为准）。本文重点交代分层与模块。
>
> 编排见 `pipeline.py`：`--agent` 开启闭环；`agent/loop.py` 的 `run_agent_loop` 按
> A→B→C→D 顺序跑四个修复器，每步即时 DTD 校验 + 内容守恒，不过即回滚。证据来源不止视觉：
> 章节层级以 **docx 标题样式**为权威（视觉清点会把表格分组标签误当标题，故结构层级不采信
> 视觉标题），作者/声明据**源文本**，漏表/漏作者才看**渲染页**重建。关键区分不在"规则 vs 模型"，
> 而在"单遍草稿 vs LLM 据证据迭代核对修正"。

### 2.1 热启动层的内部分层（产出草稿）

热启动层把 docx 快速转成一版合规 XML 草稿，供闭环核对。它本身是一条确定性管线：

```
┌─────────────────────────────────────────────────────────────────┐
│  CLI / Pipeline 编排层  (cli.py, pipeline.py)                      │
└─────────────────────────────────────────────────────────────────┘
        │  docx 路径 + 配置(期刊/元数据/LLM开关/--agent)
        ▼
┌──────────────┐   1. 解析层 parse/                                  │
│  OOXML 解析   │   docx(zip) → lxml/python-docx                     │
│              │   抽取: 段落+run格式 / 样式 / 编号 / 表 / 图(媒体)    │
│              │        / OMML公式 / 脚注尾注 / 超链接书签            │
└──────────────┘   产出: 规范化中间表示 IR (model/)                  │
        │
        ▼
┌──────────────┐   2. 语义识别层 classify/   (规则引擎 + 可选LLM)      │
│  角色判定     │   给每个 IR 块打语义标签:                            │
│              │   title/authortype/authors/aff/orcid/corresp/editor │
│              │   /date/abstract/keywords/heading(级)/figcap/tabcap  │
│              │   /reference/backsection/bodytext ...               │
│              │   低置信→LLM 兜底分类                                │
└──────────────┘   产出: 带语义标签的结构化文档 (StructuredDoc)       │
        │
        ▼
┌──────────────┐   3. 构建层 build/  (各模块 JATS 元素生成器)          │
│  JATS 构建    │   MetadataBuilder / BodyBuilder / FigureBuilder     │
│              │   FormulaBuilder / TableBuilder / ReferenceBuilder  │
│              │   XrefResolver                                      │
│              │   + 外部数据 enrich/ (journals 查表, CrossRef 可选)  │
└──────────────┘   产出: lxml ElementTree (JATS article)            │
        │
        ▼
┌──────────────┐   4. 序列化层 serialize                              │
│  输出         │   DOCTYPE + 命名空间 + pretty-print → .xml          │
│              │   图片外部化 → {article-id}/fig-0N.jpg              │
└──────────────┘
        │
        ▼
┌──────────────┐   5. 校验层 validate/                                │
│  QA          │   lxml DTD 校验 + 手写 JATS4R 风格规则检查 → 报告     │
└──────────────┘
```

**贯穿各层的公共能力**：`llm/`（统一模型客户端，带磁盘缓存——闭环与热启动语义补全共用）、`config`（YAML/.env）、`logging`（结构化日志，记录每个模块的耗时和模型调用次数，作为落地性的度量依据）。

## 3. 中间表示（IR）

解析层和语义层之间用一套既不依赖 Word、也不依赖 JATS 的数据模型（`model/`），方便单独测试、也方便替换实现：

- `InlineRun`：文本片段 + 格式标志（bold/italic/sup/sub/code）+ 可选公式(OMML节点)/超链接。
- `Block` 基类，子类：`ParagraphBlock`（runs + styleId + styleName + numbering信息）、`TableBlock`（行列单元格，含合并）、`FigureBlock`（媒体引用 + caption）、`FormulaBlock`（OMML，inline/display）。
- `Document`：有序 `Block` 列表 + 全局信息（styles 映射、media 清单、footnotes、headers）。

语义层在 IR 之上产出 `StructuredDoc`：`FrontMatter`（title/authors/affs/abstract/keywords/...）+ `BodyTree`（嵌套 Section）+ `BackMatter`（refs/acks/...）。

## 5. LLM/VLM 的两个角色与受控使用

模型在本系统里担两个角色，主次分明：

1. **主导核对/修复闭环（主）**：在 `agent/` 里驱动四个修复器——据 docx 样式重排章节层级、据源前置区修作者单位归属、拆分后置声明、看图核对补全漏表/漏作者。质量主要来自这里。关键约束：**LLM 只输出结构决策（层级大纲 / 单位归属 / 分组），由确定性代码移动已有内容块落地，不让模型自由改写正文**；作者归属里**仅单位走 LLM**，ORCID/通讯/共同贡献/邮箱这类结构化数据走确定性解析与热启动标记检测（同姓也不混）。
2. **热启动层的局部语义补全（次）**：解析作者行、结构化参考文献、角色分类拿不准时的兜底——只在规则置信度低的局部才调用，**绝不把整篇文章丢给模型自由生成**。

工程上的受控措施（回应落地性顾虑）：
- **两条硬约束 + 多处可靠性护栏（如实披露，不止两处）**：去掉了早期"结构问题查出却丢弃"的白名单行为——章节/作者/声明改由 A/B/C 实际修复，内容补全已实现作者+表格两类（`REPAIRABLE={extract_authors, rebuild_table}`，成员与早期 `ACTIONABLE` 逐字相同），漏图/漏式暂只记录到 trace、不自动修。硬约束只有两条："最终 DTD 合法"与"不编造源没有的内容"，每个修复器改完即时 DTD 校验 + 内容守恒校验，任一不过即回滚，绝不改坏。除硬约束外的护栏：A 章节"新增节须有源标题样式支撑"、C 声明"覆盖校验 + 只在能拆出更多命名节时才动"、B 作者"姓名集合不变 + ORCID 仅清张冠李戴"、D 内容补全"仅启用已实现的两类补全器"。作用是防把噪声（表格分组标签、漏切段落、同姓误配）当真实结构，而非限制 LLM 判断。
- **统一接口**：`LLMClient(provider, model)`，内部都走各后端 **OpenAI 兼容** 的 Chat Completions（本地为 sglang 起的 Qwen VLM 服务；**写具体端点和参数之前务必先查官方文档**）。
- **强制结构化输出**：按 JSON Schema 约束 + `temperature=0` + few-shot，事后再用规则校验（ORCID/DOI 正则、XML 是否合法）排除模型瞎编。
- **磁盘缓存**：按内容哈希缓存——页面不变则视觉普查只做一次；闭环多轮只重做核对+修复；重复运行不再产生额外成本，结果可复现、可秒级重放。
- **可降级**：`--llm off` 或模型/渲染不可用时，闭环自动跳过、退回热启动草稿（`agent/loop.py` 开头即判 `llm.enabled`），仍产出完整合规 XML——**这是向后兼容兜底，以质量下降为代价，不是优势宣传**。

## 6. 技术选型与依据

| 选型 | 决策 | 依据 |
|------|------|------|
| 语言 | **Python 3.12** | 服务器没有 Java/Maven；Python 生态（lxml/python-docx/OMML2MML/openai）最适合本题；开发迭代快（见 `../参考资料/baseline代码分析.md` §8、`JATS与开源工具调研.md`） |
| 渲染（视觉真值） | **soffice（docx→PDF）+ pdftoppm（PDF→PNG）** | 纯 CPU、无需 GPU 即可得到「人眼真值」页面图，作为闭环独立核对的基准；真值来源独立于被测解析器，避免循环论证 |
| 本地多模态模型 | **两卡 RTX PRO6000 上 Qwen3.6-35B-A3B VLM（sglang，OpenAI 兼容）** | 本地推理、数据不出机；OpenAI 兼容接口便于在 local/云端间切换与降级 |
| docx 解析 | **python-docx + lxml** | python-docx 提供对象模型（段落/run/表/样式/编号），lxml 直接读 `document.xml` 来补上 OMML 和字段域（python-docx 不暴露 OMML，已查证 issue #213） |
| 公式 | **lxml.XSLT + 开源 OMML2MML.XSL** | 微软官方样式表的开源移植（plurimath/meTypeset），输出 presentation MathML，许可合规 |
| XML 构建 | **lxml 直接建 DOM**（正文）+ 轻量模板（固定元数据） | 正文结构复杂（嵌套 sec/表/图/公式），DOM 构建保证良构、可校验；也便于闭环就地改同一棵活树，无需序列化往返 |
| 配置 | **YAML + .env** | journals.yaml 可扩展；.env 存密钥（python-dotenv 加载） |
| 校验 | **lxml DTD + 手写 JATS4R 风格规则**（`validate/checks.py`，非 Schematron） | 本地集成，对 CI 友好；遵循 JATS4R 关键规则（见 `../00-调研/02-数据与映射规格.md`） |
| CLI | **argparse（stdlib）** | 零依赖，省资源 |
| 测试与评测 | **pytest 单测 + 两层评测** | 单测含修复器安全护栏 `tests/test_agent_fixers.py`（集合不变/内容守恒/源支撑/DTD，守"抖动至多不生效、不改坏"）、闭环确定性核心 `tests/test_agent.py`、端到端回归；质量评测分两层——Layer-1 可定义指标（`scripts/eval/`，逐维度对照外部权威标签）+ Layer-2 每输出派独立 subagent 逐字审查（详见 `../03-评测/01-评测报告.md`） |

## 8. 端到端数据流（以样例3 JIN49347 为例）

下面是**热启动层**的草稿数据流；完整质量档（`--llm local --agent`）会在第 4、5 步之间插入 LLM 主导的核对/修复闭环（见 §2、`02-智能循环架构.md`）：渲染页面图 + VLM 普查，再跑四修复器（章节结构 / 作者归属 / 声明拆分 / 内容补全），每步 DTD 校验 + 内容守恒、不过即回滚，之后再序列化校验。

1. `cli word2jats convert 样例/样例3/第一组/初始文件.docx --journal JIN --doi 10.31083/JIN49347 --figures 样例/样例3/第一组/figures.zip -o output/`（加 `--llm local --agent` 即走完整质量档）
2. 解析层 → IR（391 段、3 表、16 OMML、7 媒体）。
3. 语义层 → StructuredDoc（front: 作者/ORCID/摘要/关键词；body: 5 大节嵌套；back: 56 参考文献）。
4. 构建层 → JATS 树；图片外部化 `JIN49347/fig-01.jpg`...；OMML→6 个 disp-formula。
5. 序列化 → `output/JIN49347.xml` + `output/JIN49347/fig-0N.jpg`。
6. 校验 → DTD 通过 + JATS4R 风格规则检查报告(`validate/checks.py`)。

## 9. 迭代路线（从能跑通的最小版本到质量核心）

热启动层（M0–M7）先把「docx → 合规 XML 草稿」这条确定性管线打磨扎实，为闭环提供好起点；M8 是质量的主来源，**不是收尾增强**：

- **M0 骨架**：CLI + 管线 + IR + 序列化空壳，先把 docx→最小合规 XML 的流程跑通。
- **M1 元数据**：title/article-type/作者/aff/ORCID/corresp/编辑/日期/摘要/关键词 + journal 查表。
- **M2 正文**：sec 树/p/inline 格式/列表。
- **M3 图片**：外部化 + fig。
- **M4 公式**：OMML→MathML + disp/inline。
- **M5 表格**：真 w:tbl → table-wrap。
- **M6 参考文献**：解析 + element/mixed-citation + xref 交叉引用解析。
- **M7 校验 + 外部补全**：跑通 DTD 校验 + JATS4R 风格规则检查流程；CrossRef 可选；参考文献结构化。
- **M8 LLM 主导的核对/修复闭环（质量核心）**：`render/inspect` + 四修复器（`structure`/`authors_fix`/`declarations`/`reconcile`+`repair`）+ `loop`——据 docx 样式重排层级、据源修作者单位归属（ORCID/通讯/共同贡献走确定性）、拆分裸声明、看图核对补全漏表/漏作者，循环收敛；两条硬约束（DTD 合法 + 不编造）+ 内容守恒回滚，去掉了早期"结构问题查出却丢弃"的白名单行为。覆盖死规则枚举不完的情况（无样式子标题、图片表、制表符表、特殊作者行、裸声明句等），是质量的主来源。
- 每个里程碑都在样例上重新跑一遍、确认没改坏（见 `../03-评测/`）。
