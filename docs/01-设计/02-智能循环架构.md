# 智能循环架构（LLM 主导的视觉/源核对闭环）

> 本文描述 `--agent` 档的**核对/修复闭环**:确定性管线先产出一版合规 XML,随后由 **LLM** 对结构难例
> 逐项核对、决定怎么改、就地修复,循环至收敛。对应代码 `src/word2jats/agent/`。整体分工
> (确定性管线为质量主体、LLM 只判结构、内容守恒不变量)见 `01-架构设计.md` §0。
>
> 两轮重构确立的关键原则:R15 去掉了早期"**结构/层级问题查出却丢弃**"的旧白名单行为——章节层级、
> 作者归属、后置声明改由 LLM 修复器(阶段 A/B/C)**实际修复**,不再"仅记录、不修"。R17 划清了修复的
> 边界——**LLM 只判结构、不生成文字**:内容补全阶段(D)现只保留**漏作者重抽**一类,"VLM 看图重建表"
> 的 OCR 路径已删除(表格图片里的文字不在 docx 文本流里,读图必造字,样例2 实测曾编造 617 词);
> 漏表/漏图/漏式仅记录到 trace(见 §2.D、§3)。系统的硬约束只有两条(下文 §3)。

## 0. 定位:谁承担什么

| 角色 | 是什么 | 地位 |
|------|--------|------|
| **确定性管线** | 解析 + 分类 + 构建,单遍产出合规 JATS(参考文献搜索式切分、图片表外部化为 graphic、制表符表切 Tab 还原) | **质量主体**(R17 后确定性档 10 样例总缺陷 4316→356),只搬运原文、天然内容守恒 |
| **LLM 修复闭环** | 渲染输入 Word 为页面图(人眼真值);用 docx 标题样式、渲染页、源文本作证据,让 LLM 判断结构歧义(层级/归属/拆分),**就地修复并循环** | **难例收敛层**:只判结构、不生成文字;实测在确定性基础上只好不坏(10 样例总缺陷 356→228,逐样例只降不升,`reports/eval/llm_agent`) |
| **优雅降级** | 模型/渲染不可达时直接交确定性管线的输出,不崩、仍合规 | 兜底:质量主体不受影响,只是难例得不到进一步收敛 |

> **为什么结构歧义要 LLM、而不是"写更全的规则"?** 输入 Word 千变万化(标题无编号、子标题只靠加粗、
> 声明是无标题的裸句子、同姓作者的 ORCID 易错配……),**死规则枚举不完**。正确性的真值是
> "**忠实于源 docx**"——而判断"这个加粗行是子标题还是表格分组标签""这个 ORCID 属于哪位同姓作者",
> 正是启发式做不了、LLM 据上下文能做的事。早期版本把**章节层级/作者归属/声明**这类"视觉/语义查出的
> 问题"一律"仅记录、不修",等于用工程上的胆怯压制 LLM 的判断——R15 纠正了这一点:改由 A/B/C 三个
> LLM 修复器**实际修复**。但 LLM 的边界同样明确(R17 确立):**判断可以交给它,文字不能由它产生**——
> 内容补全阶段(D)`loop.py` 的 `REPAIRABLE={extract_authors}` 只对**漏作者**一类生效(作者名在
> docx 文本流里、可与源核对);"VLM 看图重建表"已删除(表格图片的文字不在文本流里,OCR 无从核对、
> 实测必造字);漏表/漏图/漏式仅记录到 trace、不自动修,这是如实披露的能力边界,列入优化清单。

## 1. 闭环全貌

```
 确定性管线:规则 + 局部难例兜底 → 一版合规 JATS(parse / classify / build)
                    │
 渲染:输入 docx → 页面 PNG(soffice + pdftoppm,纯 CPU,dpi=120 实测 OCR 可读)← 人眼真值,只渲一次
                    │
 视觉普查:VLM 逐页清点页面上有什么(表/图/块级公式/标题/作者块)         ← 只清点一次,缓存
                    │
   ┌─────────── LLM 主导修复(每个修复器:看证据 → 判断 → 改 → 校验 → 留痕)───────────┐
   │  A. 章节结构修正   据 docx 标题样式 + 当前树,LLM 定正确层级,移动已有内容块重排     │
   │  B. 作者归属修正   LLM 仅定单位 affs;ORCID/通讯/共同贡献/邮箱走确定性(同姓更可靠)  │
   │  C. 后置声明拆分   据源,LLM 把无标题的裸声明句识别并归入命名 back 小节               │
   │  D. 内容补全(多轮) 漏作者→重抽(超集校验);漏表/漏图/漏式→仅记录 trace              │
   └──────────── 每步都做 DTD 校验 + 内容守恒,任一不过即回滚,绝不改坏 ─────────────────┘
                    │
   交叉引用解析 → 残留修复 → DTD 校验 → 输出 XML + 完整 trace(每步做了什么/是否生效/为何不生效)
```

## 2. 四个 LLM 主导修复器(各自修什么、怎么修、凭什么证据)

### A. 章节结构修正 `agent/structure.py`
- **修什么**:正文章节的层级错位。实测样例1:无编号的加粗小标题 "Internal validation"/"External
  validation" 被启发式误升为顶级节(与 Results 平级),且漏掉了 Heading 3 "Model validation";
  样例 S3:顶级 "Discussion" 标题丢失、Main Findings 被误升为顶级。
- **怎么修**:把 **docx 的标题样式序列**(`Heading 1/2/3` 是权威层级信号;`bold`/`italic` 是待判的
  加粗/斜体行)和当前 XML 章节树交给 LLM,由它输出正确的层级大纲(每个标题:层级 + 成节还是
  仅是嵌在段首的加粗引导句、不单独成节(排版上叫 run-in) + 现有还是需恢复);再据此**移动已有内容块**重建 `<body>`(只移动、不重写)。
- **凭什么不出错**:① 章节号是出版时才加的、源文本没有,故**不采信视觉清点的标题文本**(VLM 会把
  表格分组标签误当标题),层级以 docx 样式为准;② "新增"的节必须确为源标题候选(已剔除"后接制表符
  数据行"的表格分组标签),不许凭空造节;③ 重建后内容守恒(原文每段都在)+ DTD 校验,否则回滚。
- **效果**:样例1 误升为顶级的小标题归位、漏掉的 Heading 3 子节补回;S3 的 Discussion 恢复并正确嵌套 4.1/4.2/4.3。(此类章节层级/角色修正,价值由现行评测 L2 对位的"章节"类衡量,见 `../03-评测/评测体系设计.md`。)

### B. 作者归属修正 `agent/authors_fix.py`
- **修什么**:作者与单位/ORCID 的**对应关系**错配。实测样例4:第一作者 Carmen 被错挂了第三作者
  Ricardo 的 ORCID,多位作者与第 2、3 个单位的关联(作者→单位对应)丢失;样例2:三个同姓 Wang 的 ORCID 张冠李戴。
- **怎么修(明确分工,不同字段用不同方法)**:
  - **单位 affs**:交给 LLM 据源前置区做多单位关联(语义判断,LLM 擅长;实测样例4 正确补回 1,2 / 1,3 / 1,4)。
  - **ORCID**:**不**用 LLM,改用**确定性解析**——ORCID 块是结构化的"姓名: 16 位号"数据,按**全名 +
    去重音 + 按词精确匹配**关联到作者(`orcid_block_map`)。
  - **通讯(corresponding)/共同贡献(equal)/邮箱(email)**:也**不**用 LLM,沿用**确定性管线对作者行
    `*`/`†`/`#` 上标标记的确定性检测**(`classify/frontmatter.py` 的 `parse_author_line`),
    通讯邮箱则来自据 "Correspondence:" 块构建的映射(`fix_authors` 不在此重建、信任管线解析)。
  - 全程在**作者姓名集合不变**(不增删、不改姓)的前提下回填,重建 `<front>`,DTD 校验否则回滚。
- **为什么这几项用确定性、不用 LLM(特例披露)**:LLM 在**多个同姓作者**时不可靠——实测样例2 三个 Wang,
  LLM 曾把他们**全部标成通讯且挂同一个邮箱**、ORCID 也张冠李戴。作者行的 `*`/`†` 标记与 ORCID 块是
  确定性可解析的结构化数据,用规则解析比让 LLM 猜更稳,故这几项信任管线的确定性解析。
- **凭什么不误清正确值**:ORCID 只在"当前号其实属于另一位作者(张冠李戴)"时清除;"仅未在块中匹配到"
  不清(可能是匹配遗漏,值未必错)。
- **效果**:样例4 Carmen 的错挂 ORCID 清除、Ricardo 拿回本人 ORCID + 多单位恢复;样例2 三个 Wang
  的 ORCID 各归各位,通讯/共同贡献由 `*`/`†` 标记正确区分(Bin=通讯,Shuang/Aili=共同贡献)。

### C. 后置声明拆分 `agent/declarations.py`
- **修什么**:期刊末尾的声明(资助/利益冲突/伦理/致谢/作者贡献等)在源 docx 里常是**无标题的裸句子**
  (如 "There was no funding to perform this study."),启发式只能认带"标签:"前缀的,于是把多条声明
  全挤进一个标题下。实测样例5:四条声明全挂在 "Author Contributions" 之下。
- **怎么修**:把 back 区声明段落交给 LLM 按标准类别重新切分、命名,移动已有段落重建,DTD 校验否则回滚。
- **凭什么保守**:① 仅当切分能产出比现有**更多**的命名小节(确有挤压)时才应用——若 back 已被妥善
  拆分,跳过,保留现有忠实于源的标题(避免把源 "Acknowledgment" 改成 "Acknowledgments");
  ② 切分须**恰好覆盖**全部声明段落,否则放弃(防丢段);③ 只依据源已有内容,源没有的声明绝不新增。
- **效果**:样例5 back 从 1 个挤压标题 → 5 个命名声明节(资助/利益冲突/伦理/致谢/作者贡献);
  对源 docx 里没有的声明(发表时新增的)不凭空造。

### D. 内容补全(多轮) `agent/reconcile.py` + `agent/repair.py`
- **修什么**:页面可见、输出漏掉的内容。现只保留**一类补全器**:漏认作者(视觉发现作者数少于页面
  所见时重抽)——对应 `loop.py` 的 `REPAIRABLE={extract_authors}`。
- **怎么修**:确定性计数差(视觉⟷XML)驱动,多轮:有可补就修、再核对,直到无可补/改不动/到轮数上限。
  重抽的新作者列表必须**涵盖既有全部作者**(超集校验),否则不动——宁可不补,不把对的改差。
  作者名在 docx 文本流里、可与源核对,这是它与"看图重建表"的本质区别。
- **为什么删掉了"看图重建表"(R17)**:表格图片里的文字**不在 docx 文本流里**,VLM 看渲染页 OCR
  重建=从图片"读"字,读错即编造且无源可核对——样例2 实测编造 617 个源文档没有的词,总缺陷 611→1124
  (翻倍)。图片表现由确定性管线外部化为 `<table-wrap><graphic>`(与金标准处理一致);真缺失的表只记 trace。
- **能力边界(诚实披露)**:漏表(missing_table)、漏图(missing_figure)、漏式(missing_equation)
  **仅记录到 trace、不自动修**(实测这批样例里多为视觉噪声或解析问题),列入优化清单。

## 3. 硬约束与可靠性护栏(明确披露)

系统有两条**硬约束**,贯穿所有修复器:

1. **最终必须 DTD 合法**(JATS Journal Publishing 1.3)——赛题硬要求。每个修复器改完即时校验,不过则回滚。
2. **不编造源文档没有的内容**——正确性底线。每个修复器只移动/重组已有内容或据源/视觉补回真实内容;
   配合**内容守恒校验**(重建后原文每段都在)兜底,杜绝"为凑金标准而捏造"。

除上述两条硬约束外,各修复器还有以下**可靠性护栏**(如实列出,不止两处):

- **A 章节结构**:新增节须有**源标题样式支撑**(已剔除"后接制表符数据行"的表格分组标签),不许凭空造节。
- **C 声明拆分**:**覆盖校验**(切分须恰好覆盖全部声明段落,防丢段)+ **只在能拆出比现有更多的命名小节时才动**
  (back 已妥善拆分则跳过,避免改坏忠实于源的标题)。
- **B 作者归属**:**姓名集合不变**(不增删、不改姓);ORCID **仅清"张冠李戴"**(当前号其实属于他人时才清);
  通讯/共同贡献/邮箱走确定性标记与映射,不让 LLM 在同姓下误判(见 §2.B)。
- **D 内容补全**:只保留**漏作者重抽**(`REPAIRABLE={extract_authors}`),新列表须涵盖既有作者(超集校验);
  漏表/漏图/漏式仅记录不改——"看图重建表"因违背内容守恒已在 R17 删除(见 §2.D)。

> 这些护栏不是限制 LLM 判断,而是防止把噪声(表格标签、漏切段落、同姓误配)当成真实结构,守住"不造结构/不丢段/不错配"。

## 4. 各环节与对应代码

| 环节 | 职责 | 代码 |
|------|------|------|
| 渲染 | docx→PDF→PNG(内容哈希缓存) | `agent/render.py` |
| 视觉普查 | VLM 逐页清点(并发+缓存) | `agent/inspect.py` |
| 章节结构修正 | 据样式重排层级(移动已有块) | `agent/structure.py` |
| 作者归属修正 | LLM 修单位;ORCID/通讯/共同贡献/邮箱走确定性 | `agent/authors_fix.py` |
| 后置声明拆分 | 裸声明句→命名 back 小节 | `agent/declarations.py` |
| 内容补全 | 漏作者重抽(超集校验;漏表/漏图/漏式仅记录 trace) | `agent/reconcile.py`、`agent/repair.py` |
| 编排 | 渲染→普查→四修复器→留痕;支持按阶段消融 | `agent/loop.py` |

## 5. 复现性与稳健性

- **确定性**:每个修复器的判断有保守安全校验(集合不变、内容守恒、源标题支撑),即使 LLM 偶有抖动,
  也只会"不生效/回滚",不会把对的改坏(单测 `tests/test_agent_fixers.py` 守这些护栏)。
- **绝不静默丢内容**:表格构建失败有无损兜底;模型空响应不缓存、计入 `stats.failures`。
- **消融可验证**:`agent/loop.py` 支持按阶段开关(`agent_phases`),`scripts/eval/ablation.py` 逐个关闭
  组件、用指标量化各自贡献(消融 `PYTHONPATH=scripts .venv/bin/python -m eval.ablation`,口径为现行三层评测的缺陷数)。
- **运行档位**:`--llm off` 纯确定性(质量主体,合规、可交付);`--llm local --agent` 完整档
  (在确定性基础上收敛结构难例,实测只好不坏)。
