# 开发者指南（代码走读与扩展）

> 写给维护者和想学习的人：讲清楚每一层在做什么、关键算法怎么运作、怎么安全地扩展。
> 建议配合 `../01-设计/01-架构设计.md`（架构）和 `../00-调研/02-数据与映射规格.md`（映射规格）一起读。

## 1. 数据如何流动

```
docx ──parse──▶ Document(IR)  ──classify──▶ StructuredDoc  ──build──▶ lxml 树 ──serialize──▶ XML
                (物理结构)        (语义结构)                  (JATS DOM)
                                                                │
                                                          validate(DTD)
```

- **IR（中间表示，`model/blocks.py`）**：贴着 docx 的物理结构——按顺序排列的 `Paragraph`/`Table`，段内是 `TextRun`/`MathRun`/`ImageRun`/`BreakRun`。这一层不做任何语义判断。
- **语义模型（`model/structured.py`）**：`StructuredDoc` = 标题 + 作者 + 单位 + 摘要 + 关键词 + body(Section 树) + back + 参考文献 + 图。
- **JATS 树**：用 lxml 构建，保证格式良构、能通过校验。

"物理→语义→JATS"分成三段、彼此分开，好处是每一层都能单独测试、单独替换（比如把规则分类换成 LLM 分类，只动 classify 这一层就行）。

## 2. 逐层走读

### 2.1 parse/（OOXML 解析）
- `docx_reader.py`：用 python-docx 打开文档包、读取样式表和图片部件；再用 lxml 直接遍历 `body` 的子节点，以保证**顺序**正确，也方便控制 OMML（python-docx 不暴露 OMML）。
- `runs.py`：把 `<w:p>` 按文档顺序拆成一个个 run。识别 `w:b/w:i/w:vertAlign`(粗体、斜体、上下标)、`w:drawing`/`v:imagedata`(图片，VML 图标记为 fallback)、`m:oMath`/`m:oMathPara`(公式，区分行内和块级)、超链接。
- `ooxml.py`：命名空间常量，以及 `qn()`/`is_on()` 等工具函数。

### 2.2 classify/（语义识别——启发式引擎）
> 核心难点：docx 的样式名靠不住（样例5 全是 Normal），所以靠**内容 + run 格式**来判断角色。
- `document.py`：主分类器。用"区段状态机"先划出前置/摘要/关键词/正文/参考文献 的边界，再在前置区里识别各项元数据。
- `frontmatter.py`：解析作者行（见 §3.1）、解析单位、姓名翻转、解析日期。
- `sections.py`：识别标题（编号/样式/加粗短行）+ 构建嵌套的 Section 树 + 分配层级 id（见 §3.2）。
- `references.py`：把参考文献切成一条条 + 做轻量字段解析。
- `patterns.py`：所有正则和词典都集中在这里（邮箱/ORCID/日期/稿件类型/机构关键词/题注/小节名…）。**调参主要就改这个文件**。

### 2.3 build/（JATS 构建）
- `jats.py`：命名空间、DOCTYPE、元素工厂 `E()/sub()`、内联格式转换 `append_inline()`、序列化 `serialize()`。
- `metadata.py`：`<front>`（journal-meta 查表 + article-meta + 作者/单位/ORCID/通讯/摘要/关键词/版权）。
- `body.py`：递归渲染 Section 生成 `<body>`/`<back>`；处理图、表的题注，以及块级公式。两类伪表格走**确定性**处理(R17):图片表直接外部化为含 `<graphic>`(整张表图)的 `table-wrap`(不再 VLM 看图重建——OCR 造字);制表符表用 `vision_tables.build_table_from_text_deterministic` 切 Tab 还原 HTML 表,失败时把题注与各行就地渲为 `<p>`(无损兜底)——绝不静默丢表、也不把题注误挂到下一张真实表(避免串号)。
- `figures.py`：把图片外部化（`FigureSource` 取源 + `FigureBuilder` 转 JPG、命名、建目录、建 `<fig>`）。
- `formulas.py`：OMML→MathML3（见 §3.3）。
- `tables.py`：把真正的 `<w:tbl>` 转成 `<table-wrap>`（gridSpan→colspan、首行作表头）。
- `references.py`：生成 `<ref-list>`，按 `structured` 标志输出 element/mixed-citation。
- `xref.py`：解析正文里的交叉引用（见 §3.4）。
- `context.py`：把各个 builder 装配起来，给 body 提供判定和生成用的基础方法。`build_image_table_fallback`（R14 时是 VLM 失败的兜底，R17 起是图片表的**主路径**：确定性外部化为 `<table-wrap><graphic>`）；`build_text_table_det`（制表符表确定性还原）。

### 2.4 enrich/ · llm/ · validate/
- `enrich/journals.py`：查期刊表（`resources/journals.yaml`）。
- `enrich/refs_llm.py`：确定性切分切不动的参考文献难例交 LLM 批量结构化，带**内容守恒护栏**(R17)：返回的 title/source/作者姓名归一化后必须是原文子串，否则整条拒绝、保留 mixed-citation。
- `llm/client.py` + `cache.py`：OpenAI 兼容客户端（`local` 本机 Qwen VLM / DeepSeek / DashScope），可以一键关掉（`--llm off` 也照常出合规结果）+ 按内容哈希磁盘缓存 + 用量计量。`local` 无需 Key，base_url 读 `.env` 的 `LOCAL_LLM_BASE_URL`，缺省 `http://localhost:30000/v1`，模型 id 自动取服务端已加载的那个（多模型时按 id 排序取首，避免顺序漂移）。**可观测性(R14)**：失败/空响应计入 `stats.failures` 并打日志，且**不缓存空响应**(让瞬时抖动下次可重试,而非把一次失败永久冻结)。`cache_dir` 可指定缓存目录——给每次运行一个独立空目录即可绕过缓存、强制真实模型调用(见 `pipeline.ConvertOptions.llm_cache_dir`)。
- `validate/validator.py`：用本地的 JATS 1.3 DTD 做校验。

### 2.5 agent/（LLM 修复闭环——收敛结构难例）
> 权威说明见 `../01-设计/02-智能循环架构.md`，这里只讲代码职责。
> 思路：确定性管线先产出一版合规 XML，随后以 **docx 标题样式 + 渲染页（人眼真值）+ 源文本**为证据，由 **LLM** 逐项判断哪里不忠实于源、该怎么改，就地修复并循环至收敛——**只判结构、不生成文字**（内容守恒，R17 确立）。视觉真值（渲染图 + VLM）独立于被测解析器，不是再跑一遍解析器自证。R15 拆除的是早期“**结构/层级/声明类问题查出却丢弃**”的旧白名单——这些改由 A/B/C 三个修复器实际修复。**内容补全阶段（D）现只保留 `extract_authors` 一类补全器**（`REPAIRABLE` 集合；R17 删除了 `rebuild_table`——VLM 看图重建表=OCR 从图片读字，样例2 实测编造 617 词）；漏表（`missing_table`）、漏图（`missing_figure`）、漏式（`missing_equation`）会被检出但**仅记录到 trace、不自动修复**——这是如实披露的能力边界，已列入优化清单。除此之外修复决策不另设先验白名单，只守两条硬约束：最终 DTD 合法、不编造源里没有的内容（详见架构文档 §3）。

| 模块 | 职责 |
|------|------|
| `render.py` | 输入 docx → PDF（`soffice`）→ 逐页 PNG（`pdftoppm`），纯 CPU；按 docx 内容哈希缓存，闭环多轮复用同一批页面图。 |
| `inspect.py` | 视觉普查：VLM 逐页“看”渲染图，清点页面上实际有什么（表/图/块级公式/章节标题/作者块/参考文献条目数）。并发执行、按图片哈希缓存，**只清点一次**。 |
| `outline.py` | 纯确定性解析我们产出的 XML，给出关键结构计数（硬底线交叉校验用）+ 文本提纲（喂给 LLM 调和、供人工阅读）。 |
| `structure.py` | **章节结构修正（R15）**：据 docx 标题样式序列 + 当前章节树，让 LLM 定正确层级大纲，再**移动已有内容块**重排 `<body>`（只移动、不重写）。新增节须有源标题样式支撑，重建后内容守恒 + DTD 校验，否则回滚。 |
| `authors_fix.py` | **作者归属修正（R15）**：**仅单位 affs 走 LLM**（多单位关联）；ORCID 用**确定性解析**（全名去重音、按词精确匹配，同姓不混）；通讯/共同贡献/邮箱沿用热启动对 `*`/`†` 标记的确定性检测（同姓下 LLM 不可靠，故不用）。作者姓名集合不变前提下回填、重建 `<front>`，DTD 校验否则回滚。 |
| `declarations.py` | **后置声明拆分（R15）**：据源把 back 区无标题的裸声明句按标准类别切分、命名（资助/利益冲突/伦理/致谢/作者贡献…）。仅当能产出更多命名小节、且恰好覆盖全部声明段时才应用，否则跳过；绝不新增源里没有的声明。 |
| `reconcile.py` | 调和：视觉证据 ⟷ XML 提纲 → findings。两路并用——确定性计数差（表/图/式/文献/作者，可定位可驱动修复）+ LLM 整体调和（标题层级/遗漏/错类等需语义判断的问题）。 |
| `repair.py` | 内容补全的修复路由：现只路由 `extract_authors`（重抽漏认的作者、重建 `<front>`，新列表须**涵盖既有全部作者**否则不动）。`rebuild_table` 的路由已在 R17 移除（OCR 造字，见上），漏表等 findings 只记 trace。每次修复都核对“XML 是否真的改了”，没改不计入，不静默乱改。 |
| `loop.py` | 编排器：渲染 → 普查 → 四修复器按 **structure → authors → declarations → content** 顺序执行（content 即调和 → 内容补全多轮，仅修 `REPAIRABLE`＝`{extract_authors}`，**漏表/漏图/漏式只记录不修**）；无可修复 finding / 本轮无修复生效 / 到轮数上限即收敛。全程在同一棵活的 lxml 树上操作并留痕，支持按阶段消融。 |

> 同在 `agent/` 下的 `refine.py` 是 R5 引入的“智能升级层”（`--refine`，也被 `repair.py` 调用来重抽作者）：确定性抽取留缺口时让 LLM 补抽，只填空缺、不覆盖。它是热启动阶段的补救，不属于 R15 四修复器闭环本体。

## 3. 关键算法

### 3.1 作者行解析（`frontmatter.parse_author_line`）
作者通常写在一段里，用上标标出单位、通讯、共同贡献。算法是这样的：先把 runs 合并成一串 `(文本, 是否上标)` 的段；遇到上标段时，它前面累积文本的"尾部姓名"就是当前作者，上标内容解析为 marker（数字→aff、`*`→通讯、`†/#`→共同贡献）；姓名按"最后一个词作姓"翻转成 surname/given-names；并去掉学位后缀（M.D./Ph.D.）。如果没有上标，就退回到按逗号切分 + 剥掉尾部 marker（也兼容 Unicode 上标 `²`）。

### 3.2 标题识别与分节（`sections._heading_level`）
先排除含制表符的行（那是表格数据）和图表题注；编号标题要求是**真正的节号**（带内部的点如 `2.1`，或带结尾的点如 `2.`，这样能排除 "1 month" 这类数据行）；其次看样式名是否暗示这是标题；再不然看是否是"加粗短行 + 常见小节名/标题式"。用栈按级别搭出嵌套树，并分配 `S1/S1.SS1/S1.SS1.SSS1` 这种形式的 id。

### 3.3 OMML→MathML（`formulas.FormulaBuilder`）
用微软 OMML2MML.XSL 的开源移植版，经 libxslt（按 1.0 处理）做转换。这里有两个关键坑：① XSLT 的输出带 `<?xml?>` 声明，得先剥掉再包裹；② **JATS 的 MathML3 DTD 是按字面前缀声明元素的**（DTD 校验不认命名空间），所以必须把默认命名空间下的 MathML **重建成带 `mml:` 前缀**的元素。一段是块级还是行内，看这段是否只含公式 + 编号来判定。

### 3.4 交叉引用解析（`xref.XrefResolver`）
对整棵树的 `<p>/<td>/<th>` 文本做后处理：用正则匹配 `[8-15]`(展开成 b8/b15)、`Fig. N`(→F00N)、`Table N`(→T00N)、`Eqn N`(→E00N)，**只有目标 id 确实存在时**才生成 `<xref>`，否则保留原文（这样不会出现指向空处的 IDREF，保证符合 DTD）。

## 4. 如何扩展

| 需求 | 改哪里 |
|------|--------|
| 新增期刊 | 在 `resources/journals.yaml` 补一条（code/title/abbrev/issn） |
| 新增稿件类型 | `classify/patterns.py` 的 `ARTICLE_TYPES` |
| 调整角色识别规则 | `classify/patterns.py`（正则/词典）+ 对应的 classify 模块 |
| 接入新的 LLM 提供商 | `llm/client.py` 的 `_PROVIDERS`（只要 OpenAI 兼容即可） |
| 扩展交叉引用形式 | `build/xref.py` 的正则 |
| 新增校验规则 | `validate/checks.py`（手写 JATS4R 风格规则;DTD 层在 `validate/validator.py`,未来可叠加 Schematron） |

## 5. 运行 LLM 修复闭环

### 5.1 命令与档位
完整档（确定性 + LLM 难例兜底 + 闭环）：

```
python -m word2jats convert <docx> --llm local --agent
```

- `--agent`：开启 LLM 修复闭环（据 docx 样式 / 渲染页 / 源文本核对 → LLM 判断并就地修复 → 循环收敛；四修复器按 章节结构 → 作者归属 → 后置声明 → 内容补全 顺序）。**必须配合 `--llm`**（如 `--llm local`）提供模型；模型或渲染不可达时自动跳过、直接交确定性管线的输出（优雅降级兜底，不报错）。
- `--agent-rounds N`：闭环最大轮数，默认 3。无可修复 finding、或某一轮没有任何修复生效，会提前收敛。
- 可叠加：`--crossref`（联网补参考文献 DOI/刊名全称）、`--figures <zip或目录>`（外部图片包，缺省用 docx 内嵌图）、`--doi`/`--journal`（指定刊物）。
- 对照基线：`--llm off`（纯确定性，秒级、不依赖模型）即产出合规、可交付的 XML，承担质量主体（R17 后 10 样例总缺陷 356）；`--llm local --agent` 在其上进一步收敛难例（全量 356→228，逐样例只降不升，见迭代日志 R17）。

> 已验证：样例2（8 张图片表，确定性外部化为 graphic）跑 `--llm local --agent` 总缺陷 53→28、无新增编造、DTD 通过（见迭代日志 R17）。评测体系与全样例缺陷清单口径见 `../03-评测/评测体系设计.md`。

### 5.2 连接本地模型服务
`local` 后端走 OpenAI 兼容接口，无需 Key：

- base_url 优先读项目根目录 `.env` 的 `LOCAL_LLM_BASE_URL`，缺省 `http://localhost:30000/v1`（本机 sglang 起的 Qwen VLM 服务，localhost:30000）。
- 模型 id 自动取服务端已加载的第一个模型，命令里无需指定 `--model`。
- 渲染依赖系统命令 `soffice`（LibreOffice，docx→PDF）与 `pdftoppm`（poppler-utils，PDF→PNG），纯 CPU；任一缺失则闭环跳过渲染、退回草稿。
- 地址/超时/默认模型都在 `llm/client.py` 的 `_PROVIDERS["local"]`，渲染细节在 `agent/render.py`，可据此改。

### 5.3 看 trace 与跑评测
- 每次带 `--agent` 运行，都会在输出目录落盘 `{article_id}.agent-trace.json`：一次性视觉普查结果 + 逐轮 findings / 已修复（applied）/ 跳过原因（skipped）/ 修复前后计数。这既是质量门控，也是透明交付依据。
- 评测不再算单一分数、也不用 AI，而是**三层确定性、每条缺陷可追溯到源**地找出输出 XML 的问题（权威设计见 `../03-评测/评测体系设计.md`）。对照物是冻结的 `样例数据/<key>/结构参考.xml`（忠实结构化 A + 可查补全 B、不含出版编辑加工 C）加 `scope.json`，**不是委员会上线版本**。三层各有独立对照物：
  - **L0 合法**（`scripts/eval/validity.py`）：JATS 1.3 DTD 校验 + JATS4R 风格出版规范规则集（error/warning/info 三级），不看参考。
  - **L1 忠实**（`scripts/eval/fidelity.py`）：对源 docx 的词多重集守恒（不丢字/不加字/不改字）+ 外部化图片逐字节 md5 比对。
  - **L2 对位**（`scripts/eval/structure.py`）：对 `结构参考.xml` 按语义键逐类对齐（front/作者/单位/章节/图/表/公式/参考文献/交叉引用/back 等），出命中/漏标/多标 + 缺陷清单；带覆盖守门（遍历参考∪输出两树，元素全集外即报未覆盖）与 B 档补全覆盖率单列。

    一键跑（仓库根目录）：

    ```
    PYTHONPATH=scripts .venv/bin/python -m eval.run --llm off               # 全 10 例，纯确定性、不吃 GPU
    PYTHONPATH=scripts .venv/bin/python -m eval.run --samples 01,03         # 只跑指定样例
    PYTHONPATH=scripts .venv/bin/python -m eval.run --llm dashscope --agent # 云端模型 + Agent 视觉闭环
    PYTHONPATH=scripts .venv/bin/python -m eval.ablation                    # 消融：逐个关闭修复器/阶段，用剩余缺陷数量化贡献
    ```

    产物落 `reports/eval/<tag>/eval.{json,txt,html}`（默认 tag=latest）：两组分列、逐样例三层结果、缺陷清单、B 档覆盖率，顶层无加权总分。`report.py` 负责汇总。

### 5.4 复现性
早期那套 pass@k 复现性评测已废弃、不再使用：它只比 7 个结构计数、且拿我方自己的历史输出当参考目标，等于“稳定复现了自己（含 bug）的输出”，并不证明对源/结构参考正确。现由 §5.3 的三层确定性评测取代（理由见 `../03-评测/评测体系设计.md`）。

现在的复现性来自机制本身：每个修复器都带保守安全校验（集合不变 / 内容守恒 / 源标题支撑 / DTD），LLM 偶有抖动至多导致“不生效、回滚”，不会把对的改坏（`tests/test_agent_fixers.py` 守这些护栏）；ORCID 等结构化数据走确定性解析（非采样）；渲染页是确定性 CPU 产物、按内容哈希缓存。

## 6. 测试与评测
