# 开发者指南（代码走读与扩展）

> 写给维护者和想学习的人：讲清楚每一层在做什么、关键机制怎么运作、怎么把它跑起来、怎么安全地扩展。
> 术语（JATS、DTD、OOXML、OMML、MathML、ORCID、element/mixed-citation、xref 等）在
> `../00-调研/02-数据与映射规格.md` 有集中解释，本文首次用到时也会简要说明。

## 0. 先理解方法：一句话

这个程序把一篇学术论文的 Word 文件（`.docx`）转成 **JATS 1.3 XML**——JATS 是学术出版界通用的
文章结构化标准，用一套固定的 XML 标签把标题、作者、单位、摘要、正文章节、图表公式、参考文献等
逐一标出来；**DTD**（文档类型定义）是这套标签的语法规则书，赛题要求输出必须能通过 JATS 的 DTD 校验。

方法只有一句话，也只有一条路径：

> **让大模型（LLM）做"理解"，让确定性规则做"保证"。**

- **理解**：哪一行是标题、哪一段是作者、哪张表其实是一张图片、某条参考文献的各字段边界在哪——
  这些"这段内容扮演什么角色"的判断，全部交给 LLM。
- **保证**：文本内容**不由 LLM 重写**。程序把 Word 里的原始文字按"源块索引"引用回来，渲染时
  逐字取回，斜体 / 上标 / 加粗零损失；再在出口做硬校验，确保没有一个字是模型编出来的。

这条路径没有可选分支、没有降级档、没有"纯规则档"。它是从旧架构（"规则做理解 + LLM 打补丁"）
**倒置**而来的——旧的 `classify/`（规则理解）和 `agent/`（视觉修复闭环）已整体删除，本文描述的是
倒置之后的现状。

## 1. 数据如何流动

```
docx ─parse──▶ IR(Document)  ─understand(LLM 三 pass)──▶ SemanticDoc  ─render──▶ JATS 树 ─serialize──▶ XML
              物理结构          结构判定(理解层)           语义模型         机械构造
                                                                            │
                                                                     verify(出口校验)
                                                       内容守恒 + DTD 合法 + 结构自洽
```

四个词贯穿全程：

- **IR（中间表示，Intermediate Representation）**：贴着 docx 物理结构的中间数据——按顺序排列的
  段落 / 表格，段内是一个个 **run**（Word 里"一段连续同格式的文字"叫一个 run）。这一层**不做任何语义判断**。
- **内容流（content stream）**：把 IR 序列化成"给 LLM 看的纯文本"，每个源块占一行、带一个稳定的
  `[idx]` 编号。LLM 的所有产出都用 `[idx]` 指回源块。
- **SemanticDoc（语义模型）**：LLM 判定完成后的结构化文档对象——标题、作者、单位、摘要、章节树、
  图表公式、参考文献。它携带的是"已经从 IR 取回的原始 runs 或校验过的子串"，是理解层与渲染层之间
  的**类型化契约**。
- **JATS 树**：用 lxml（Python 的 XML 库）构建，保证格式良构、能过 DTD 校验。

分层的好处：每一层职责单一、能单独测试、单独替换。想换更强的模型只动 `llm/`；想改渲染只动 `render/`；
想加校验只动 `verify/`。

## 2. 目录结构与各模块职责

源码都在 `src/word2jats/` 下。

| 目录 / 文件 | 职责 | 是否含语义判断 |
|-------------|------|----------------|
| `parse/` | **解析层**：docx → IR。用 python-docx 打开文档包、lxml 遍历保证顺序，把段落、表格、内联 run 读出来。 | 否，纯机械 |
| `understand/` | **理解层**：IR → SemanticDoc。序列化内容流、机械定位参考区、跑三个 LLM pass、把 JSON 组装回语义模型。 | **是，理解全在这里** |
| `semantic/model.py` | **语义模型**：定义 SemanticDoc 及其字段（作者/单位/章节/参考…），是理解层与渲染层的契约。 | 否，只是数据类型 |
| `render/` | **渲染层**：SemanticDoc → JATS 树。front / body / back / references / tables 逐部分机械构造。 | 否，纯机械消费 |
| `verify/` | **出口校验**：渲染后自检——内容守恒（有没有编造字）+ DTD 合法 + 结构自洽。 | 否，机械核对 |
| `build/` | **构建原语**（被 render 复用）：`jats`（元素工厂/序列化/DOCTYPE）、`formulas`（OMML→MathML）、`figures`（图片外部化）、`xref`（正文交叉引用）。 | 否，纯机械 |
| `validate/` | **校验与机械修复**：`validator`（DTD 校验）、`checks`（JATS4R 风格规则）、`repair`（悬空引用/空表行的机械修补）。 | 否 |
| `enrich/journals.py` | **期刊查表**：从 `resources/journals.yaml` 按刊号取 journal-meta（这类信息 docx 里通常没有，属出版系统注入，是允许的补全）。 | 否 |
| `llm/` | **模型接入**：`client`（OpenAI 兼容客户端）、`cache`（响应磁盘缓存）。 | 是理解层的执行器 |
| `model/blocks.py` | **IR 数据模型**：TextRun / MathRun / ImageRun / BreakRun / Paragraph / Table / Document。 | 否 |
| `pipeline.py` | **单一编排**：把上面各层串起来（见 §1 的流程图）。 | — |
| `cli.py` | **命令行入口**：`python -m word2jats convert …`。 | — |
| `resources/` | DTD 文件、`journals.yaml`（21 本期刊）、`OMML2MML.XSL`（公式转换样式表）。 | — |

## 3. 逐层走读

### 3.1 parse/（OOXML 解析）
**OOXML** 是 Word 文档 `.docx` 内部的 XML 格式（Office Open XML）。

- `docx_reader.py`：用 python-docx 打开文档包、读样式表和图片部件；再用 lxml 直接遍历 `body`
  的子节点以保证**顺序**正确，也便于处理 python-docx 不暴露的 **OMML**（Office Math Markup
  Language，Word 的公式表示）。
- `runs.py`：把 `<w:p>`（一个段落）按文档顺序拆成一个个 run，识别粗体 / 斜体 / 上下标
  （`w:b`/`w:i`/`w:vertAlign`）、图片（`w:drawing`/`v:imagedata`，VML 图标记为 `is_fallback`——
  多为公式的位图截图，后续忽略）、公式（`m:oMath` 行内 / `m:oMathPara` 块级）、超链接。
- `ooxml.py`：命名空间常量与 `qn()` / `is_on()` 等工具函数。

产物是 `model/blocks.py` 里定义的 `Document`：一个有序的 `blocks` 列表（`Paragraph` 与 `Table`
交错），段落里是 `runs` 列表。这层只搬结构，不判断"这段是什么"。

### 3.2 understand/（理解层——LLM 做判断）
这是本架构的核心。它把 IR 变成语义模型，分七个文件：

- `serialize.py`：把 IR 序列化成**内容流**（`ContentStream`）。关键设计：
  - 每个源块一行，前缀稳定的 `[idx]`；LLM 所有产出都用 `idx` 指回。
  - 上标 / 下标编码成 `^{...}` / `_{...}`——作者姓名后的单位角标、通讯符 `*`、共同贡献符 `†/#`
    都靠上标呈现，编码后 LLM 一眼可辨，且仍是纯文本。
  - **图片 / 公式 / 图片表只给占位符** `⟦IMG#n⟧` / `⟦MATH#n⟧`，**不喂字节、不喂渲染图**——
    从架构上物理杜绝"看图 OCR 造字"（OCR = 光学字符识别，让模型从图片里读字，会编造原文没有的内容）。
  - 行级标注加粗 / 居中 / 样式名 / 列表，给 LLM 判标题、题注、层级的排版信号（有时可靠、有时
    全无——如样式全是 Normal 的样例，此时 LLM 只能靠语义判定）。
- `segment.py`：**机械**定位参考文献区边界。只找明显的文本记号——"References/Bibliography"
  这个词（从后往前找，正文里也可能出现该词，靠后的更稳），或首条 `[1]` 参考条目（无标题时从文档
  55% 位置往后找）。这是表示层的分块，"这段扮演什么角色"仍交给 LLM。前置区窗口上限 `FRONT_CAP=130`
  行——前置元数据总在文档最前，给 front pass 一个足够宽的窗口即可，无需喂整篇。
- `passes.py`：跑三个 LLM pass（front / body / references），把内容流的相应区间喂给模型、取回
  结构 JSON。单次输出上限 `_MAX=8192` token。参考文献可能几十上百条，按 `[N]` 条目边界分块
  （每块 28 条）调用再合并；某块返回条数少于预期（多因输出超上限被**截断**），就**自适应二分**
  递归重试到补齐（`_refs_chunk`）。这是抗超时 / 抗截断的关键，见 `../02-开发/02-代码审查与加固.md`。
- `prompts.py`：三个 pass 的系统提示词（英文书写——被解析的论文正文是英文，英文指令让模型在该
  任务上表现最好；这是实现细节，与"对用户用中文交流"无关）。所有提示词共享一段**铁律前言**：
  内容守恒（每个输出字符串必须是输入的逐字子串）、绝不改写 / 翻译 / 扩写 / 概括 / 读图 / 编造、
  只输出一个 JSON 对象。
- `patterns.py`：**表示层**解析助手——从题注剥"Fig. N."前缀、认出"References"这个词、规整 ORCID、
  给无标题的裸声明配 IMR 规范标题（`CANON_DECL_TITLE`）。注意：这些是"把已有文本切成 label + 正文"
  的表示层操作，不是"这段是什么角色"的语义判断（那已全归 LLM）。
- `assemble.py`：把三个 pass 的 JSON **组装**成 SemanticDoc。核心职责是**索引解析**——LLM 的产出
  以 `idx` 指回源块，这里取回原始 `runs`（正文类内容）或按占位符取回图 / 式；只有必须切分处（作者
  行→逐位作者、参考行→各字段、结构化摘要块内、通讯段）才消费 LLM 给的**子串**，并对子串做守恒检查。
  这里还承载几处机械重建：原生表 `gridSpan→colspan`/`vMerge→rowspan`、制表符表切 Tab 归一成矩形、
  结构化摘要块内切分、公式安全网、参考字段出口守恒（细节见 `02-代码审查与加固.md`）。
- `understand.py`：编排上面几步（序列化 → 定位参考区 → front/body/refs 三 pass → 组装），
  返回 `(SemanticDoc, meta)`。`meta` 记录分块位置与各 pass 原始 JSON，供调试。

**三 pass 的分工契约**（提示词里定义，`assemble` 里消费）：

- **front pass**：产出前置区字段——文章类型 / 分类、标题块索引、作者（姓 / 名 / 关联单位角标 /
  通讯 / 共同贡献 / ORCID / 邮箱）、单位、通讯块索引、日期（收稿 / 修回 / 录用）、编辑、摘要
  （是否结构化 + 各子标题 + 段落索引）、精简摘要（precis）、关键词、前置声明、正文起始块索引。
- **body pass**：**不逐段枚举**，只产出章节大纲（`[{标题块索引, 层级}]`）+ 后置声明 + 特殊块
  （图 / 表 / 公式，带各自覆盖的源块索引）。组装器按标题 level 重建章节树，两标题之间的普通段落
  自动归位，遇特殊块锚点插入并"消费"其跨度。
- **references pass**：逐条切字段——标签、块索引、作者、et al、团体作者、文章标题、刊名 / 书名、
  年 / 卷 / 期 / 起页 / 止页、DOI、注释、出版类型。切不动的整条落回原文（后续渲染成 mixed-citation）。

### 3.3 semantic/model.py（语义模型 = 契约）
定义一组 dataclass：`Author` / `Affiliation` / `Editor` / `DateInfo` / `AbstractSection` /
`Para` / `Figure` / `TableBlock` / `Formula` / `Section` / `Declaration` / `Reference`，容器是
`SemanticDoc`。字段命名和取值口径对齐评测 L2（作者按姓名对齐、图表按题注对齐、参考按 label 对齐、
章节按"归一标题+深度"对齐）。

关键立场就写在这个文件的文档字符串里：正文类对象（`Para`/`Section` 等）携带的是**从 IR 取回的
原始 runs**，不是模型输出的文本；只有 `Author`/`Reference` 这类"必须把一个源块切成多个语义单元"
的对象，才携带 LLM 给的、且经出口校验的子串。**内容守恒因此是结构性成立的**——文字来自 IR，不来自模型。

### 3.4 render/（渲染层——纯机械消费）
LLM 已经把每个源块判成 Para / Figure / TableBlock / Formula 并组织成章节树，渲染器只按类型
逐一构造 JATS 元素，不再做任何"这段是什么"的判断。

- `render.py`：总装。构造 `<article>`，依次挂 front / body / back，再跑交叉引用解析、机械修复、序列化。
- `front.py`：`<front>` = journal-meta（走期刊查表）+ article-meta（作者 contrib-group、单位、
  通讯 author-notes、日期 history、版权 permissions、摘要、关键词）。作者的单位 / 通讯 / 共同贡献
  交叉引用只在对应目标确实存在时才发出（防悬空 IDREF）。通讯段**忠实保留 docx 原文**（邮箱包成
  `<email>`，不模板化重建）；单个作者带孤立 `†/#` 且无声明视为噪声，不生成脚注。
- `body.py`：`<body>` = 递归渲染 Section 树。空 `<p>`、只有标题无内容的空 `<sec>` 会被跳过
  （避免产出违规空元素）。
- `back.py`：`<back>` = 声明类小节（按标题关键词路由到 `<ack>`/`<glossary>`/`<sec>`）+ ref-list
  + IMR 固定的 Publisher's Note。
- `references.py`：`<ref-list>`。字段齐全 → `element-citation`（结构化引用），否则 → `mixed-citation`
  （整段原文兜底）。ref 的 id 取自显示编号并**强制全局唯一**（无标签条目与标签号可能相撞）。
- `tables.py`：TableBlock → `<table-wrap>`。`kind=grid` → `<table><thead><tbody>`（裸 `<th>`、
  裸 `<table>`，与金标准一致，单元格文字逐字来自 runs）；`kind=image` → `<table-wrap><graphic>`
  （整表是图片，绝不 OCR 读图）。
- `context.py`：`RenderContext`——把公式 / 图片 builder 与输出路径打包，供各 render 模块共用，
  只承载机械设施（编号计数、字节外部化），不含内容判定。

### 3.5 verify/（出口校验）
渲染完成后自检，是"让 LLM 主导变安全"的最后一道防线。

- `conservation.py`：**内容守恒校验**。把 docx 和输出 XML 各自拆成"内容词多重集"（token
  multiset——按词计数的集合），比对：输出里有、docx 里没有的内容词 = **编造**（硬违规）；docx 有、
  输出没有的 = 可能漏内容（软信号）。口径与评测 L1 一致（内容词 = 长度≥2 且非纯数字；DOI/ORCID
  链接等"B 档网络子树"允许补全，不计编造）。
- `verify.py`：出口校验入口，综合三项——内容守恒（编造词数）+ DTD 合法 + 结构自洽（`validate/checks`
  的 JATS4R 风格规则），产出一份报告。
- `repair.py`：渲染 + 校验的编排（`render_verify_repair`）。当前它渲染一次并跑校验、产出报告；
  真正的"修复"由**确定性上游守卫**承担（组装层剔除编造字段、渲染层只在目标存在时生成引用、
  `validate/repair` 机械修掉残留悬空引用 / 空表行），而不是事后向 LLM 重问。这是有意的取舍：本架构
  下正文按源块索引取回原文、内容守恒结构性成立，出口几乎无编造可修，LLM 重问既慢又引入非确定性。

### 3.6 build/（构建原语，被 render 复用）
- `jats.py`：命名空间、DOCTYPE、元素工厂 `E()`/`sub()`、内联格式转换 `append_inline()`、序列化 `serialize()`。
- `formulas.py`：**OMML→MathML**。用微软 OMML2MML.XSL 的开源移植版经 libxslt 转换。两个关键坑：
  ① XSLT 输出带 `<?xml?>` 声明，得先剥掉；② JATS 的 MathML3 DTD 按**字面前缀**声明元素（DTD 校验
  不认命名空间），所以必须把 MathML 重建成带 `mml:` 前缀的元素。display（块级）公式的平衡括号会
  折成 `mfenced`，与金标准一致。
- `figures.py`：图片外部化——直写原始字节（按 md5 命中去重，不重编码），建目录、建 `<fig>`。
- `xref.py`：正文**交叉引用**解析。docx 里没有引用域 / 书签，交叉引用全靠文本识别：正则匹配
  `[8-15]`（展开成 b8…b15）、`Fig. N`（→F00N）、`Table N`（→T00N）、`Eqn N`（→E00N），还支持
  拼写数字（"Table one"→T001）。**只有目标 id 确实存在时**才生成 `<xref>`，否则保留原文（不产生
  指向空处的 IDREF）；能递归进入 bold/italic/sup/sub 等内联元素内部（文献引用常被上标包住）。

### 3.7 validate/、enrich/、llm/
- `validate/validator.py`：用本地 JATS 1.3（MathML3）DTD 做结构合法性校验。有一个易踩的坑已处理：
  老版 libxml2 无法解析**含非 ASCII 字符的绝对路径**，而本项目目录名含中文，会导致 DTD 静默加载失败、
  校验退化为"跳过"。修法是先 `chdir` 到 DTD 所在目录、再用相对文件名加载。
- `validate/checks.py`：JATS4R 风格的出版规范检查（悬空引用、重复 id、空正文、缺标题、参考整类丢失、
  ORCID 必须是完整 URL、公式必须含 `mml:math` 等），DTD 管不了"提取得对不对"，这层补上。
- `validate/repair.py`：确定性机械修复——悬空 `xref` 拆壳保留文字、空 `<tr>` 删除，纯结构操作、不改语义。
- `enrich/journals.py`：期刊查表。从 `resources/journals.yaml`（21 本 IMR Press 期刊）按 journal-id
  取 journal-meta；能从 DOI 前缀字母推断刊号（`10.31083/JIN49347` → `JIN`），从 DOI 取文章号（`JIN49347`）。
- `llm/client.py`：统一 LLM 客户端。DeepSeek / DashScope 都是 OpenAI 兼容接口，用 openai SDK
  统一调用；`temperature=0`、`response_format=json_object`（求确定复现）、关闭 Qwen 思维链、
  磁盘缓存、失败计量。模型不可达 / 缺 Key 时 `enabled=False`、调用返回 `None`，理解层据此产出空
  结构（仍出 DTD 合法骨架）——这是接口层的健壮兜底，不是"可选方法分支"。
- `llm/cache.py`：响应磁盘缓存，见 §4.4。

## 4. 如何运行

### 4.1 环境准备
项目用一个独立的虚拟环境 `.venv`（Python 3.12），源码在 `src/` 下但**未 pip 安装**，所以运行时
要用 `PYTHONPATH=src` 把它加进模块搜索路径。

```
python3 -m venv .venv
.venv/bin/pip install -e ".[llm,dev]"     # llm=openai+dotenv，dev=pytest
```

`-e ".[llm,dev]"` 装的是 `pyproject.toml` 里声明的依赖：核心是 python-docx / lxml / Pillow /
PyYAML；`llm` 附加 openai + python-dotenv；`dev` 附加 pytest。

### 4.2 转换一个 docx
命令格式（以样例 03 为例，路径都是仓库根目录下的真实路径）：

```
PYTHONPATH=src .venv/bin/python -m word2jats convert \
    样例数据/03/初始文件.docx \
    --journal JIN \
    --doi 10.31083/JIN49347 \
    --figures 样例数据/03/figures.zip \
    --llm dashscope \
    -o output
```

参数（全部来自 `cli.py`，`--help` 可查）：

| 参数 | 含义 |
|------|------|
| `docx`（位置参数） | 输入 docx 路径 |
| `-o` / `--out-dir` | 输出目录，默认 `output`。XML 落 `<out>/<文章号>.xml`，图片落 `<out>/<文章号>/` |
| `--journal` | 期刊 id（如 RCM/JIN/HSF），缺省时尝试从 DOI 前缀推断 |
| `--doi` | 文章 DOI，如 `10.31083/JIN49347`；决定文章号和 journal-meta |
| `--figures` | 外部图片包（zip 或目录），缺省时从 docx 内嵌图片提取 |
| `--llm` | 理解层模型后端，`dashscope`（默认）/ `local` / `deepseek`。**方法必需**——理解全靠它 |
| `--no-validate` | 跳过出口校验（DTD + 内容守恒 + 结构自洽），只出 XML |

运行后终端打印文章号、各项统计（作者数 / 单位数 / 章节数 / 图表公式计数 / LLM 调用与 token 数 /
出口校验的编造词数 / 耗时）和 DTD 校验结论。

### 4.3 LLM 配置（.env）
云端 provider 需要 API Key，从仓库根目录的 `.env` 读取（`.env.example` 是模板，复制成 `.env`
填真实值）。默认后端是 **DashScope**（阿里云百炼，OpenAI 兼容模式），默认模型 **qwen3.7-plus**
（文本与视觉同一模型），需要两个变量：

```
DASHSCOPE_API_KEY=sk-xxxxxxxx
DASHSCOPE_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
```

其他后端：`deepseek` 需 `DEEPSEEK_API_KEY` / `DEEPSEEK_BASE_URL`；`local` 是本机
sglang/vLLM 起的 OpenAI 兼容服务（无需 Key，`LOCAL_LLM_BASE_URL` 缺省 `http://localhost:30000/v1`，
模型 id 自动取服务端已加载的那个）。三家的模型名 / base_url 都在 `llm/client.py` 的 `_PROVIDERS`。

模型超参固定：`temperature=0`、`response_format=json_object`、关闭思维链、单次输出上限 8192 token、
DashScope 请求超时 240 秒。**不做超参调优**（temp=0 求确定复现）；架构 model-agnostic，可换更强模型
（`LLMClient(model=...)`）。

### 4.4 缓存机制
每次 LLM 请求按内容哈希缓存到磁盘，**重复运行零额外成本、结果可复现**（对评测复现和控成本都关键）。

- 缓存键 = `(provider, model, system, user)` 的 SHA256；命中则直接读盘、不再调模型。
- 默认缓存目录是当前工作目录下的 `.llm_cache/`（已在 `.gitignore` 忽略）。
- **空响应不缓存**——让一次瞬时抖动下次可重试，而不是把失败永久冻结。
- 想强制真实调用（绕过缓存）：给一个独立空目录当缓存目录即可（`ConvertOptions.llm_cache_dir`，
  评测驱动就是这么给每个样例隔离缓存的）。

### 4.5 跑评测
评测对冻结的"结构参考"逐条找缺陷，是本项目质量把关的权威手段（设计见 `../03-评测/评测体系设计.md`）。
在 `scripts/` 目录下运行（`eval.run` 会自己把 `src/` 加进搜索路径、向上找到根目录的 `.env`）：

```
cd scripts && ../.venv/bin/python -m eval.run --llm dashscope           # 全 10 例
cd scripts && ../.venv/bin/python -m eval.run --llm dashscope --samples 03,S03   # 指定样例
```

评测流程：对每个样例跑转换 → L0 合法（`validity.py`：DTD + JATS4R 风格规则）→ L1 忠实
（`fidelity.py`：对源 docx 的词多重集守恒 + 图片逐字节 md5）→ L2 对位（`structure.py`：对
`结构参考.xml` 按语义键逐类对齐，出命中 / 漏标 / 多标 + 缺陷清单）→ `report.py` 汇总。产物落
`reports/eval/<tag>/{eval.json,eval.txt}`（默认 tag=latest），顶层无加权总分，0 缺陷即满分。
对照物永远是冻结的 `样例数据/<key>/结构参考.xml` + `scope.json`（不是委员会上线版本）。当前实测
成绩以 `../03-评测/评测体系设计.md` 和 `../02-开发/03-迭代日志.md` 为准。

### 4.6 跑测试
```
.venv/bin/python -m pytest -q
```

共 **60 项**，三个文件（`pyproject.toml` 已把 `src/` 设为 pytest 的 pythonpath，无需手动指定）：

- `tests/test_eval.py`：**评测器自身回归**——遍历 10 例锁住关键不变量（参考自比 L2 零缺陷、
  覆盖守门零未覆盖、参考过 L0 零 error、L2 两跑逐字节一致，另核 `scope.json` 与实测参考一致）。
  纯确定性，不依赖模型 / GPU。
- `tests/test_integration.py`：遍历 10 例端到端转换 + DTD / 出版规范断言 + 退化输入（无 DOI /
  无图片包）。
- `tests/test_render_units.py`：渲染层单元测试——制表符表切分丢空格、矩形归一补 / 并列、结构化
  摘要按子标题切分且保斜体、标题前缀剥离、规范声明标题、表格 label 剥离、xref 拼写数字。

**改完代码务必跑 pytest**——10 例的端到端 DTD 校验是"没改坏"的最强保障。

## 5. 如何扩展

| 需求 | 改哪里 |
|------|--------|
| 新增期刊 | 在 `resources/journals.yaml` 的 `journals:` 下补一条（journal-id / title / abbrev / issn） |
| 接入新的 LLM 提供商 | `llm/client.py` 的 `_PROVIDERS`（只要 OpenAI 兼容即可） |
| 换更强 / 换默认模型 | `_PROVIDERS[<provider>]["default_model"]`，或调用时传 `LLMClient(model=...)` |
| 调整 LLM 的判定行为 | `understand/prompts.py` 的三个 pass 系统提示词（增删输出字段、改判定口径） |
| 增删语义字段 | `semantic/model.py` 定义字段 → `understand/assemble.py` 组装 → `render/*` 渲染，三处对齐 |
| 扩展交叉引用形式 | `build/xref.py` 的正则 |
| 新增校验 / 出版规范规则 | `validate/checks.py`（JATS4R 风格）；DTD 层在 `validate/validator.py` |
| 调整表述层解析（题注前缀 / ORCID / 规范标题） | `understand/patterns.py` |

扩展时守住两条硬约束：**最终 DTD 合法**、**不编造源里没有的内容**（内容守恒）。新增语义字段后，
记得在提示词里让 LLM 只给原文子串、并在组装 / 出口做守恒检查。改完跑 pytest。
