# 02 · 领域基础

这个项目要做的事，是把一篇 Word 投稿稿转成学术出版界通用的结构化 XML。要看懂它，先得懂它所在的领域。这一篇从零讲清五块背景：目标格式 **JATS** 长什么样、源头的 **docx** 内部是怎么组织的、公式为什么得换一套写法、参考文献有哪两种著录法、以及 **JATS4R** 这个"最佳实践"补了什么。每块都不假设你是同行，术语第一次出现就用大白话解释，并尽量拿项目里真实存在的文件片段来印证。读完这一篇，后面几篇讲"怎么做、做得怎么样"你就能跟上了。

每节末尾都附了出处，方便你自己追查核对。

## 一、JATS 1.3：给论文结构做标注的 XML 标准

### 先说清楚两个底层概念

**XML** 是一种通用的数据格式，特点是用成对的尖括号标签把内容裹起来，标明"这段是什么"。比如 `<article-title>论文标题</article-title>`，一看就知道中间那串字是标题。标签可以层层嵌套，于是一份 XML 就是一棵有名有姓的树。

**DTD**，全称 Document Type Definition（文档类型定义），是一份规则文件，规定"这类 XML 里允许出现哪些标签、谁能套在谁里面、哪些是必填的"。有了 DTD，就能拿一份 XML 去比对规则、判断它"合不合法"。

理解了这两点，就能理解 JATS 的本质：它就是一套专门为学术论文定制的标签词汇表加配套 DTD。所谓"生成合法的 JATS XML"，说白了就是产出一份能通过 JATS DTD 校验的 XML。

### JATS 是什么、解决什么问题

**JATS**，全称 **Journal Article Tag Suite**（期刊文章标签套件），是学术出版界通用的、用 XML 描述期刊论文结构的标准。它的正式标准号是 **ANSI/NISO Z39.96**，最早由美国国家医学图书馆（NLM）在 2002 年发起，如今由美国的标准化组织 NISO 维护。PubMed Central 等大型文献库交换和长期保存论文全文，用的就是它。

出版界为什么需要这么一套东西？一篇论文出版后，出版社要在网站上排版、要推送进各类数据库、要生成 PDF、要支持全文检索、要让引文系统匹配上参考文献。如果每个系统各用各的格式，彼此就没法交换。JATS 的价值，就是**把论文的"结构语义"（谁是作者、哪段是摘要、哪条是参考文献、哪个是公式）从"排版长什么样"里剥离出来**，固化成一份中立、机器可读、能长期归档、能跨系统交换的 XML，下游各取所需。这恰好对应本竞赛的任务本质：只给内容加上结构，不改动内容本身。

### 三种"口味"，本项目用哪一种

JATS 并非只有一套标签，而是提供了三套详略和松紧不同的版本，供不同环节使用：

| 标签集 | 面向的场景 | 约束宽严 |
|---|---|---|
| Journal Archiving（归档，绿版） | 长期保存、尽量兼容各种既有内容 | 最宽松 |
| **Journal Publishing（出版，蓝版）** | **出版社生成发表内容** | **居中** |
| Article Authoring（写稿，橙版） | 作者撰写稿件 | 最严格 |

本项目产出的正是中间那套 **Journal Publishing**。证据钉在每份样例 XML 的第二行 DOCTYPE 声明上（`样例数据/01/结构参考.xml`）：

```
<!DOCTYPE article PUBLIC
  "-//NLM//DTD JATS (Z39.96) Journal Publishing DTD v1.3 20210610//EN"
  "https://jats.nlm.nih.gov/publishing/1.3/JATS-journalpublishing1-3.dtd">
```

这一行同时钉死了四件事：标准是 **JATS（Z39.96）**、口味是 **Journal Publishing**、版本是 **v1.3**、发布日期 **2021-06-10**。也就是说，本项目锁定的 **JATS 1.3 是 2021 年的版本**。NISO 后来在 2024 年又发布了 1.4，但 1.3 是本竞赛既定的基线，不是用了过时的东西。为保证离线可复现，项目把这套 1.3 的 DTD（连同后面要讲的 MathML3 和一批 ISO 字符实体集）完整内嵌在了仓库里（`src/word2jats/resources/dtd/`），校验时不必联网去 NLM 的服务器取。

### 一篇文章的固定骨架：front / body / back

JATS 文档的根标签是 `<article>`，往下固定分三大段，这是所有 JATS 文档共同的顶层结构：

- **`<front>`**——头部，装**全部元数据**：发在哪本刊、谁写的、什么单位、什么时候收稿发表、版权归谁、摘要、关键词。
- **`<body>`**——正文主体：章节、插图、表格、公式。
- **`<back>`**——尾部：参考文献、致谢、声明、附录、脚注。

`<front>` 内部再分两块。`<journal-meta>` 是期刊级信息，同一本刊的所有文章都一样；`<article-meta>` 是本篇独有的信息。看一段真实的期刊元数据（`样例数据/01/结构参考.xml`）：

```xml
<journal-meta>
  <journal-id journal-id-type="publisher-id">RCM</journal-id>
  <journal-title-group>
    <journal-title>Reviews in Cardiovascular Medicine</journal-title>
    <abbrev-journal-title abbrev-type="publisher">Rev. Cardiovasc. Med.</abbrev-journal-title>
  </journal-title-group>
  <issn pub-type="ppub">1530-6550</issn>   <!-- 纸质版刊号 -->
  <issn pub-type="epub">2153-8174</issn>   <!-- 电子版刊号 -->
  <publisher><publisher-name>IMR Press</publisher-name></publisher>
</journal-meta>
```

这里的 **ISSN**（International Standard Serial Number，国际标准连续出版物号）是一本期刊的国际编号，纸质版和电子版各有一个。

再看 `<article-meta>` 里一个真实的作者条目：

```xml
<contrib contrib-type="author" corresp="yes">
  <contrib-id contrib-id-type="orcid">https://orcid.org/0000-0003-3315-7840</contrib-id>
  <name><surname>Dang</surname><given-names>Aimin</given-names></name>
  <degrees>M.D., Ph.D.</degrees>
  <xref ref-type="aff" rid="aff1"><sup>1</sup></xref>       <!-- 上标 1，指向机构 aff1 -->
  <xref ref-type="corresp" rid="cor1"><sup>*</sup></xref>   <!-- 通讯作者标记 -->
  <email>amdangfw@163.com</email>
</contrib>
```

这里出现了一个贯穿整个 JATS 的机制——**交叉引用**。作者用 `<xref rid="aff1">` 指向文中某个 `<aff id="aff1">`（机构条目），靠 `id`（给元素起的锚点名）和 `rid`（引用这个锚点）两个属性配对，效果类似数据库里的外键，把"作者"和"他的单位"关联起来。文中的"见图 1""见参考文献 [5]"也都是这么挂上去的。片段里的 **ORCID** 是研究者的一个全球唯一数字身份码。`<article-meta>` 里其余常见构件还有：`<article-id pub-id-type="doi">`（文章的 **DOI**，一个永久唯一的标识符）、`<title-group>`（标题）、`<history>`（收稿/修回/接收日期）、`<permissions>`（版权与开放获取许可）、`<abstract>`（摘要，可以再切成结构化小节）。

`<body>` 里的主要构件：`<sec>`/`<title>`/`<p>`（章节/章节标题/段落，可层层嵌套）、`<fig>`（插图）、`<table-wrap>`/`<table>`（表格）、`<disp-formula>`（独立成行的公式）和 `<inline-formula>`（夹在句子里的行内公式）。看一段真实的插图（`样例数据/01/结构参考.xml`）：

```xml
<fig id="F001" position="float">
  <label>Fig. 1</label>
  <caption><title>Calibration plots of models</title></caption>
  <graphic xlink:href="RCM46777/fig-01.jpg" id="F001.g1"/>
</fig>
```

注意图片是**外部化**存的——XML 里只用 `<graphic xlink:href>` 存一个文件名指针，图片本身另存为独立文件，不塞进 XML。项目的做法是：从 docx 内嵌的媒体里把图片字节按它在正文里出现的先后顺序取出来，命名成 `{文章号}/fig-0N.<原格式扩展名>`（文章号取 DOI 短号，如 `RCM46777`），**直接写原始字节、不重新编码**，原来是 jpeg 就存 `.jpg`、png 就存 `.png`。XML 里只留文件名。图片外部化是竞赛的明确要求，也符合出版实务。

`<back>` 里最要紧的是参考文献 `<ref-list>`，放到第四节专门讲。

### 两个命名空间

`<article>` 根标签上还会声明两个 XML **命名空间**（namespace，一种给标签加"出身前缀"、避免不同来源的标签重名的机制）：

```xml
<article xmlns:mml="http://www.w3.org/1998/Math/MathML"
         xmlns:xlink="http://www.w3.org/1999/xlink"
         dtd-version="1.3" article-type="research-article">
```

- **`xlink:`** 来自 W3C 的 XLink（XML 链接语言）。JATS 用它的 `xlink:href` 属性来"指向外部资源"，比如上面图片指针里的那个 `xlink:href`。
- **`mml:`** 来自 W3C 的 MathML。凡是带这个前缀的标签，都表示"这段归 MathML 管"，也就是公式（见第三节）。

> **出处**：JATS 全称、标准号、三套标签集与松紧定位——<https://jats.nlm.nih.gov/>；版本 1.3=2021、1.4=后续——<https://jats.nlm.nih.gov/versions.html>；元素释义——项目内《JATSv1.3 完整手册.pdf》；真实片段——`样例数据/01/结构参考.xml`；图片外部化命名规则——`样例数据/说明.md`。这三个"绝不能混"的对象（源文件、上线版本、结构参考）和它们各自的角色，在 [03-数据与结构参考](03-数据与结构参考.md) 里讲透。

## 二、docx / OOXML：源文件内部是什么样

要转换 docx，先得知道打开它看到的是什么。

`.docx` 说白了就是**一个换了后缀的 zip 压缩包**，正式名字叫 **Office Open XML（OOXML）**，由微软主导，2006 年成为 Ecma 标准 ECMA-376，2008 年又成为国际标准 ISO/IEC 29500。把任意一个 `.docx` 解压，里面是一堆 XML 文件和媒体文件（对 `样例数据/01/初始文件.docx` 实测）：

```
word/document.xml              正文主体：标题、作者、正文、参考文献几乎全在这一个文件里
word/styles.xml                样式定义
word/media/image1.wmf          内嵌图片，一个个躺在 media/ 目录下
word/_rels/document.xml.rels   关系文件：正文里的引用编号 ↔ 实际媒体文件 的映射表
```

**一个关键认知：论文的文字内容，几乎全挤在 `word/document.xml` 这一个文件里。** 这就是解析器要啃的东西。

它的正文是一棵嵌套的标签树，核心是三层（标签都带 `w:` 前缀）：

| 标签 | 含义 |
|---|---|
| `<w:p>` | paragraph，一个段落 |
| `<w:r>` | run，段落里**格式一致的一小段**——只要改一处加粗、字号或颜色，就会断成一个新 run |
| `<w:t>` | text，run 里真正的那串文字 |

这里藏着解析 docx 最典型的一个坑：**一句连贯的话，在 Word 内部常常被切成好几个 run**。某个词加粗、某个字是上标，Word 就把它单独切成一个 `<w:r>`。所以从 `<w:t>` 里读出来的往往是零碎的文字块。解析器的活儿，就是把这些被样式切碎的 run 重新拼成连续的文本，同时记住哪一段是加粗、哪一段是斜体、哪一段是上下标，将来好映射成 JATS 里的 `<bold>`/`<italic>`/`<sup>`/`<sub>`。这个"run 切分"的现象后面还会再遇到——它也是评测里某些"假差异"的根源（见 [06-评测与成绩](06-评测与成绩.md)）。

图片和公式在 docx 里长这样：`<w:drawing>` 是"这里有一张图"的占位，内部用编号指向 `word/media/` 里的真实图片文件；`<m:oMath>` 则是一个数学公式，用的是微软自己的数学标记 OMML（下一节讲）。

> **出处**：OOXML 是 zip 包、ECMA-376/ISO 29500 的沿革——<https://en.wikipedia.org/wiki/Office_Open_XML>；docx 内部目录结构与各标签——对 `样例数据/01/初始文件.docx` 解压实测。

## 三、OMML → MathML：公式为什么要换一套写法

### 为什么非转不可

根子上是两套数学标记语言互不兼容：

- **Word 里的公式用 OMML**——全称 Office Math Markup Language，是 OOXML 标准的一部分，标签带 `m:` 前缀（就是上一节那个 `<m:oMath>`），微软自家的格式。
- **JATS 里的公式必须用 MathML**——**MathML** 是 W3C 制定的国际标准数学标记语言，3.0 版于 2010 年成为 W3C 推荐标准（2014 年发布第二版），并被采纳为国际标准 ISO/IEC 40314。本项目用的 DTD 正是"Journal Publishing 加 **MathML 3**"的版本，DTD 主文件名就写着 `JATS-journalpublishing1-3-mathml3.dtd`。

于是逻辑很清楚：docx 里存的是 OMML，JATS 里要的是 MathML，中间必须做一次 **OMML→MathML** 转换。这是硬约束，不是可选项。

### 怎么转

业界的标准做法，是套用一张微软官方提供的 **XSLT 样式表**（XSLT 是一种"把一种 XML 变换成另一种 XML"的模板语言）。Word 自带一张 **`OMML2MML.XSL`**，专门干 OMML→MathML 这件事，而且它可以脱离 Word 单独使用——直接拿从 docx 里抽出来的公式去跑这张样式表，出来就是 MathML。本项目用的正是这张样式表（`src/word2jats/resources/OMML2MML.XSL`）。学术出版界把 Word 公式搬进 JATS，走的也是这条经典路线。

转换出来长什么样？看 `样例数据/03/结构参考.xml` 里一个真实的块级公式（有删节）：

```xml
<disp-formula id="E001">
  <label>(1)</label>
  <mml:math display="block" alttext="AF=\frac{\sum_{i}{P(f_i)×f_i}}{\sum{P}}">
    <mml:mrow>
      <mml:mi>A</mml:mi><mml:mi>F</mml:mi><mml:mo>=</mml:mo>
      <mml:mfrac> ... </mml:mfrac>       <!-- 一个分式 -->
    </mml:mrow>
  </mml:math>
</disp-formula>
```

几个要点：MathML 用标签把数学结构一层层描述出来——`mml:mi` 是标识符（变量）、`mml:mo` 是运算符、`mml:mfrac` 是分式；`display="block"` 表示这是独立成行的块级公式（对应句中行内公式则是 `<inline-formula>`）；`alttext` 属性里还顺手存了一份类 LaTeX 的纯文本，给那些渲染不了 MathML 的场景兜底。这个"既给 MathML 又给一份文本"的做法，正好呼应第五节要讲的最佳实践。

> **出处**：OMML 属于 OOXML、`OMML2MML.XSL` 随 Word 附带且可独立使用——<https://learn.microsoft.com/>、<https://www.ncbi.nlm.nih.gov/books/NBK350572/>；MathML 是 W3C 标准、对应 ISO/IEC 40314——<https://www.w3.org/TR/MathML3/>；项目内嵌的 MathML3 版 DTD 与样式表——`src/word2jats/resources/`；真实公式——`样例数据/03/结构参考.xml`。

## 四、参考文献著录：element-citation 与 mixed-citation

一条参考文献，JATS 允许用两种方式来写，两种都是官方认可的合法写法，区别在"拆得多细"。

### 结构化著录 `<element-citation>`

把一条文献的每个字段都**拆成独立的标签**：作者拆成 `person-group` 下的一串 `name`（每个再分 `surname` 姓、`given-names` 名），此外还有 `article-title`（篇名）、`source`（期刊名）、`year`（年）、`volume`（卷）、`fpage`/`lpage`（起止页）等等。它内部**不放排版用的标点**——逗号、句号、卷页之间那些分隔符，都由下游按具体期刊的样式规则临时生成。看真实片段（`样例数据/01/结构参考.xml`，有删节）：

```xml
<ref id="b1">
  <label>[1]</label>
  <element-citation publication-type="journal">
    <person-group person-group-type="author">
      <name><surname>Faggiano</surname><given-names>P</given-names></name>
      <name><surname>Dasseni</surname><given-names>N</given-names></name>
    </person-group>
    <article-title>Cardiac calcification as a marker …</article-title>
    <source><italic>European Journal of Preventive Cardiology</italic></source>
    <year>2019</year><volume>26</volume><fpage>1191</fpage><lpage>1204</lpage>
  </element-citation>
</ref>
```

这样一来，机器能精确读出"第一作者姓 Faggiano、2019 年、第 26 卷、1191 到 1204 页"。**什么时候用它**：当你想要机器可处理的结构化数据时——自动匹配 DOI、构建引文网络、按不同期刊的样式随时重新排版。代价是标注量大、每个字段都得抽准。

### 自由文本著录 `<mixed-citation>`

把一条文献**基本按最终排版好的样子存成一整串文本**，只做很轻的内部标注，排版时的标点和先后次序原样保留。看真实片段（`样例数据/S03/结构参考.xml`，有删节）：

```xml
<mixed-citation publication-type="journal">ESHRE Guideline Group on RPL, Bender Atik, R.,
  Christiansen, O. B., … &amp; Goddijn, M. (2023). ESHRE guideline: recurrent
  pregnancy loss: an update in 2022. <source><italic>Human reproduction open</italic></source>,
  2023(1), hoad002.</mixed-citation>
```

可以看到，整条引文基本是一串连排的文本，标点、括号、卷期页码都按显示样子保留，只有期刊名用 `<source>` 轻轻标了一下。

**什么时候用它**：当你手头只有排好版的引用串，逐字段拆解成本高或容易拆错，而你又想原样保住它的显示效果时。代价是机器很难精确取用其中某一个字段。

### 一个真实且重要的观察

这两种写法在真实的出版产物里是**并存**的，选哪种取决于产出流程，没有绝对的优劣——都是合法 JATS。本项目为 10 个样例建的结构参考，统一走 `element-citation` 全字段结构化，这是一个有意的选择：结构化数据信息量更大，既方便评测逐字段比对，也更利于复用。10 个样例里，只有补充组的 **S03** 的结构参考里含少量 `mixed-citation`。至于"结构参考"到底是个什么对象、为什么这么定，见 [03-数据与结构参考](03-数据与结构参考.md)。

顺带认识一个名字：上面那串文本的排法——"作者姓加名的首字母，多作者用 et al.；接篇名；接期刊名；再接年份、卷、起止页"——就是医学文献通行的 **NLM/Vancouver 风格**（PubMed 采用的引文样式）。认得它，就能理解"为什么参考文献偏偏是这几个字段、顺序偏偏是这样"。

> **出处**：两种著录方式的定义与定位——项目内《JATSv1.3 完整手册.pdf》；真实片段——`样例数据/01/结构参考.xml`、`样例数据/S03/结构参考.xml`；本项目统一用 element-citation 的口径——`样例数据/说明.md`；NLM/Vancouver 风格——美国国家医学图书馆《Citing Medicine》。

## 五、JATS4R：DTD 管不到的那部分

### 它是什么

**JATS4R**，全称 **JATS for Reuse**（为"复用"而生的 JATS），是一个社区工作组（自 2018 年起挂靠 NISO）。它专门研究"JATS 该怎么标，标出来的内容才能最大程度地被复用和交换"，并把研究结论写成一套**最佳实践推荐**。

### 为什么需要它——DTD 的能力有边界

关键在于：**JATS 的 DTD 只能校验"结构合不合法"，管不了"标得好不好、一不一致"。** 举两个例子就明白了：DTD 允许 `<year>` 里放任意文本，却没法要求"年份必须是四位数字"；DTD 允许一个公式给出多种表示，却没法要求"这几种表示必须在数学上等价"。这一类超出 DTD 表达能力的规则，正是 JATS4R 要补的空档。

技术上，JATS4R 把这些推荐写成 **Schematron**——一种基于"规则加断言"的 XML 校验语言，专门用来表达 DTD 表达不了的约束（比如"若出现 A 则必须满足 B"），并按错误级别和主题（如 math 数学、permissions 版权）分门别类地校验。

### 举两个例子

- **公式**：当一条公式用 `<alternatives>` 同时给出多种表示（比如既给 MathML、又给 LaTeX）时，JATS4R 要求每一种表示都正确、完整，且彼此在逻辑上等价；而且它**明确不偏向 MathML**——`<alternatives>` 内部没有哪个是隐含的"首选表示"。
- **版权与许可**：对 `<permissions>`（版权声明、许可证、开放获取标记）该怎么标，JATS4R 给出统一规范，好让下游系统能可靠地判断"这篇能不能被复用、以什么许可复用"。

### 对本项目意味着什么

DTD 合法只是"及格线"，JATS4R 代表"更专业的做法"。是否逐条落地 JATS4R 是一个取舍；但理解它，能解释很多"样例为什么这么标"的细节——比如公式为什么既给了 `mml:math` 又在 `alttext` 里存一份文本，版权为什么要完整地给出声明加许可证。本项目的评测在"DTD 合法"之外，也参考了 JATS4R 的部分规范（见 [06-评测与成绩](06-评测与成绩.md)）。

## 把整条链串起来

一句话概括 word2jats 所在的领域：它读进一个 `.docx`（本质是 OOXML 的 zip 包，正文挤在 `document.xml` 里，靠 `w:p`/`w:r`/`w:t` 三层标签承载文字、`w:drawing` 承载图、`m:oMath` 承载公式），再"只加结构、不改字"地把内容重新组织成一份合法的 **JATS 1.3 Journal Publishing** XML——front/body/back 三段式，图片从 docx 内嵌媒体按顺序取出、外部化成 `{文章号}/fig-0N.<原格式>` 的独立文件，公式经 OMML→MathML 转成 `mml:math`，参考文献著录成 `element-citation`——并尽量向 JATS4R 的最佳实践看齐。

难点也就藏在这条链里：判断"哪段是标题、哪条是参考文献"要读懂内容，而搬运正文文字又要求一个字都不能动。这两个方向相反的要求怎么同时满足，正是 [04-系统设计](04-系统设计.md) 要回答的。
