# 03 · 数据与结构参考

这篇讲我们拿什么数据来做、拿什么当"正确答案"、以及两者之间那条容易被忽略却决定成败的边界。**看这个项目，最容易犯的错是把出版社的"上线版本"当成要逐字节还原的目标——那是错的。** 这篇就把这件事讲透。

## 每个样例目录里有什么

主办方给了 10 个样例，平铺在 [`样例数据/`](../样例数据/) 下（`01`–`05`、`S01`–`S05`）。每个样例目录的文件（据 [`样例数据/说明.md`](../样例数据/说明.md)）：

| 文件 | 是什么 | 谁提供 |
|---|---|---|
| `初始文件.docx` | 投稿用的 Word 论文稿，**内容的唯一权威** | 主办方 |
| `结构参考.xml` | 评测的对照物：忠实结构化 docx 得到的 JATS XML（下面详解） | 本队构建、人工核定、冻结 |
| `上线版本.xml` | 出版社最终发表的 JATS XML——**仅 01–05 有** | 主办方 |
| `figures.zip` | 当初构建 `结构参考.xml` 时从 docx 内嵌媒体抽出的图片中间产物；转换器与评测都不再使用它 | 本队（中间产物） |
| `scope.json` | 该样例的可查证元数据清单与已知编辑加工记录（审计用） | 本队 |
| `附件.zip` | 补充材料（目前仅 01 有） | 主办方 |

## 三个绝不能混的对象

这是理解整个任务的关键。做"结构化技术"必须严格区分三样东西（据 [`样例数据/说明.md`](../样例数据/说明.md)）：

| 术语 | 指什么 | 它的角色 |
|---|---|---|
| **源文件** | `初始文件.docx` | 内容的唯一权威。要输出的每个字都以它为准 |
| **上线版本** | 出版社最终发表的 `上线版本.xml`（仅 01–05） | = 忠实结构化 **+ 出版方的编辑加工**。**不是评测目标**；只用作出版体例的格式模板、抽全性核对、元数据旁证 |
| **结构参考** | 为 10 例各建的 `结构参考.xml` | = "把 docx 忠实结构化 + 补齐可查可推的元数据、但不含编辑加工"的理想产物。**这才是评测打分的对照物** |

为什么上线版本不能当目标？因为出版社在正式发表前，编辑做了大量 docx 里根本没有的加工——改写标题和摘要、替换或重排参考文献、修订文字、补写声明、改正作者笔误、事后填上收稿日期。这些信息**在 docx 里不存在，任何忠实于 docx 的转换器都不可能、也不应该把它们"还原"出来**。硬要对齐上线版本，就等于要求转换器去猜测和编造原文没有的内容——这与"不改内容"的任务本质直接冲突。

所以评测的对照物是**结构参考**：它只包含"从 docx 能忠实做出来的（A）"加"可查可推的标准元数据（B）"，剔除了"出版方编辑加工（C）"。转换器的目标，是产出**合法、完整、忠实还原 docx 结构**的 JATS，而不是去逼近那个掺了人工加工的上线版本。

## A / B / C 三档边界：该做、可做、不做

把上面这条边界说得更精确，就是三档（据 [`样例数据/说明.md`](../样例数据/说明.md) 与各样例 `scope.json`）：

- **A 档——该做，docx 里直接就有**：正文、标题、作者、单位、摘要、关键词、参考文献原文、表格、图题、公式。逐字来自 docx OOXML，作者的拼写/时态/大小写/疑似笔误一律原样保留。这是转换器的主战场。
- **B 档——可做，可查可推的标准元数据**：期刊名/ISSN（按刊号查表）、`article-id`（= DOI）、版权与开放获取声明模板、交叉引用的关联关系。这些 docx 里通常没有，属出版系统按固定规则注入，可靠且可核实，所以补齐。
- **C 档——不做，出版方的编辑加工**：改写的标题摘要、替换重排的参考文献、修订过的文字、补写的声明句、改对的笔误、事后填的日期、docx 里没有的样板小节。**这些既不做、也不作为评测扣分依据**——因为它们不在 docx 里，忠实的转换器本就够不着。

一句话：**A 是必须还原的，B 是合理补齐的，C 是刻意不碰的。** 评测正是按这条边界设计的（[06-评测与成绩](06-评测与成绩.md)）。

## "结构参考"是怎么建出来的（可审计）

结构参考是评测的标尺，所以它本身必须做得扎实、可核对。构建方法（据 [`样例数据/说明.md`](../样例数据/说明.md)）：

1. **忠实优先**：正文/标题/作者/参考/表格/图题的每个字符逐字来自 docx OOXML 原文，只做结构化、不改内容，连疑似笔误都原样保留。
2. **剔除 C 档**：上线版本里 docx 得不到的编辑加工一律不进结构参考；该字段用 docx 忠实值，docx 没有就不产出该元素。
3. **补 B 档**：按刊号查表补 journal-meta，`article-id` = DOI，补版权/开放获取模板与交叉引用关联；参考文献统一做结构化著录（`element-citation`），字段逐字来自 docx。
4. **图片型表格特例（02）**：02 的 8 张"表"在 Word 里是整张图片，结构参考采用上线版本对这些图片表的权威转写，并引用从 docx 内嵌媒体提取、外部化的图片文件。
5. **逐篇校验后冻结**：每篇都要过 DTD 合法、docx↔结构参考的词多重集守恒（反查无内容增删）、每个 `<graphic xlink:href>` 都指向存在且可解码的外部化图片文件（规则验证），方可冻结进版本库。

主样例 01–05 的结构参考由本队基于 docx 独立构建（拿上线版本当体例/抽全/B 档旁证，但内容以 docx 为准、剔除 C）；补充样例 S01–S05 没有上线版本可参照，方法相同。

## 输入和输出长什么样

**输入（docx）** 本质是一个装着 XML 的压缩包，正文是一串段落和表格，内联着文本、图片、公式（[02-领域基础](02-领域基础.md) 讲 docx/OOXML 的内部构造）。它有内容，但结构是隐含的：哪段是标题、哪段是图题，文件本身常常说不清。

**输出（JATS XML）** 则把结构显式标出来，分成三大块：`<front>`（题名、作者、单位、摘要、关键词、期刊与文章元数据）、`<body>`（分节正文，含图 `<fig>`、表 `<table-wrap>`、公式 `<disp-formula>`）、`<back>`（参考文献 `<ref-list>` 和各类声明）。同一篇文章，输入是"有内容、结构隐含"，输出是"内容不变、结构显式"——转换器做的就是这中间那一步。JATS 各元素的含义见 [02-领域基础](02-领域基础.md)，转换器如何一步步生成见 [04-系统设计](04-系统设计.md) 与 [05-模块实现](05-模块实现.md)。
