# 04 · 系统设计

这篇讲整个方案的骨架和最关键的取舍：为什么不走"纯规则模板"或"纯大模型改写"这两条常见路线，我们选的第三条路是什么，以及它靠什么保证不改坏原文。读完你会明白这个项目区别于常规做法的核心在哪。

## 先看清问题的本质

任务是把一篇 Word 投稿稿转成 JATS XML，且是**结构化技术**——只把隐含的结构显式标出来，**不改动内容**（[01-竞赛与任务](01-竞赛与任务.md)）。这里有两个对立的难点，同时成立：

1. **结构要靠"看内容"才能判**。docx 里一段文字到底是标题、正文、图题还是参考文献，Word 文件本身往往说不清。理论上段落有"样式名"可依据，但真实投稿里样式名经常缺失或标错（作者随手排版），所以判断某段扮演什么角色，很多时候只能读懂它的内容才知道。这正是大模型擅长、死规则枚举不完的事。

2. **内容一个字都不能改**。作者的拼写、时态、大小写、甚至疑似笔误，都要原样保留（[03-数据与结构参考](03-数据与结构参考.md) 讲了为什么）；斜体、上标、下标这些内联格式也要一并留住。这恰恰是大模型不擅长、反而会"顺手改写"的地方。

一个方案要同时满足这两条——**结构判断要聪明，内容搬运要死板**——是这个问题的核心张力。下面两条常见路线各只顾一头，所以都不够。

## 为什么不选纯规则模板

最直接的想法是写规则：按样式名和排版特征识别标题、作者、参考文献，再套模板生成 XML。主办方提供的基线代码（`baseline-develop/`，Java 实现，用 Apache Tika 抽取文本、FreeMarker 套模板）大体是这条路。

它的问题是**结构判断这一头太脆**：

- 真实 docx 的样式名不可靠，一旦缺失或标错，基于样式的规则就失灵。
- "这段是不是标题""这条参考文献的作者到哪儿结束"这类判断，本质要理解内容，死规则只能枚举有限模式，长尾永远覆盖不全。
- 于是要么漏判、错判，要么规则越堆越多、越堆越难维护，仍挡不住没见过的排版。

内容搬运这一头它其实没问题（模板只搬不改），坏就坏在结构判断撑不住。

## 为什么不选纯大模型改写

另一个极端：把 docx 的文字整段喂给大模型，直接让它输出 JATS XML。结构判断这一头它很强，但**内容搬运这一头会失守**：

- 大模型是"生成"模型，让它输出全文，它会顺手改写——调整措辞、丢掉斜体上标、补充或删改字句，甚至凭空编造。这直接违反"不改内容"。
- 输出不确定：同一篇文章两次转换可能不一样，无法复现、无法核对。
- 最危险的是**看图造字**：论文里常有整张表格其实是一张图片、公式是 MathType 截图。若把图片喂给多模态模型让它"读出"内容，模型会把看不清的地方编出来。本项目早期确实试过让模型看图重建表格，实测在一个样例上编造出 600 多个原文根本没有的词——这条路已被彻底废弃。

结构判断这一头它很好，坏就坏在内容会被它改写、编造。

## 我们的选择：把"判断结构"和"搬运内容"彻底分开

既然一条路强在结构、弱在内容，另一条反过来，那就**让每一头交给擅长它的机制**：

> **大模型只做"判断结构"，从不产出正文文字；所有正文文字按源块编号从 docx 原文原样取回。**

具体拆成三层职责：

- **大模型负责理解**：读文档，判断每一段扮演什么角色（标题/作者行/正文/图题/参考文献…）、层级关系、以及参考文献里各字段的边界。它的产出全部是"**第 N 个源块是什么**"这样的**结构判定**，用源块的编号（索引）来指代内容，而不是把内容抄出来。
- **原文按索引取回**：解析层把 docx 拆成有序的"源块"（每个段落/表格一块），逐块编号。渲染时，凡是正文类内容，都按大模型给的编号回到解析层，取回那一块的**原始 runs**（带斜体/上标/加粗的最小文本单元）原样输出。**文字自始至终没有经过大模型的输出**。
- **确定性规则负责落地**：把结构判定机械地变成合法 XML——数学公式 OMML→MathML 转换、图片外部化、JATS 元素拼装、正文里"Fig. 3""[5]"这类交叉引用的解析、DTD 合法性校验。这些都是确定的、可复现的机械变换，不含任何内容判断。

### 关键不变量：内容守恒是"结构性成立"

"内容守恒"指转换后的正文文字与 docx 原文严格一致、不增不减不改。本方案的守恒不是靠"转换完再比对补救"，而是**结构性成立**：正文文字压根不流经大模型，而是按编号从原文取回，所以想改都改不了。斜体、上标、下标随原始 runs 一起取回，零损失。

只有一种情况必须把一个源块切成多个语义单元——比如"张三¹, 李四², 王五\*"这样一行要拆成逐位作者，一条参考文献要拆成作者/标题/刊名/年卷期页各字段，通讯作者段要拆出姓名/地址/邮箱，结构化摘要一段里要分出小标题和正文。**这时大模型给的是"子串"**（它说"这一段的第 3 到第 12 个字是标题"），出口校验再确认这些子串确实是 docx 原文的逐字子串；对不齐就退回更保守的表示（例如整条参考文献落回自由文本著录 mixed-citation，见 [02-领域基础](02-领域基础.md)），宁可结构粗一点，也不放任编造。

### 从物理上杜绝看图造字

图片、公式、以及"整张表其实是图片"的情形，喂给大模型的**只是占位符**——形如 `⟦IMG#1⟧`、`⟦MATH#2⟧` 的记号，**不含任何图像字节**。大模型看不到图像，也就无从"读图"，看图造字在架构层面就不可能发生。图片和公式的真实内容由确定性规则处理：图片按竞赛要求外部化成独立文件、XML 里用 `<graphic>` 引用；公式用微软官方的 OMML→MathML XSLT 转成标准 MathML。

### 确定性：同一篇文章逐字节复现

大模型调用把温度参数设为 0（模型尽量取最确定的输出），并对每次请求做磁盘缓存。这样同一输入的转换结果逐字节可复现，与并发顺序无关——这对一个要被反复评测、核对的工程很重要。也正因为各任务相互独立且结果确定，10 个样例、以及每篇内部的多个理解任务都**全量并发**执行（云端模型支持高并发，串行是纯浪费）。

## 数据怎么一步步流过

```
 docx
  │  parse        用 python-docx 开包、lxml 保序遍历正文
  ▼                段落/表格/内联 run（文本·公式·图片·换行），纯物理结构、不做语义判断
 IR（中间表示）
  │  serialize    每个源块序列化成带稳定编号 [idx] 的一行；上下标编码成 ^{}/_{}，
  ▼                图片公式只留占位符 ⟦IMG#n⟧/⟦MATH#n⟧
 内容流（喂给大模型看的文档表示）
  │  understand   三个大模型 pass：front（标题/作者/单位/摘要/日期…）、body（正文分节层级）、
  ▼                refs（参考文献切分）。产出全是"第 N 块是什么"的结构判定
 结构判定（JSON，全用 idx 指代内容）
  │  assemble     按 idx 把原始 runs 取回，组装成类型化的 SemanticDoc；
  ▼                需切分处校验子串为 docx 原文，对不齐则回退
 SemanticDoc（语义模型，理解层与渲染层之间的契约）
  │  render       机械构造 front/body/back，解析交叉引用，兜底修复悬空引用/空表行
  ▼
 JATS XML
  │  verify       出口自检：词多重集守恒（比 docx 没多没少）+ DTD 合法 + 结构自洽
  ▼
 校验报告
```

一个要点：**渲染层和出口校验只消费 SemanticDoc，不再回看 docx**。理解层一旦把结构判定完、把原文取回封进 SemanticDoc，下游职责就单一了。SemanticDoc 这个"类型化契约"是理解层（聪明但不确定）和渲染层（死板但可靠）之间的清晰分界。

## 出错兜底为什么不靠"再问一次大模型"

一个自然的想法是：出口校验发现问题，就把问题回给大模型让它修。本方案**有意不这么做**，而是把兜底放在**确定性的上游守卫**上：

- 组装层：参考字段必须是原文子串/词高度重叠，否则置空、必要时整条退回 mixed-citation；无标签的参考按位置补编号；结构化摘要在块内切分防重复。
- 渲染层：交叉引用只在目标确实存在时才生成，引用 id 强制唯一，从源头杜绝悬空和重复。
- 渲染末：机械修掉残留的悬空引用、空表行。

理由是：本架构下正文按源块索引取回原文、内容守恒结构性成立，**出口几乎没有可编造的内容需要修**；而回问大模型既慢又引入不确定性，得不偿失。所以出口校验主要是**自检与报告**（守住 DTD 合法、守恒无破例），而不是一个"发现-重问-再生成"的循环。这是"确定、即时、无抖动"和"灵活、但慢且不稳"之间的取舍，本项目选前者。

## 这套设计好在哪

- **内容零损失、零编造**，且不是靠运气或事后补救，而是结构上就做不到改写——这是最硬的保证。
- **结构判断有大模型的理解力**，不依赖脆弱的样式名，换没见过的排版也能处理（补充样例 S01–S05 是完全没给过"正确答案"的泛化测试，见 [06-评测与成绩](06-评测与成绩.md)）。
- **可复现、可核对、可并发**，工程上扎实。
- **职责单一、分层清晰**：解析只搬物理结构、理解只判语义、渲染只做机械变换、校验只做自检，每层都好懂好维护（逐模块见 [05-模块实现](05-模块实现.md)）。
