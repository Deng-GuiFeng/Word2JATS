# 05 · 模块实现

这篇是代码地图：不读源码，也能知道"某件事在哪个包做的"，据此维护和扩展。上一篇 [04-系统设计](04-系统设计.md) 讲了整体思路和取舍，这篇落到代码的组织。

## 分层总览

代码在 [`src/word2jats/`](../src/word2jats/) 下，按转换的自然顺序分层，每层职责单一：

```
parse/      docx → 中间表示（IR）           只搬物理结构，不判语义
understand/ IR → 结构判定 → SemanticDoc      唯一"判语义"的地方（调大模型）
semantic/   SemanticDoc 定义                 理解层与渲染层之间的类型化契约
render/     SemanticDoc → JATS 树            机械构造，不判内容
build/      渲染用的底层构件                 图片外部化 / 公式转换 / 元素工厂 / 交叉引用
verify/     出口自检                         内容守恒 + DTD + 结构自洽
validate/   DTD 校验 + 检查 + 兜底修复
llm/        大模型客户端 + 磁盘缓存
enrich/     期刊元数据查表
model/      IR 数据类型定义
resources/  JATS DTD、OMML2MML.XSL、journals.yaml
```

顶层编排在 [`pipeline.py`](../src/word2jats/pipeline.py) 的 `convert()`，命令行入口是 [`cli.py`](../src/word2jats/cli.py)。**理解层（understand）与渲染层（render）通过 `semantic/model.py` 里的 `SemanticDoc` 这个契约解耦**——这是理解整个代码组织的关键接缝：上游负责"判断结构、把原文封进 SemanticDoc"，下游只消费 SemanticDoc、不再回看 docx。

> **给维护者的一句话**：要改"判断什么"，动 `understand/prompts.py` 和 `understand/assemble.py`；要改"怎么变成 XML"，动 `render/` 和 `build/`；两者靠 `SemanticDoc` 隔开，互不牵连。

## 逐包详解

### parse —— docx 解析成中间表示

把 Word 文件读成一棵与 JATS 无关的中间表示（IR，Intermediate Representation）。

- `docx_reader.py`：用 python-docx 开包，再用 lxml 直接按顺序遍历正文（python-docx 不暴露公式，必须用 lxml 才能保住顺序和公式）。解析样式表、嗅探图片格式（PIL 识别，WMF/EMF 按文件头兜底）、读原生表格的合并/表头信息。
- `runs.py`：把一个段落拆成有序的"run"（最小内联单元），处理文本、超链接、公式、图片；MathType 之类的公式截图位图标记为"回退位图"，后续忽略。
- `ooxml.py`：命名空间和取值的底层工具函数。
- 产出 `Document`：一串有序的段落和表格。**这一层不做任何语义判断**，只忠实搬运物理结构。

### model —— 中间表示的数据类型

`blocks.py` 定义 IR 的数据类：段内联的 `TextRun`（带粗体/斜体/上下标/超链接）、`MathRun`（保存原始公式元素，留待后续转换）、`ImageRun`（图片字节+格式）、`BreakRun`（换行）；块级的 `Paragraph`、`Table`、`TableCell`、`TableRow`（带表头标记）；容器 `Document`。这些结构贴近 docx 的物理形态，不含语义。

### understand —— 理解层（唯一判语义的地方）

这是大模型工作的地方，也是内容守恒机制的核心所在。

- `serialize.py`：把 IR 序列化成"给大模型看的文档表示"`ContentStream`——每个源块一行，带稳定编号 `[idx]`；上标下标编码成 `^{}`/`_{}`，图片公式换成占位符 `⟦IMG#n⟧`/`⟦MATH#n⟧`（**不含图像字节**）。大模型看到的就是这份编号文本。
- `segment.py`：机械定位参考文献区的边界（找 "References" 标题或首条 `[1]`），把文档粗分成前置+正文区和参考区。纯记号切分，不判语义。
- `prompts.py`：三个理解任务的提示词。每个提示词都写死一段"铁律"：输出必须是输入的逐字子串、绝不读占位符里的图、只返回一个 JSON。
- `passes.py`：真正调用大模型跑三个任务，并处理参考文献的分块并发与"切不齐就二分重试"。
- `assemble.py`：理解层最重的模块（约 700 行）。把三份结构判定 JSON 组装成 `SemanticDoc`——按编号取回原始 runs，切分处消费大模型给的子串并做守恒检查（见下一节）。
- `understand.py`：编排入口，负责三个任务的并发调度。

**三个理解任务各判什么**：

| 任务 | 判定内容 |
|---|---|
| front | 文章类型、题名、作者（姓名/单位角标/通讯/共同贡献/ORCID/邮箱）、单位、通讯段、日期、编辑、摘要（含结构化子节）、关键词、前置声明，以及正文从第几块开始 |
| body | 正文分节（每节标题在第几块、第几层级）、尾部声明、图/表/公式的锚点位置 |
| refs | 每条参考文献切成作者/标题/刊名/年卷期页等字段；切不动的整条走自由文本著录 |

**并发**：参考任务与前置/正文任务相互独立，后台并发跑；前置→正文有依赖（正文起点取自前置判定），保持串行。参考文献按每 28 条一块、多块全量并发；某块因输出截断而条数不足时，二分成两半再并发重试到补齐。这套并发已硬编码，云端模型支持高并发，串行是纯浪费。

### semantic —— 理解层与渲染层的契约

`model.py` 定义 `SemanticDoc` 及其组成（作者、单位、摘要、章节、图、表、公式、参考文献、声明等）。关键在于：**正文类对象携带的是从 IR 取回的原始 runs**（如章节标题、图题、正文段），**切分类对象携带的是校验过的子串**（如参考文献各字段、单位文本）。字段的命名和取值口径对齐评测的对位层（[06-评测与成绩](06-评测与成绩.md)）。

### render —— 生成 JATS 树（纯机械）

消费 `SemanticDoc`，机械地构造 JATS 的 `<front>`/`<body>`/`<back>` 三部分，不做任何内容判断。

- `render.py`：总装，并触发交叉引用解析、兜底修复、序列化。
- `front.py`（最重）：期刊元数据（查表）+ 文章元数据（题名/作者/单位/通讯/日期/版权/摘要/关键词）。
- `body.py`：把章节树渲成 `<body>`，内嵌图/表/公式。
- `back.py`：声明小节 + 参考文献列表 + 固定的出版方声明。
- `references.py`：每条参考渲成结构化著录 `<element-citation>` 或自由文本 `<mixed-citation>`。
- `tables.py`：表格渲成 `<table-wrap>`（网格表或整表图片两种）。
- `context.py`：`RenderContext` 打包图片/公式的构造器与计数。

### build —— 渲染用的底层构件

不含内容判定的机械设施。

- `jats.py`：JATS 元素工厂、DOCTYPE 声明、把 runs 逐字输出成内联 XML、最终序列化。
- `figures.py`：图片外部化——按竞赛要求把图片抽成独立文件 `{文章号}/fig-0N.jpg`，**直写原始字节、不重新编码**，XML 里用 `<graphic>` 引用。
- `formulas.py`：用微软官方的 `OMML2MML.XSL` 把 Word 公式转成标准 MathML3，块级公式的成对括号折成 `<mfenced>`（与出版体例一致）。
- `xref.py`：把正文文本里的 "Fig. 3"、"Table 2"、"[5]"、"[8-15]" 用正则识别成交叉引用 `<xref>`（机械匹配，非内容判定）。

### verify —— 出口自检

- `conservation.py`：把 docx 原文和输出 XML 各取"词多重集"比对，报告"编造"（输出有、原文无，硬违规）和"可能漏失"。这是内容守恒的最后一道独立闸。
- `verify.py`：汇总 DTD 校验 + 内容守恒 + 结构自洽检查，给出报告。
- `repair.py`：渲染并校验一次（说明见下文"关于修复"）。

### validate —— DTD 校验与质量检查

- `validator.py`：用本地 JATS 1.3 DTD 做合法性校验。
- `checks.py`：结构自洽检查（悬空交叉引用、重复 id、空 body、缺题名/作者、空参考列表、空表行、图缺 graphic 等）。
- `repair.py`：机械兜底——拆掉悬空交叉引用的外壳但保留其中文字、删除空表行。

### llm / enrich —— 模型接入与元数据

- `llm/client.py`：`LLMClient`，与厂商无关的 OpenAI 兼容客户端，温度 0、要求返回 JSON、并发计数线程安全。`llm/cache.py`：按内容哈希的磁盘缓存，支持并发原子写，是"同输入逐字节复现"的基础。
- `enrich/journals.py`：从 `resources/journals.yaml` 按刊号查期刊元数据、从 DOI 推期刊代号和文章号（B 档补全）。

## 内容守恒落在代码里的三道闸

[04-系统设计](04-系统设计.md) 讲了内容守恒是"结构性成立"。它在代码里由三道闸把守：

1. **索引取回（主闸）**：序列化时每个源块记下编号、把 IR 块存进查找表；组装时正文类内容直接按编号返回原始 runs 对象。**正文文本全程不流经大模型**，这是守恒成立的根本。
2. **参考字段守恒（切分闸）**：`assemble.py` 的 `_sanitize_ref` 是最严格的显式守恒门——长字段（标题/刊名）与原文词集重叠不足就判编造置空；短字段（卷/期/页）必须是原文归一子串否则置空；作者姓氏必须在原文出现；对不齐时整条退回自由文本著录。作者/关键词标题/结构化摘要子节等切分处也各有子串校验。
3. **出口守恒（兜底闸）**：`verify/conservation.py` 独立地把输出与 docx 做词多重集比对，任何"编造"都会被报出来，是最后的独立核对（gold-free，任何新样例可跑）。它在 docx 侧**按段落拼合 run 再切词**，消除 Word 分 run 存词造成的切词假象（"Age"存成"A"+"ge"这类）；与评测忠实层的口径差异见 [06-评测与成绩](06-评测与成绩.md)。因它没有金标准仲裁、且 docx 里注入的期刊元数据与不可约的无分隔词天然会"多出"，其 `n_fab` 是**粗略自检指标**、非精确编造计数——"正文不改写"的硬保证来自主闸（正文按索引取回、不经大模型），不靠这个数。

## 关于"修复"

代码里 `verify/repair.py` 的函数名叫 `render_verify_repair`，但**它实际上只渲染一次、校验一次就返回，并没有"发现问题-重问大模型-再生成"的循环**。这是有意的设计（理由见 [04-系统设计](04-系统设计.md)"出错兜底为什么不靠再问一次大模型"）：真正的纠错由确定性上游守卫承担，出口校验主要是自检与报告。参数 `max_rounds`/`repair_rounds` 是这个演进过程留下的未使用参数。

## 已知遗留（待后续清理）

如实记录几处"能跑但冗余"的历史遗留，供后续维护（不影响当前功能与成绩）：

- `ConvertOptions` 里 `crossref`/`refine`/`agent`/`agent_rounds`/`agent_dpi`/`agent_phases`/`repair_rounds` 等字段，是早期"确定性档 + 视觉修复闭环"架构的残留，`convert()` 已不再读取；评测驱动 `scripts/eval/run.py` 仍按旧签名传入、被静默忽略。
- 几个定义但已无调用者的函数（如客户端的视觉问答、未接入的 JATS4R 检查、旧的前置窗口切分）。
- `AbstractSection.lead` 字段目前不会被设置，对应的渲染分支不触发。

这些属于旧架构（基于规则的分类层、基于视觉的修复闭环）退场后的尾巴，清理时需连带调整评测驱动的调用签名并重新验证，宜作为独立一次维护来做，不与功能改动混在一起。
