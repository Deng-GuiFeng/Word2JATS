# 05 · 模块实现

这篇是一张代码地图。读完你会知道：这个转换器的代码分成哪几层、每一层放在哪个包、一份 Word 稿是怎么一步步流过这些包变成 JATS XML 的，以及"正文不被改动"这条硬要求具体落在代码的哪几个地方。上一篇 [04-系统设计](04-系统设计.md) 讲的是方法和取舍——为什么让大模型只判结构、正文按编号取回、渲染走确定性规则；这一篇把那套思路落到文件和函数上，好让人不读源码也能维护和扩展它。

约定：下文出现的 JATS、docx/OOXML、OMML、element-citation 等术语都在 [02-领域基础](02-领域基础.md) 里从零讲过；"内容守恒"（转换后正文与源文件逐字一致、不增不减不改）见 [04-系统设计](04-系统设计.md)——本篇只在首次出现时用一句话带过。

## 分层总览

转换器的代码在 [`src/word2jats/`](../src/word2jats/) 下，按"一份稿子被处理的自然顺序"分层，每层职责单一、互不越界：

| 包 | 职责一句话 |
|---|---|
| `parse/` | 把 Word 文件（docx）读成一棵与 JATS 无关的中间表示，只搬物理结构，不判语义 |
| `model/` | 定义那棵中间表示的数据类型（段落、表格、文字片段、公式、图片…） |
| `understand/` | 全项目**唯一判语义的地方**：把中间表示交给大模型判结构，再按编号把原文取回 |
| `semantic/` | 定义 `SemanticDoc`——理解层与渲染层之间的类型化契约 |
| `render/` | 把 `SemanticDoc` 机械地拼成 JATS 的三大块 `<front>`/`<body>`/`<back>` |
| `build/` | 渲染要用的底层构件：图片外部化、公式转换、XML 元素工厂、交叉引用识别 |
| `verify/` | 出口自检：内容守恒比对 + DTD 校验 + 结构自洽检查 |
| `validate/` | DTD 校验器、质量检查、以及渲染末尾的确定性机械修复 |
| `llm/` | 与厂商无关的大模型客户端 + 磁盘缓存 |
| `enrich/` | 期刊元数据查表（按刊号/DOI 补 journal-meta） |
| `resources/` | 静态资源：JATS 1.3 的 DTD、微软的 `OMML2MML.XSL`、`journals.yaml` |

"中间表示"（IR，Intermediate Representation）是个贯穿全篇的说法，指一份介于 Word 和 JATS 之间、谁都不偏向的数据结构：它照抄 docx 的物理形态（哪段在前、哪个字加粗），但不携带任何"这段是标题、那句是图注"的判断。判断留给后面的理解层。

顶层编排在 [`pipeline.py`](../src/word2jats/pipeline.py) 的 `convert()` 函数，它按 parse → understand → render → verify 的顺序把各子包串起来。命令行入口是 [`cli.py`](../src/word2jats/cli.py)，只有一个 `convert` 子命令、六个参数（docx 路径、`-o` 输出目录、`--journal`、`--doi`、`--no-validate`、`--llm` 后端）。温度、随机种子、模型名这些只在做评测和消融实验时才需要覆盖，因此不进命令行，仅在程序内部传参可达（见 [07-消融与方法验证](07-消融与方法验证.md)）。

**理解整套代码组织，抓住一条接缝就够了：理解层（understand）和渲染层（render）之间，靠 `semantic/model.py` 里的 `SemanticDoc` 解耦。** 上游负责"看懂结构、把原文封进 `SemanticDoc`"，下游只消费 `SemanticDoc`、不再回头看 docx。要改"判断什么"，动 `understand/`；要改"怎么变成 XML"，动 `render/` 和 `build/`；两边被这个契约隔开，互不牵连。

## 逐包详解

### parse —— 把 docx 读成中间表示

docx 本质是个换了后缀的 zip 包，正文几乎都在 `word/document.xml` 里，文字被拆成"段落 `<w:p>` → 片段 `<w:r>` → 文本 `<w:t>`"三层。这一层的活就是把它无损地读成 IR。

- `docx_reader.py`：主解析器。用 python-docx 打开 zip 包，再用 lxml 直接按顺序遍历正文。这里有个关键选择——不用 python-docx 的高层接口，因为那个接口既不暴露公式，又会打乱段落和表格的原始先后次序；只有直接遍历才能同时拿到顺序和对公式、图片的精确控制。它还负责建样式名映射、嗅探图片格式、读原生表格的合并与表头信息。
- `runs.py`：把一个段落拆成有序的一串"run"（run 指一段格式相同的连续内容，是 Word 里最小的内联单元）。它逐个处理文本、制表符、换行、超链接、公式、图片，逐 run 读出加粗/斜体/上下标——这几个格式是原样带进 IR 的，零损失。图片解析要判真伪：MathType 之类公式以矢量截图（wmf/emf）形式嵌进来的，标记为"回退位图"、后续忽略；真正的插图（jpeg/png/tiff…）才留下。判据按图片格式而非嵌入容器——因为现代 Word 常把真图裹在兼容包装里，只看容器会漏掉真图。
- `ooxml.py`：命名空间常量和底层 XML 取值工具。比如 OOXML 里"元素在即为真、除非显式写 false"的布尔约定，就由这里的 `is_on()` 实现。

产物是一个 `Document`：一串有序的段落和表格。**这一层绝不做语义判断**，只忠实搬运物理结构。公式在这里也只是把原始的 `<m:oMath>` 元素原样存下，不转换——转换是后面 `build/` 的事，免得把 XSLT 依赖耦合进 IR。

### model —— 中间表示的数据类型

`blocks.py` 定义 IR 用到的全部数据类：内联的 `TextRun`（带粗体/斜体/上下标/超链接）、`MathRun`（保存原始 OMML 公式元素）、`ImageRun`（图片字节 + 格式）、`BreakRun`（换行）；块级的 `Paragraph`、`Table`、`TableCell`、`TableRow`（带跨页表头标记）；以及容器 `Document`。这些类贴着 docx 的物理形态，不含一丝语义。

### understand —— 理解层（唯一判语义的地方）

这是大模型干活的地方，也是内容守恒机制的核心。它把 IR 交给大模型判结构，但**文字始终从源块原样取回、绝不让大模型重新生成**——这正是 [04-系统设计](04-系统设计.md) 里"内容守恒构造性成立"的落点。

- `serialize.py`：把 IR 序列化成一份"给大模型看的文档表示"。每个源块占一行，行首带稳定编号 `[idx]`（idx 就是这个块在文档里的顺序号）；上标下标编码成 `^{}`/`_{}`，图片和公式换成占位符 `⟦IMG#n⟧`/`⟦MATH#n⟧`——**只给占位符、不给任何图像字节**。大模型看到的自始至终是这份编号文本，它没有任何像素可"看图 OCR 造字"。它还会给行打上排版标记（加粗/居中/列表/样式名），当作判标题、判层级的信号。
- `segment.py`：机械定位参考文献区的边界——从后往前找 "References/参考文献" 这类整行标题，找不到就在文档后段找首条 `[1]`。这是纯记号切分、零漂移，把文档粗分成"前置+正文区"和"参考区"，好让三个任务各看一段、缩小上下文、还能并发。这属于表示层切分，"这段扮演什么角色"仍全交大模型。
- `prompts.py`：三个理解任务的提示词。每个提示词开头都写死同一段铁律，核心是"内容守恒"：你输出的每个文本串必须是输入文本的逐字子串，绝不改写、翻译、扩写、概括、纠错、编造；占位符只能按编号引用，绝不读、绝不猜。
- `passes.py`：真正调用大模型跑三个任务。参考文献按每 28 条一块、多块全量并发；某块因输出被截断而条数不足时，二分成两半再并发重试到补齐——这是为 02、04 那种超长参考列表兜底的救命机制，消融显示真正离不开它的是 02（关掉后它的缺陷从 11 暴涨到 1051，见 [07-消融与方法验证](07-消融与方法验证.md)）。书籍类文献特有的编者、出版社字段，还另起一次针对性调用单独抽取，免得混进主提示词把期刊文献的抽取带偏。
- `assemble.py`：理解层最重的模块（约 700 行）。把三份结构判定 JSON 组装成 `SemanticDoc`——正文类内容按编号 O(1) 取回原始 runs，只有"必须把一个源块切成多个语义单元"的地方（作者行拆成逐个作者、参考条拆成各字段、结构化摘要按子标题切）才消费大模型给的子串，并在出口做守恒校验（见后文"三道闸"）。
- `understand.py`：编排入口，负责并发调度。

三个任务各判什么：

| 任务 | 判定内容 |
|---|---|
| **front** | 文章类型、题名、作者（姓名、单位角标、通讯、共同贡献、ORCID、邮箱）、单位、通讯段、日期、编辑、摘要（含结构化子节）、关键词、前置声明，以及正文从第几块开始 |
| **body** | 正文分节（每节标题在第几块、第几层级）、尾部声明、图/表/公式的锚点位置。普通段落不逐一枚举——由标题区间推断。表分三型：原生网格表、用制表符拼排的文本表、整张就是一张图片的表 |
| **refs** | 每条参考文献切成作者/标题/刊名/年卷期页等字段；切不动的整条走自由文本著录（mixed-citation） |

并发拓扑是三层全量并发（云端模型支持高并发，串行是纯浪费）：顶层让参考任务与"前置→正文"并发（前置和正文有依赖，正文起点取自前置判定，故这两个串行）；参考各块之间并发；截断二分的两半也并发。

### semantic —— 理解层与渲染层的契约

`model.py` 定义 `SemanticDoc` 及其组成（作者、单位、摘要、章节、图、表、公式、参考文献、声明等）。这个契约的要害在于两类字段的区分：**正文类对象携带的是从 IR 取回的原始 runs**（章节标题、图题、正文段——斜体、上下标、加粗零损失地带过来），**切分类对象携带的是校验过的子串**（参考各字段、单位文本）。渲染层只认这个结构，从此不再碰 docx。

### render —— 生成 JATS 树（纯机械）

消费 `SemanticDoc`，机械地拼出 JATS 的三大块，全程不判内容——出错只可能是组装 bug，不涉及语义。

- `render.py`：总装入口。依次拼 `<front>`/`<body>`/`<back>`，然后跑交叉引用解析、做确定性兜底修复、序列化成字节。全程用 lxml 构建 DOM 树而非拼字符串，保证 XML 良构可校验（主办方的 Java 基线走的是字符串拼接那条路）。
- `front.py`（最重）：期刊元数据（查表得来）+ 文章元数据（题名、作者、单位、通讯段、日期、版权、摘要、关键词）。这里有个值得一提的判断：共同贡献（几位作者并列第一）必须有显式声明块才生成对应标记，只凭作者名旁的角标（†/#）不算——因为 10 例里没有一例用 `@equal-contrib` 属性，而大模型常把孤立角标误标，强行认定会连带造出多余的脚注和引用。
- `body.py`：把章节树渲成 `<body>`，内嵌图、表、公式；空节点（只有标题没内容也没子节）静默丢弃。
- `back.py`：声明类小节（致谢、缩略语表等按标题关键词分派容器）+ 参考文献列表 + IMR Press 固定的出版方声明。
- `references.py`：每条参考渲成结构化著录 `<element-citation>`（字段齐全时）或自由文本著录 `<mixed-citation>`（切不动时兜底）。ref 的 id 取自参考文献的显示编号而非顺序序号，以正确处理跳号。
- `tables.py`：表格渲成 `<table-wrap>`——网格表出 `<table>`，整张是图片的表出 `<graphic>`（只引用、不读图造字，02 那 8 张"表"其实全是图片，见 [03-数据与结构参考](03-数据与结构参考.md)）。
- `context.py`：`RenderContext`，把公式、图片的构造器和各类编号计数打包共享。

### build —— 渲染用的底层构件

不含内容判定的机械设施。

- `jats.py`：JATS 元素工厂、命名空间与 DOCTYPE 声明、把 runs 逐字输出成内联 XML、最终序列化。它在输出前会先合并相邻的同格式 run——既消掉 Word 的碎片化（把 "Fig."+" 1" 拼成能被识别的 "Fig. 1"），也让内联格式干净。
- `figures.py`：图片外部化。把 docx 内嵌媒体按正文出现顺序抽成独立文件 `{文章号}/fig-0N.<原格式扩展名>`——扩展名随原图真实格式（jpeg→.jpg、png→.png、tiff→.tif），**直写原始字节、不重新编码、不做任何格式转换**，XML 里用 `<graphic>` 引用。
- `formulas.py`：用微软官方的 `OMML2MML.XSL` 把 Word 公式转成标准 MathML3。转完还得把元素名统一加上 `mml:` 前缀——因为 JATS 的 DTD 校验只按字面前缀匹配、不认命名空间，不加前缀会校验失败。块级公式的成对括号折成 `<mfenced>`（照出版体例的写法）。XSLT 万一加载失败，就降级返回空、公式被跳过，不崩管线。
- `xref.py`：把正文里的 "Fig. 3"、"Table 2"、"[5]"、"[8–15]" 用正则识别成交叉引用 `<xref>`。这是机械匹配、不理解语义：区间只在跨度不大时才展开（避免把页码误当图表区间）；目标不存在时退回纯文本（避免产生指向空处的悬空引用）；"Fig. 2A" 这种带分区字母的、以及补充材料引用，一律保留纯文本不拆。

期刊元数据（journal-meta，如刊名、缩写、ISSN）在 docx 里通常根本不存在，属于允许由出版系统补全的部分，因此走 `enrich/journals.py` 从 `resources/journals.yaml` 查表注入，而非从正文抽取。

### verify —— 出口自检

- `conservation.py`：内容守恒的独立核对。把 docx 原文和输出 XML 各切成"词多重集"（把文本拆成"词→出现次数"再做集合差）比对，报出"编造"（输出有、原文全篇都没有的词，硬违规）和"可能漏失"（原文有、输出无）。关键在于它在 docx 一侧**按段落拼合 run 再切词**，消掉 Word 分 run 存词造成的假象（比如 "Age" 被存成 "A"+"ge"、"Keywords" 被存成 "Key"+"w"+"ords"）——同一段的多个 run 必属同批文字，段内拼合直接把这类切词噪声抹平。
- `verify.py`：出口校验入口，汇总 DTD 校验 + 内容守恒 + 结构自洽检查，给出报告。
- `repair.py`：`render_verify_repair()`——名字里带 repair，但它只渲染一次、校验一次就返回，没有"发现问题-重问大模型-再生成"的循环（原因见后文边界一节）。

### validate —— DTD 校验、质量检查、机械修复

- `validator.py`：用包内自带的 JATS 1.3 DTD 做合法性校验。这里有个并发上的讲究：老写法每次校验都切进程工作目录去加载 DTD，而切目录是进程级全局操作，网页应用并发跑转换时会互相踩、假报"table 未声明"。现在改成用绝对路径直接加载 + 进程级锁 + 缓存，DTD 只加载一次，线程安全。
- `checks.py`：结构自洽检查——悬空交叉引用、重复 id、空 body、缺题名或作者、参考文献整类丢失、空表行、图缺 graphic 等，每条带严重级别。这里有一处专门修过的判断：**判一个 `<table-wrap>` 是不是空，必须 `table`、`graphic`、`media` 三者皆无才算空**——因为图片型的表（源稿直接给一张图当表，JATS 合法、02 就是这样）只有 `graphic` 没有 `table`，只认网格表会把它误报成空表。
- `repair.py`：渲染末尾的确定性机械兜底——拆掉悬空交叉引用的外壳但保留其中文字、删掉空表行（删之前先把尾随文本并到相邻节点防丢字）。纯结构修复，不改语义，是"最后一道防线"。

### llm / enrich —— 模型接入与元数据

- `llm/client.py`：`LLMClient`，与厂商无关的 OpenAI 兼容客户端（DeepSeek、阿里云百炼、本地部署都走同一套接口）。温度默认 0、强制返回 JSON、并发计数线程安全。`llm/cache.py`：按调用内容的哈希做磁盘缓存、支持并发原子写——这是"同一份输入逐字节复现"的真正基础。这里有个反直觉但重要的事实：温度 0 在云端**并非**位级确定（实测同输入会给出不同结果），复现靠的是这层缓存把首次响应冻在磁盘上，而不是靠温度（详见 [07-消融与方法验证](07-消融与方法验证.md)）。
- `enrich/journals.py`：从 `journals.yaml` 按刊号查期刊元数据、从 DOI 前缀推期刊代号和文章号。

## 评测与网页应用两个包

除了转换器本身，仓库里还有两个独立的包，各服务于不同目的。

### scripts/eval —— 三层评测器

这个包是给转换质量打分用的自建评测系统，成绩和口径详见 [06-评测与成绩](06-评测与成绩.md)。它的立身之本是：**100% 确定、完全不含大模型、不出一个加权总分**，只对每个样例产出一份"离忠实结构化还差多少"的逐条缺陷清单。打分函数逐字不改就得同一结果，因此结论可复现、可审计。

- `run.py`：一键入口。对每个样例先跑转换器出 XML，再依次跑 L0/L1/L2 三层打分、聚合报告；10 个样例全量并发。
- `samples.py`：唯一的样例登记表，记 10 例（主组 01–05、补充组 S01–05）各自的 docx、结构参考 XML、scope 等路径。
- `validity.py`（L0 合法层）：DTD 校验 + DOCTYPE 逐字核对 + 一批出版规范规则（id 全局唯一、交叉引用必须闭合、公式须机读、ORCID 须完整 URL 等）。只有 error 级违规才计入缺陷。
- `fidelity.py`（L1 忠实层）：词多重集守恒，以冻结的结构参考仲裁"真丢失/真编造"；图片走规则验证（文件存在 + 能解码成真图 + 图数与结构参考吻合）。
- `structure.py`（L2 对位层）：对结构参考按语义键对齐（不按位置），逐类（作者/单位/摘要/章节/图/表/公式/参考/交叉引用…）算命中、漏标、多标。
- `normalize.py`：归一化，只吸收表示层等价（大小写、上下标 Unicode、破折号引号、空白、章节编号前缀），绝不吸收结构差异。
- `report.py`：聚合成机器可读的 `eval.json` 和人类可读的报告，顶层不出总分，只列逐样例缺陷数和跨样例的系统性根因。
- `ablation.py`：消融实验的基础设施。用 monkeypatch 在评测边界注入，跑"换模型/换温度"（部署维度）和"逐个拆可分离模块"（模块有效性）两类消融，复用 `run.py` 的三层打分，转换器源码逐字节不动。结论详见 [07-消融与方法验证](07-消融与方法验证.md)。

注意：评测层的 `fidelity.py`（在结构参考仲裁下用逐词口径判真丢失/真编造）与转换器出口的 `verify/conservation.py`（无仲裁、按段拼合的自检口径）是两套东西、目的不同，别混为一谈。

### webapp —— 校样工作台

这是给期刊编辑用的网页应用，编辑给一份 Word 就能拿到 JATS 并在网页上核对，为什么这么设计、结果页怎么组织，详见 [08-Web应用](08-Web应用.md)。它是个 FastAPI 单进程服务，前端是不带框架、不需构建的原生 JS。

- `app.py`：服务主体——全部 HTTP 端点、进程内任务表、线程池调度。转换是一次阻塞十几到几十秒的云端大模型调用，因此不在请求线程里做，而是丢进线程池后台跑，前端每秒轮询取结果。API key 由服务端持有，前端从不接触；同一份文件重传命中磁盘缓存即秒回。
- `render.py`：服务端预览渲染。用 NCBI 公有领域的 JATS 预览样式表（一份 4000 多行的 XSLT）把 JATS 变成期刊样式的 HTML。放服务端渲染是因为浏览器原生的 XSLT 能力正被各厂商移除、靠不住。它在渲染前后还做几件浏览器端难做的事，其中一件值得点明：**参考文献的分隔标点（温哥华式的"刊名. 年;卷(期):页"）只在这层预览时注入**——交付的 XML 本身逐字不带这些字面标点（这符合 JATS 规范，也与结构参考一致，标点本是渲染系统的职责）。
- `fidelity.py`：网页版的忠实自检。它复用转换器 `verify/conservation.py` 的按段拼合口径取 docx 词，算出正文的保留率并把逐词差异摆出来给编辑核对——用的是绕开 Word 分 run 假象的诚实口径。
- `static/`：前端页面。上传、轮询、五分区结果页（成品预览/原文核对/内容清单/合规检查/XML 源文件）都在这里。

## 内容守恒落在代码里的三道闸

[04-系统设计](04-系统设计.md) 说内容守恒是"构造性成立"的。它在代码里具体由三道闸把守：

1. **索引取回（主闸）**：序列化时给每个源块记下编号、把 IR 块存进查找表；组装时正文类内容直接按编号返回原始 runs 对象。**正文文本全程不流经大模型**——这是守恒成立的根本，不是靠概率约束，而是文字压根没经过会改写它的那一环。
2. **参考字段切分（切分闸）**：`assemble.py` 的出口校验是最严格的显式守恒门。参考的长字段（标题、刊名）与原文词集重叠不足就判编造、置空；短字段（卷、期、页）必须是原文的归一子串否则置空；作者姓氏必须在原文出现；对不齐时整条退回自由文本著录。作者、关键词标题、结构化摘要子节等其它切分处也各有子串校验。
3. **出口守恒（兜底闸）**：`verify/conservation.py` 独立地把输出与 docx 做词多重集比对，任何"编造"都被报出来。它不依赖任何标准答案（gold-free），任何新样例都能跑。因为它没有仲裁、且 docx 里按规范注入的刊名/ISSN/版权样板词、以及原文里无空格无标点的不可约词边界天然会"多出"，它报的编造数只是**粗略自检信号**、不是精确编造计数——"正文不改写"的硬保证来自主闸（正文按编号取回、不经大模型），而不靠这个数字为零。

## 当前实现的边界

如实记几处现状，都不影响功能与成绩，但维护时该知道：

`verify/repair.py` 的函数虽叫 `render_verify_repair`、签名里还带着 `max_rounds` 一类参数，但它**只渲染一次、校验一次**就返回，没有任何修复循环——纠错早已前移为前面那些确定性上游守卫，这几个参数是架构演进留下的空壳。同样，`ConvertOptions` 里还有若干字段（`crossref`/`refine`/`agent` 之类）是为兼容旧评测调用签名保留的，`convert()` 已不再读取。`validate/checks.py` 里另有一组 JATS4R 出版规范检查是完整实现的，但当前没有挂进转换主流程，只作备查。此外，docx 的脚注（footnotes.xml）目前不解析——对本任务够用，但不是全量保真。这些清理起来会牵动评测调用签名、宜作独立一次维护来做，因此现在按兵不动。
