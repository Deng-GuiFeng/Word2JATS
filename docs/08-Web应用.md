# 08 · Web 应用

这一篇讲项目里那个网页——我们叫它「校样工作台」。读完你会知道：为什么一个命令行工具还要再套一层网页，这个网页给谁用、要解决他们的什么顾虑，它在技术上怎么搭起来，以及那张结果页为什么长成「交付前自检报告」的样子。

命令行版怎么装、怎么跑，在 [09-安装与使用](09-安装与使用.md) 里；这里只讲这个网页本身的设计。

---

## 为什么要做这个网页

转换器本身是个命令行程序：敲一条命令，进去一个 Word 文件，出来一份 JATS XML（JATS 是学术出版界通用的、用 XML 描述期刊论文结构的标准，详见 [02-领域基础](02-领域基础.md)）。对写代码的人来说这够用了。但我们额外做了一个网页应用，原因有两个，而且是性质完全不同的两件事。

**第一件，是把门槛拆掉。** 真正要用这个工具的人是期刊编辑，不是程序员。让他们去装 Python、配环境变量、敲命令行，这条路基本走不通。网页把这些全挡在后面：编辑打开一个网址，把 Word 稿拖进去，等几分钟，下载一个压缩包，里面就是 XML 加图片。中间那套模型调用、XML 生成、校验，他一点都不用管。这是落地性最直观的一环——竞赛评分里，「落地性」占的分量最重（见 [01-竞赛与任务](01-竞赛与任务.md)），一个编辑真能上手用的界面，比任何说明都有说服力。

**第二件，更本质，是把项目的核心主张「摆到明面上」。** 这个项目的立身之本是一句话：**只添加结构，绝不改动正文一个字**（我们把它叫「内容守恒」——转换后的正文文字与源 Word 稿逐字一致，不增、不减、不改，机制见 [04-系统设计](04-系统设计.md)）。问题是，XML 是一堆尖括号标签，编辑看不懂；如果工具只吐一份 XML 出来，这个主张就变成了一句无法验证的空话，编辑凭什么相信你没把他的稿子改坏？所以网页把两件看不见的事翻译成看得见的东西：一是**排版预览**，让编辑用眼睛确认图、表、公式、参考文献都在、位置对；二是**原文核对**，把输出和原稿逐词比一遍，把两边对不上的词一个一个摆出来给他看。看得见，才信得过。

## 用它的人是谁，他在担心什么

设定的用户是期刊的生产编辑、排版人员，或者小型开放获取（OA）刊物的责任编辑。这类人有几个共同点：多数不想、也不需要懂 XML 和 DTD（DTD 是规定「XML 里哪些标签合法、能怎么嵌套」的规则文件）；他们的心态是**校样审阅员**——拿到一份即将付印的稿子，逐项核对有没有问题，最后决定能不能签字放行。

他们最怕两件事：**把原文改坏了**（哪怕改一个数字、漏一句结论，学术稿件都是事故），以及**漏掉内容**（某张表、某条参考文献没转进来）。他们心里真正要回答的问题只有一个：**这份东西，我能不能放心交出去。**

整个网页，尤其是那张结果页，就是围着这个问题设计的。它不摆技术指标给编辑看，它替编辑把该核对的都核对一遍，然后把结论顶在最上面：可交付，还是待确认。

## 几条绕不开的硬约束

在讲怎么搭之前，先说清楚有几个技术现实是躲不掉的，它们直接决定了这个网页长什么样。

- **转换很慢，而且是阻塞的。** 一次转换要调好几趟云端大模型来判断文章结构，整个过程实测 109 到 252 秒（10 个样例，默认模型），稿子越长、参考文献越多越久。如果让网页请求一直等在那儿，服务会被卡死。所以转换不能同步做，必须改成「先提交、后查结果」的异步方式，慢活儿甩到后台去跑。
- **每次转换都真花钱。** 调云端模型是要按量付费的，API 密钥（key，调用模型的凭证）必须由服务端保管，绝不能发到浏览器里让用户拿到。同时，同一份稿子如果重复转，不该重复烧钱，得有缓存。
- **产物不是一个文件，是一包。** 输出的 JATS XML 里会引用图片，图片是从 Word 里提取出来单独存成文件的（详见 [02-领域基础](02-领域基础.md) 里讲的「图片外部化」）。所以下载得打成一个压缩包，XML 和图片一起给。
- **浏览器不能再靠自己渲染 XML。** 把 JATS XML 变成好看的期刊排版页面，靠的是一套叫 XSLT 的变换样式表（可以理解成「把 XML 翻译成 HTML 的规则」）。浏览器原本内置了这个能力，但各家浏览器正在陆续把它移除，靠它不可持续。所以渲染这一步必须挪到服务端做。

下面的架构，基本上就是对这四条约束逐条作答。

## 架构：一个进程把所有事办了

整个网页应用是**一个 FastAPI 进程**。FastAPI 是 Python 里一个轻量的网页服务框架，天生就会处理文件上传、异步请求，还能顺带把静态网页托管起来，一个进程就同时当了后端接口和网页服务器，不用再另起一台。前端是一个纯手写的 HTML 页面加一段原生 JavaScript，**没有用任何前端框架、不需要构建打包**——因为交互本身就很简单，无非是「上传、等待、看结果」几个状态来回切换，引入 React 那一套只会给部署和评审添麻烦。

**转换怎么异步跑。** 编辑点「开始转换」，浏览器把 Word 文件发到 `/api/convert` 这个接口。服务端不当场转，而是生成一个任务号（task_id）立刻返回，把真正的转换活儿丢进一个后台线程池慢慢跑。浏览器拿到任务号后，每隔一秒去问一次 `/api/status/{任务号}`，看进度到哪了；一旦状态变成「完成」，再去 `/api/result/{任务号}` 把结果拉回来。这样请求线程秒回，服务不会被那几分钟卡住。后台真正干活的，还是命令行版同一套转换管线（`word2jats.pipeline.convert`），网页层只负责收文件、派活、展示——转换逻辑一行都没有重写，这也保证了网页出来的结果和命令行完全一致。

**进度是能看见的。** 转换管线跑到「读取 Word」「识别结构」「生成 XML」「检查合规」这几个阶段时，会回调通知服务端，服务端记进任务状态里，前端据此把进度条上对应的步骤点亮。编辑等待时不是干瞪眼，能看到活儿进行到哪一步。

**任务状态存哪。** 就存在进程内存里的一张表（一个字典，用锁保护读写，避免后台线程和请求线程打架）。没有上数据库、没有上 Redis。这是**刻意的单机取舍**：当前是一台机器对外提供服务，一张字典就够。代价是服务一重启，任务记录就全没了——这个边界后面还会再提。

**密钥和缓存都在服务端。** API 密钥只放在服务端的配置文件里（`.env`），前端从头到尾碰不到。模型调用结果落到磁盘缓存（`webapp/_cache/`），同一份稿子再传一次，直接命中缓存秒回、不再花钱。每个任务的上传件和产物放在 `webapp/_runs/<任务号>/`，分片上传的中途块放在 `webapp/_uploads/<上传号>/`（拼完即清）。这三个目录都是运行期产物，不入库、可随时删。

**渲染放在服务端。** 前面说了浏览器原生 XSLT 正被移除，所以由服务端用一套成熟的样式表把 JATS 变成期刊样式的 HTML。这套样式表用的是 **NCBI（美国国立生物技术信息中心）公开发布的 JATS 预览样式表**，属于公有领域、可自由使用，本身有四千多行、久经考验，自己重写不现实。放服务端还有个额外好处：可以在变换前后做一些浏览器端很难做的加工（改写图片引用、给参考文献补标点、处理公式命名空间、剥掉多余的诊断信息），下面讲结果页时会具体说到。变换时还锁死了样式表读取外部资源的权限，防止它偷偷联网。

**对外的接口清单**（编辑不会直接接触，但能帮你看清系统边界）：

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/` | 上传页 |
| GET | `/api/journals` | 期刊下拉列表（刊号 + 刊名） |
| POST | `/api/convert` | 一次性提交转换（Word 文件 + 可选 DOI / 期刊）→ 返回任务号 |
| POST | `/api/upload/init` | 开一个分片上传会话（文件名 / 总字节 / 总块数）→ 返回上传号 |
| PUT | `/api/upload/{上传号}/{序号}` | 上传第几块 |
| GET | `/api/upload/{上传号}` | 查已收到哪些块、还缺哪些（断点续传靠它） |
| POST | `/api/upload/{上传号}/complete` | 按序拼回原文件、校验哈希，转入转换 → 返回任务号 |
| GET | `/api/status/{任务号}` | 轮询状态（排队 / 转换中 / 完成 / 失败 + 阶段 + 耗时） |
| GET | `/api/result/{任务号}` | 取结果（内容清单 + 校验 + 忠实自检 + XML 全文） |
| GET | `/api/render/{任务号}` | 服务端渲染的期刊样式 HTML（供预览用） |
| GET | `/assets/jats-preview.css` | 预览页配套样式表 |
| GET | `/api/download/{任务号}` | 下载压缩包（XML + 外部化图片） |
| GET | `/api/figure/{任务号}/{文件名}` | 预览页引用的图片 |

前四个 `/api/upload/*` 是分片上传通道，为绕开 Cloudflare 隧道对单个请求的 100 秒超时而加，根因和实测参数见 [10-部署上线](10-部署上线.md)；`/api/convert` 是一次性通道，留给小文件和命令行调用。

**几处细节值得一提，因为它们体现了「替编辑把关」的态度。**

出错时给的是人话，不是报错堆栈。后台转换整个包在异常捕获里，无论中间哪一步崩了，服务都不会挂，而是把内部错误翻译成编辑看得懂的话——比如上传的根本不是有效的 Word 文件，就提示「这个文件打不开，可能不是有效的 Word 文档或已损坏」，而不是甩一串英文异常，也不会泄露服务器上的文件路径。

图片接口对 TIFF 做了转换。学术出版的插图常常是 TIFF 格式，浏览器不认。为了**预览**能显示，服务端会把 TIFF 临时转成 PNG——注意，只是预览时转，**下载包里的原始字节一动不动**。转换时还特意处理了透明背景：先合成到白底再转，否则透明区域会被填成黑色，把本来黑线黑字的科研图整个吞没。这种「为了让人看清、又绝不动原始数据」的分寸，正是整个项目的态度缩影。

图片接口还防了目录穿越攻击——请求的文件名会先解析成绝对路径，确认确实落在该任务自己的输出目录里，才允许读，杜绝有人用 `../` 之类的路径去翻服务器上的其它文件。

## 结果页：一张「交付前自检报告」

结果页是整个网页的重头戏，它的信息架构不是按技术模块排的，而是**按一个校样编辑心里的疑问顺序**排的，分成五个区。而且**结论先行**：页面最上方先盖一个章——「可交付」或「待确认」。这个结论是算出来的：如果 DTD 校验没过、或者存在高等级的结构问题，就盖「待确认」并写明有几处要处理；否则盖「可交付」。编辑一眼就知道大局，要不要往下细看，自己决定。

往下五个区，各回答一个问题：

- **§1 成品预览**——「排版出来是什么样，图表公式齐不齐？」这里嵌的就是服务端渲染的期刊样式页面，编辑先整体扫一眼，图、表、公式、参考文献在不在、位置对不对。这一区对应的技术实质是 XSLT 渲染，但对编辑来说就是「看清成品」。
- **§2 原文核对**——「正文有没有被改坏、漏掉？」这是把内容守恒摆到明面的地方，下一节专门讲。
- **§3 内容清单**——「各部分都数对了吗？」把文章拆成「文章信息 / 正文 / 参考文献」三组，列出作者数、单位数、关键词、分节数、图表公式数、参考文献条数等，每组配一句提示编辑该核对什么（比如「对照原稿封面，核对作者顺序、单位对应、关键词是否齐全」）。这一区背后是转换管线产出的统计数字，但呈现成一张让编辑逐项打勾的清单。
- **§4 合规检查**——「符不符合出版标准？」这里是 DTD 校验结果，加上 DTD 之外的结构质量检查，按严重程度分级列出。术语用「合规检查」而不是「DTD 校验」，是有意的——编辑关心的是「合不合出版规范」，不是规范叫什么名字。
- **§5 XML 源文件**——「原始产物长什么样？」高亮显示完整的 JATS XML，并明确标注「供技术人员核对，普通编辑无需查看」。它摆在最后，是给排版技术人员留的后门，不打扰编辑。

整套用词都刻意站在编辑视角，避开实现术语：叫「原文核对」不叫「词表比对」，叫「内容清单」不叫「统计数据」，叫「成品预览」不叫「XSLT 渲染」。但每一区背后对应的技术实现是清楚的，这也是为什么这一节两头都点到——让工科读者既看得懂编辑那一面，也知道底下是什么机制。

## 诚实核对：把「没改坏」证给人看

§2 原文核对是这个网页最较真的地方，因为它要兑现整个项目最重的那句承诺。

它做的事很直接：把输出 XML 里的正文取词、把原稿 Word 里的正文取词，两边做词频比对，算出两个覆盖率——**输出里有多少词是来自原稿的**（衡量有没有凭空多出内容）、**原稿里的词有多少保留进了输出**（衡量有没有漏掉内容），再把两边对不上的词列出来（数量多时给一份代表性样本，约 40 个）供编辑逐词核对。

这里有个容易踩的坑，处理得很讲究。Word 在内部会把一个词拆散存进好几个「片段」（run，是 Word 里带样式的最小文字单元），同一个单词可能横跨好几段——比如 "paradigm" 可能被存成 "p" 加 "aradigm"。如果照着这些片段直接切词去比，就会凭空冒出一大堆「对不上」的假差异，明明正文一个字没改，却报出满屏问题，把「没改坏」这个事实污染成假警报。所以这里**不按 Word 的原始片段切词**，而是复用转换管线里的「按段落先拼合、再切词」的口径——先把一段里被拆碎的片段拼回完整文字，再切词比对。这样得出的差异才是真实的、值得核对的。

即便如此，比对结果里通常还是会有一小撮「多出的词」和「少掉的词」，页面对这两类都老实交代了它们的来路，不藏着掖着：「多出的词」大多是系统按出版规范补进去的元数据（刊名、ISSN（国际标准连续出版物号，一本刊的唯一编号）、版权和开放获取声明——这些本就是结构化要加的、不属于原文），偶尔夹带个别切词边界差异；「少掉的词」则可能是随图片一起转走的图表内文字，或者作者单位、通讯地址、ORCID 这类改成了结构化字段著录的信息，让编辑逐词确认「不是正文被漏掉」。摆出来让人核对，而不是给个「100% 通过」的黑箱结论——这才是工科读者会信的做法。

还有一处「只在明面上补、绝不写进产物」的分寸，值得单独点出。参考文献在 JATS 里用的是**结构化著录**（element-citation，把一条文献拆成作者、年份、卷、期、页这些独立字段，详见 [02-领域基础](02-领域基础.md)），按规范这些字段本身**不该带标点**——分隔用的句点、分号、括号是渲染系统的活儿，不是数据的一部分。可 NCBI 那套样式表偏偏不补这些分隔，于是「2023」「24」「11939」会糊成一串「20232411939」，没法读。解决办法是：**只在预览渲染那一刻，按字段类型临时注入温哥华式的分隔标点**（温哥华式是医学期刊常见的参考文献标点风格，形如「刊名. 年;卷(期):页」），让预览读起来像真实期刊条目；而**下载得到的 XML 里，这些字面标点一个都没有**，与我们冻结的结构参考逐字一致，符合 JATS 规范。换句话说，好看的标点只活在预览层，交付的数据保持纯净。

## 已知的边界

三条限制，都是「单机对外服务」这个定位下的主动取舍，诚实摆在这里：

其一，**任务记录存在进程内存里，服务一重启就全丢**，也没法多机横向扩展。要抗并发，得把任务表换成数据库或 Redis。

其二，**任务产物和模型缓存只增不清**。`webapp/_runs/` 和 `webapp/_cache/` 没有过期清理逻辑，长期不停地跑，磁盘会一直往上涨，得靠人工定期清。分片上传的中途目录 `webapp/_uploads/` 有清理，但只认得当前进程内的会话——进程重启后，之前留下的目录就没人扫得到了。

其三，**没有认证、限流和任务配额**。除了单文件大小上限，任何人拿到地址都能不限次提交转换，而每次转换都真花钱调云端模型。当前靠「地址不公开传播」挡着，这不是安全措施。

这些不影响它作为落地性载体的价值：一个编辑能真正拖进一份稿子、几分钟后拿到可交付的 JATS 包、还能亲眼核对正文没被改坏——这件事本身，就是这个项目「能真用起来」最直接的证明。
