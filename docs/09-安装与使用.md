# 09 · 安装与使用

这篇是操作手册：把环境装好、转换一篇论文、起网页应用、跑评测复现成绩、跑测试。所有命令都可以直接照抄执行，都在项目里真实跑通过。读完你就能亲手把 word2jats 用起来。

前面几篇讲的是"是什么、为什么"，这一篇只讲"怎么做"。方法背后的道理见 [04-系统设计](04-系统设计.md)，评测口径见 [06-评测与成绩](06-评测与成绩.md)，网页应用的设计见 [08-Web 应用](08-Web应用.md)。

## 运行环境

**Python 版本**：3.9 及以上。项目在 Python 3.12 上完整验证过（依赖清单和 Docker 镜像都基于 3.12）。

**依赖库**：命令行转换需要 6 个核心库，网页应用再额外需要 3 个。

| 库 | 干什么用 |
|---|---|
| `python-docx` | 解析 Word 文档（docx 是换了后缀的 zip 包，正文几乎全在里面的 `word/document.xml`，见 [02-领域基础](02-领域基础.md)） |
| `lxml` | 构建 XML、跑 OMML→MathML 的样式表转换、用官方规则文件校验 XML 是否合法 |
| `Pillow` | 读取内嵌图片、按字节识别格式与尺寸——核心转换据此把图外部化、直写原始字节不重编码；网页应用另用它把浏览器不认的 TIFF 出版图按需转成 PNG 仅供预览，不动交付的原始字节 |
| `PyYAML` | 读期刊查表等配置 |
| `openai` | 调大模型做结构理解（走 OpenAI 兼容接口，DashScope、DeepSeek 都用它） |
| `python-dotenv` | 从 `.env` 文件读取模型 API Key |
| `fastapi`、`uvicorn`、`python-multipart` | 仅网页应用需要：Web 框架、服务器、解析文件上传 |

这里要澄清一点：`openai` 和 `python-dotenv` 不是"可选增强"，而是必需项。本项目的转换方法靠大模型判断文章结构（哪段是标题、参考文献每个字段的边界在哪里），没有大模型就出不了可用结果——道理在 [04-系统设计](04-系统设计.md) 讲透了。这一点也决定了下面"配密钥"这一步不能省。

**大模型后端与密钥**：默认后端是阿里云百炼 DashScope 的 `qwen3.7-plus` 模型（走 OpenAI 兼容接口）。你需要一个 API Key，填进项目根目录的 `.env` 文件。**没配可用密钥时程序不会报错，但只会产出一个"空壳"——结构合法、内容却几乎是空的 XML**，那不是可用结果，只是不崩而已。

**一个必须知道的版本坑**：转换和评测都要用 JATS 官方的 DTD（文档类型定义，即"哪些标签合法、能怎么嵌套"的规则文件，见 [02-领域基础](02-领域基础.md)）来校验 XML 合不合法。这一步对 `lxml` 背后的 `libxml2` 库版本很敏感。项目自带虚拟环境里的 lxml 6.1.1 能正常加载 JATS DTD；而某些较旧的构建（例如某些 Anaconda 环境自带的旧版 lxml）会在加载 DTD 时直接抛 `DTDParseError`。**结论：装依赖时用 lxml 6.0 及以上；跑评测请用项目自带的 `.venv`，别用系统里别的 Python。** 用 Docker 时不用操心这个——镜像里的 lxml 轮子自带匹配的 libxml2。

## 装环境

项目自带一个装好依赖的虚拟环境 `.venv/`。首次准备环境，二选一：

```bash
# 方式一：沿用项目自带的虚拟环境（推荐，已验证）
.venv/bin/python -m pip install -r requirements.txt

# 方式二：另建一个新的虚拟环境
python -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

`requirements.txt` 已经把命令行核心 6 个库和网页应用的 3 个库都列全，一条命令装到位。

## 配置密钥

把密钥模板复制成 `.env`，填入你自己的 Key（至少配一个后端即可）：

```bash
cp .env.example .env
# 然后编辑 .env，把 DASHSCOPE_API_KEY=... 那一行换成真实的 Key
```

模板 `.env.example` 里给了两个后端的位置：默认的 DashScope，和可选替代的 DeepSeek。每个后端各有 `_API_KEY` 和 `_BASE_URL` 两项，`_BASE_URL` 一般保持模板里的默认值不用动。密钥文件不会进版本库，打包提交物时也会被排除，不用担心泄露。

## 转换一篇论文

命令行入口是 `word2jats convert`。不做正式安装也能用 `python -m word2jats` 直接调用，只要把 `src` 目录加进模块搜索路径：

```bash
PYTHONPATH=src .venv/bin/python -m word2jats convert \
    样例数据/03/初始文件.docx \
    --journal JIN \
    --doi 10.31083/JIN49347 \
    -o output/
```

参数一览：

| 参数 | 作用 |
|---|---|
| 第一个位置参数 | 输入 docx 路径（必填） |
| `--journal` | 期刊代号（如 `RCM`/`JIN`/`HSF`/`CEOG`），缺省时尝试从 DOI 前缀推断 |
| `--doi` | 文章 DOI（数字对象标识符），用来生成文章标识、并推断期刊 |
| `-o` / `--out-dir` | 输出目录（默认 `output`） |
| `--llm` | 大模型后端：`dashscope`（默认）/ `deepseek` / `local`（本地自建模型） |
| `--no-validate` | 跳过出口校验（DTD + 内容守恒 + 结构自洽），排查问题时才用，正常别加 |

其中"内容守恒"指的是：转换后的正文文字与源 Word 稿逐字一致，不增、不减、不改——这是本项目的核心保证，出口校验会核对它。

跑完会在输出目录得到 `<文章号>.xml`（本例是 `JIN49347.xml`）和外部化出来的图片文件，终端会打印统计：作者数、参考文献数、图表公式数，以及 DTD 校验是否通过。要换成自己的稿子，把 docx 路径、`--journal`、`--doi` 换掉即可。

## 起网页应用

网页应用「校样工作台」把命令行那一套包成了一个网页：编辑上传一篇 Word，几十秒后拿到 JATS XML 和一份"交付前自检报告"，全程不碰命令行。它为什么这么设计、结果页那五个分区各在核对什么，见 [08-Web 应用](08-Web应用.md)；这里只讲怎么把它跑起来。

**本地起服务**：

```bash
python -m webapp                              # 默认 http://127.0.0.1:8000
python -m webapp --host 0.0.0.0 --port 8080   # 换端口 / 对外开放
```

启动前同样要配好 `.env`（服务端持密钥，每次转换都真实调用云端模型、真花钱）。浏览器打开地址，拖入一篇 docx（可选填 DOI、期刊），点开始转换即可。同一个文件再传会命中磁盘缓存、秒回。结果页分五个区：成品预览、原文核对、内容清单、合规检查、XML 源文件。

**用 Docker 部署**：

```bash
docker build -t word2jats .
docker run -p 8000:8000 -e DASHSCOPE_API_KEY=sk-xxxx word2jats
```

镜像基于 `python:3.12-slim`，装依赖后只拷 `src/` 和 `webapp/` 进去，容器起来就在 8000 端口跑网页应用。**API Key 靠运行时的 `-e` 注入、不打进镜像**——镜像可能被分发，密钥打进去就等于泄露，所以刻意分开。构建好后浏览器访问 `http://<主机>:8000` 即可。

## 跑评测复现成绩

评测会把 10 个样例逐一转换，再用三层评测（合法 / 忠实 / 对位）打出一份逐类的缺陷清单——具体每层查什么、当前成绩如何，见 [06-评测与成绩](06-评测与成绩.md)。要复现成绩，**必须用项目自带的 `.venv`**（DTD 校验对 libxml2 版本敏感，前面讲过），并且把大模型后端显式设为 `dashscope`（评测脚本默认是 `off`，那是不调模型的空跑档，出不了真成绩）：

```bash
PYTHONPATH=scripts .venv/bin/python -m eval.run --llm dashscope
```

常用变体：

```bash
# 只评指定样例（逗号分隔）
PYTHONPATH=scripts .venv/bin/python -m eval.run --llm dashscope --samples 01,03,S01
# 给这次结果起个标签，产物落到 reports/eval/<标签>/；默认标签是 latest
PYTHONPATH=scripts .venv/bin/python -m eval.run --llm dashscope --tag mytest
```

关于产物、并发和复现：

- **产物**：`reports/eval/<标签>/eval.json`（机读汇总）、`eval.txt`（逐样例逐类缺陷清单），以及各样例的转换输出。当前成绩就在 `reports/eval/latest/eval.json` 里——10 例合计 80 条缺陷，全部通过 JATS 1.3 DTD 校验。
- **并发**：10 个样例、每个样例内部的多个理解任务，都是全量并发跑的。云端模型支持高并发，串行纯属浪费；并发已硬编码进脚本，不用配置。
- **确定复现**：模型调用温度设为 0，并带一层磁盘缓存。首次运行会真实调用模型、把每个响应缓存到 `reports/eval/_llm_cache/`；之后再跑直接命中缓存，几秒完成，同一输入逐字节复现、与并发顺序无关。要注意的是，逐字节复现是缓存带来的，而不是温度 0 本身带来的——实测云端在温度 0 下也并非位级确定（这一点的来龙去脉见 [07-消融与方法验证](07-消融与方法验证.md)）。

## 跑测试

```bash
.venv/bin/python -m pytest
```

测试套件共 79 个用例，绝大多数不依赖大模型，随时能跑：

- **确定性单元测试**（占大头）：锁住渲染与组装层的机械正确性——比如把大模型可能吐出的畸形索引归一化、制表符拼排的表格切成规整网格、参考文献著录在网页预览时补上分隔标点却不动交付的 XML。这些不调模型，任何环境都能跑、都该全绿。
- **评测器自身的回归**：拿结构参考（本队为每个样例建的、评测打分用的对照 XML）自己比对自己，验证评测器无漏检、两次跑逐字节一致。
- **端到端集成测试和网页应用测试**：会真正跑一遍转换，因而依赖大模型。为了不在每次测试时真花钱、又能确定复现，它们复用上面评测预热出来的 DashScope 磁盘缓存；**缓存不存在（或没配 Key）时，这几例会自动跳过而不是失败**，并提示先跑一次评测预热缓存。所以"收集到 79 个用例"不等于"79 个全部通过"——干净环境里那几例是跳过状态，先跑一次 `python -m eval.run --llm dashscope` 把缓存热起来，它们才会真正执行。

## 常见问题

- **输出几乎是空的**：多半是没配好大模型密钥，程序退化成了只出合法空壳。检查 `.env` 里的 Key 是否填对、有效。
- **DTD 校验处报 `DTDParseError`**：用了不兼容的旧版 lxml/libxml2。改用项目自带的 `.venv`（或用 Docker，镜像里的版本是对的）。
- **图片没出来**：图片会从 docx 内嵌媒体按正文出现顺序自动提取、外部化成独立文件。若没出来，先确认 docx 里是不是真的含内嵌图（有些稿子的"图"其实是链接到外部文件的，那就取不到）。
- **集成测试被跳过**：这是正常行为，不是报错。它在等评测预热的缓存，先跑一次评测即可。
