# 10 · 部署上线

这篇讲怎么把网页应用（[08-Web 应用](08-Web应用.md)）挂到公网上给外人用、日常怎么维护、以及为此在网络层做了哪些不得不做的处理。读者是要接手运维这套部署的人：知道命令行，但不了解 Cloudflare、隧道这类概念——凡术语，第一次出现都先讲明白。

本机指部署所在的服务器 **PRO6000**（实验室一台带 GPU 的机器，在校园网内）。本项目的转换全靠云端大模型 API，不吃本机显卡，所以这台机器在这里只是个普通的 Web 服务器。

---

## 一、现在长什么样

**对外地址：`https://word2jats.jianglab.work`**，任何人用浏览器打开就能上传 Word、拿到 JATS XML。

整条链路：

```
浏览器
   │ HTTPS（证书由 Cloudflare 自动签发）
   ▼
Cloudflare 边缘节点（离访客最近的一个）
   │ 加密隧道（本机 cloudflared 主动发起的长连接）
   ▼
PRO6000 上的 cloudflared 进程
   │ 按域名转发到本地端口
   ▼
127.0.0.1:8504 ← 网页应用（uvicorn 起的 FastAPI 服务，由 systemd 托管）
```

**为什么要用「隧道」而不是把域名直接解析到本机。** PRO6000 在校园网的 NAT 后面（NAT：多台内网机器共用一个对外出口，内网 IP 从公网无法直接访问），没有可对外的公网 IP；而且在中国大陆用域名对公众提供网站服务需要 ICP 备案，走流程要十几个工作日。**Cloudflare Tunnel** 绕开这两条：本机运行一个叫 `cloudflared` 的程序，主动向 Cloudflare 的边缘节点建立一条加密长连接（隧道）；访客访问域名时先到 Cloudflare，Cloudflare 再经这条隧道把请求送回本机。这样本机不需要公网 IP、不开任何入站端口、免备案，HTTPS 证书也由 Cloudflare 自动签发。代价是域名的解析必须托管在 Cloudflare。

这套「域名 → 本机端口」的通用框架不属于本项目，它在本机的 `~/deploy_website/` 有独立文档（隧道名 `jianglab`、如何加新站点等）。本篇只讲 word2jats 这个站点自己的部分。

**两个访问入口：**

| 入口 | 地址 | 特点 |
|---|---|---|
| 公网 | `https://word2jats.jianglab.work` | 任何人可用；经 Cloudflare 隧道，见下「四」的上传处理 |
| 校园内网 | `http://10.39.12.242:8504` | 只有校园网内可达；直连本机、不过 Cloudflare，快且稳，适合本地自测与校内使用 |

## 二、进程与端口

部署由两个常驻进程组成，各管一段，都由 **systemd** 托管（systemd：Linux 的服务管理器，能开机自启、进程崩溃自动重启、日志统一进 journal）：

**1）网页应用本身**——systemd 服务 **`word2jats-web`**（单元文件 `/etc/systemd/system/word2jats-web.service`），跑 `.venv/bin/python -m webapp --host 0.0.0.0 --port 8504`，监听 **8504** 端口（端口号沿用 `~/deploy_website` 的约定：新站点从 8504 起）。`--host 0.0.0.0` 表示所有网卡都监听，这样校园内网 IP 也能连上（若只写 `127.0.0.1` 就只有本机自己能连）。单元里几处关键设定：`WorkingDirectory` 设为项目根目录（应用靠向上查找定位根目录下的 `.env` 密钥文件，见 [09-安装与使用](09-安装与使用.md) 的「配置密钥」）；`Environment=NO_PROXY=*` 强制直连——本项目只调用 DashScope 国内云 API，绝不能走机器上的 Clash/VPN 代理；`Restart=on-failure` 崩溃自动拉起。已 `enable` 开机自启。

**2）隧道进程 `cloudflared`**——服务名 `cloudflared`，同样已设为开机自启。它读 `~/.cloudflared/config.yml`，把 `word2jats.jianglab.work` 转发到 `localhost:8504`。

**起、停、查：**

```bash
# —— 网页应用 ——
sudo systemctl status word2jats-web      # 看状态
sudo systemctl restart word2jats-web     # 改了应用代码后重启生效
sudo systemctl stop word2jats-web        # 停
sudo journalctl -u word2jats-web -f      # 实时日志

# —— 隧道 ——
sudo systemctl status cloudflared        # 看状态
sudo systemctl restart cloudflared       # 改了 config.yml 后重启生效
sudo journalctl -u cloudflared -f        # 实时日志
```

> **改了应用代码后要 `sudo systemctl restart word2jats-web`** 才生效（Python 进程启动时就把代码加载进内存了）。前端静态文件（JS/CSS/HTML）是每次请求现读磁盘，改了刷新浏览器即可——但注意 Cloudflare 会缓存 JS/CSS，见「五、缓存」。

## 三、验证部署是否正常

按「从里到外」的顺序查，一步不通就停在那一层：

```bash
# 1. 应用在不在（本机自查，不过隧道）
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8504/        # 期望 200

# 2. 隧道通不通（有没有连接器）
cloudflared tunnel info jianglab                                       # 期望看到 CONNECTOR

# 3. 公网到不到（经 Cloudflare）
curl -s -o /dev/null -w "%{http_code}\n" https://word2jats.jianglab.work/   # 期望 200
```

第 1 步不通 → 应用挂了，看 `sudo journalctl -u word2jats-web -e` 里的报错。第 1 步通、第 3 步不通 → 隧道或 DNS 的问题，看 `journalctl -u cloudflared`。

## 四、大文件上传：为什么要「分片」

这是这套部署里最需要理解的一处。它不是锦上添花，是不做就会坏。

**问题。** 经 Cloudflare 隧道时，一次 HTTP 请求如果超过约 **100 秒**源站还没回应，Cloudflare 会掐断并返回 **524** 错误（524：Cloudflare 特有的「源站超时」码）。而作者的投稿 Word 常带大量插图、有几十 MB；国内到 Cloudflare 边缘（实测落在美国洛杉矶）这条国际链路又慢又容易丢包，把整个文件用一次请求传完，要么超过 100 秒撞上 524，要么传到一半连接就断了（浏览器报 `Failed to fetch`、或 502）。实测：一个几十 MB 的文件直传，多次尝试里大半失败。

**为什么不能简单绕开。** Cloudflare 官方对这类长上传的建议是「把该子域名设成不经 Cloudflare 代理（DNS-only）」——但这条对隧道不适用：隧道的域名记录必须开启 Cloudflare 代理才能工作，一旦关掉，隧道就失效了（隧道没有真实公网 IP 可解析）。而那个 100 秒超时，免费版不可调。所以只剩一条路：**别让任何单个请求接近 100 秒**。

**做法：分片 + 断点续传上传。** 把文件在浏览器端切成若干小块（**数据块**，每块 2 MiB），一块一块单独上传；每块几秒就传完，远低于 100 秒。中途某块断了，只重传那一块，不用从头再来（这就是**断点续传**）。全部块传完，服务端按序拼回原文件、校验无误后，才走原来的转换流程。这套协议借鉴了业界成熟的可恢复上传标准（tus.io）和大厂的分块惯例（Google 云存储），并针对上面的隧道约束做了取舍。

服务端为此新增了几个接口（`/api/upload/init`、逐块 `PUT`、查缺失、`complete`），并保留原来的一次性上传接口 `/api/convert` 供小文件和命令行使用。实现细节见 [05-模块实现](05-模块实现.md) 的网页应用一节。

**两个关键参数，都是有实测依据定的：**

- **数据块 2 MiB（而非更大的 4 MiB）。** 真实隧道实测传 30 MB：块大小从 4 MiB 换成 2 MiB，总耗时几乎不变（差异淹没在网络抖动里），但**单块最慢从 15 秒降到 8.7 秒**。块越小，中途撞上断连的概率和白扔的字节越少、离 100 秒超时越远、进度条也更细腻；代价（请求数变多）在下面的并发下被掩盖，可忽略。

- **并发 3 块同时传（而非 1 块）。** 真实隧道实测传 30 MB：

  | 同时传几块 | 上传耗时 | 聚合速率 |
  |---|---|---|
  | 1 | 66.5 s | 462 KB/s |
  | **3** | **26.7 s** | **1151 KB/s** |
  | 6 | 25.5 s | 1203 KB/s |

  为什么并发能快 2.5 倍——明明是同一条带宽？因为**单条连接在这条高延迟、有丢包的国际链路上根本吃不满带宽**：一条 TCP 连接的速度被往返延迟和丢包压制（丢一次包，发送速率就减半再慢慢爬回来），远达不到链路上限。多开几条并发连接，各自独立，就把单条吃不下的容量补上了。到 3 条已接近链路天花板，再加到 6 条几乎不再变快，反而让每块变慢（单块最慢从 8 秒涨到 15 秒）、还更容易触发 Cloudflare 的频率限制。所以 **3 是收益与代价的平衡点**。

  一个诚实的保留：上面实测用的是独立连接。真实浏览器对 Cloudflare 走 HTTP/2 多路复用，多个请求可能挤在一条连接上，客户端这一段的并发红利会打折；但真正慢的是跨太平洋那段隧道，并发红利主要来自那里，方向不变。此外「一块卡住不拖累其它块」这个好处与协议无关，始终成立。

这两个参数是前端 `webapp/static/app.js` 里的 `CHUNK_SIZE` 和 `UP_CONCURRENCY`，要调直接改那里（块大小另可用 `window.__W2J_CHUNK_SIZE__` 在运行时覆盖）。

## 五、缓存：静态文件带版本号

Cloudflare 默认会缓存 JS/CSS 这类静态文件（缓存数小时，且每个边缘节点各缓存一份）。这带来一个坑：改了 `app.js` 后，很多访客的浏览器仍从 Cloudflare 缓存里拿到**旧脚本**，配上新页面就会行为错乱。

处理办法：首页 HTML 由动态接口 `/` 返回（这个不被缓存），返回时给引用的静态文件 URL 自动挂上一个基于文件修改时间的版本号，形如 `/static/app.js?v=1784103600`。文件一改，修改时间变，URL 就变，等于换了个新地址，自动绕开所有缓存。**所以改完前端不需要手动清 Cloudflare 缓存**，刷新即是最新。这段逻辑在 `webapp/app.py` 的 `index()` 里。

## 六、隧道传输的一处调优

`cloudflared` 默认用 QUIC 协议（跑在 UDP 上）与 Cloudflare 通信。实测这台机器上 QUIC 上传吞吐很低——一是 QUIC 需要较大的系统 UDP 缓冲区而默认值偏小，二是校园网对 UDP 常有限速。改成 **HTTP/2 协议（跑在 TCP 上）** 后上传明显变快。所以 `~/.cloudflared/config.yml` 里显式写了 `protocol: http2`。

（另外 `/etc/sysctl.d/99-cloudflared-quic.conf` 把系统 UDP 缓冲区调大了，那是 QUIC 时代留下的，现用 HTTP/2 后不再起作用，留着无害；若哪天改回 QUIC 会用到。）

## 七、已知约束

- **国际链路是硬瓶颈。** 隧道边缘落在美国，国内到那里又慢又丢包。分片上传解决的是「不失败」，不是「变快到本地那样」；真实速度受这条链路限制，服务器端无法根除（免费版 Cloudflare 不给选更近的边缘节点）。校园内用户直接用内网地址（见「一」）可完全绕开。
- **单点。** 这台机器关机、断网，或隧道进程挂掉，公网立即不可访问。好在网页应用与隧道两个常驻服务都由 systemd 托管、已开机自启并崩溃自动重启，所以机器重启后一般无需人工干预即可自行恢复。
- **Cloudflare 的机器人防护会拦非浏览器请求。** 用 `Python-urllib` 等默认 UA 直接打接口会被挡（返回 403）；真实浏览器和带浏览器 UA 的 `curl` 不受影响。自己写脚本测接口时需带上浏览器 UA。
