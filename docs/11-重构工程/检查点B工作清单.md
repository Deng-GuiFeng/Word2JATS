## 一、本文用途

本文汇总检查点 B 最近三轮运行及其后续分析，用作逐项讨论、修改和验收的唯一工作清单。

执行纪律如下：

1. 一次只处理一个编号问题；当前问题没有完成验收前，不顺带修改下一项。
2. 修改前先确认事实、根因、是否属于原施工规划，以及是否需要调整施工规划。
3. 禁止为某个样例增加专用判断、固定词表、标题名单、正则补丁或失败后临时拆分策略。
4. 每项修改必须解决同类 Word→JATS 问题，而不是只让现有 14 例通过。
5. “代码已经修改”不等于“问题已经修复”。只有针对性测试、全量测试、真实模型重跑和评测结果全部符合该项验收条件，才能勾选“确认修复”。

## 四、如何共同解释 V1 与 V2

V1与V2明显方向不同时，不能任选一个相信，也不能把两个数字相加。

V1适合回答“具体有哪些问题”。它把一条整篇缺失、一处字段错误和一个词种差异都记作一行，因此其总行数不能表示问题造成的实际损失大小。

V2适合回答“金标准中的细小事实完成了多少”。大结构恢复后，其中大量元素和文字都会成为正确事实，因此能够反映整片内容从无到有；但普通正确事实很多时，也可能掩盖少数关键功能完全失败，所以必须同时检查规划写明的必过项目。

X03是最典型的例子：

- 重构前35条参考文献全部缺失；重构后35条全部存在。
- V1参考文献类从“35条整条缺失”变成“29个内部字段问题”，该类实际改善。
- V1的文字问题也从20降到10。
- 但表格问题从0增到12、文后声明从1增到15、交叉引用从38增到45，最终清单总行数从103增到125。
- V2按内部事实计算，匹配元素从577增到1360、匹配文字从328增到793，所以元素和文字F1大幅上升。
- 然而X03要求的43个作者—年份引用仍然全部失败，因此它只能判为“参考文献整体恢复，但检查点仍未通过”。

后续判断顺序固定为：

1. 先看XML合法、文字和媒体守恒等不可妥协条件；
2. 再看施工规划明确列出的必过项目；
3. 再看V2八项结果，判断整体完成度；
4. 最后用V1同类问题清单定位原因；
5. 禁止再用V1总行数单独判断整体进退。

### B-01　X01正文分析必然超过转换器自行设置的20K输出上限

**状态：暂时解决。X01单次全新调用已经验证；最终确认留待检查点B的三轮无缓存复验。**

已确认事实：

- 转换器把模型单次输出上限设置为20,000 token。
- X01的正文分析把`w0-1214`共1215个源记录放进一次请求。
- 三轮均为第一次达到长度上限、原样重试一次、第二次再次达到长度上限，共稳定失败6次。
- 失败后整份正文分析作废，导致X01正文基本为空；参考文献30条虽已识别，正文引用和正文结构仍无法生成。

根因判断：当前窗口只按输入长度决定，没有保证所需输出也能装进单次返回。这不是模型随机性，也不是某种论文内容规则。

与规划的关系：原规划只写了“超过单次输入预算时按长度机械切窗”，没有覆盖输入不长但预期输出很长的情况。这是目前唯一已经确认需要先报告、再决定是否调整规划的地方。

处理决定（2026-08-19）：

- 不针对X01切窗，不增加失败后二分，也不增加任何正文内容规则；
- 根据当前模型文档，将转换器默认的单次输出上限由`20,000`改为`128,000`；这里的128K按十进制计数，即`128000`，不是`128×1024`；
- 所有理解任务继续共用同一个可配置的`output_token_budget`，没有为X01设置专用值；
- 客户端同时支持显式传入`None`时不发送`max_tokens`，但转换器当前默认值明确使用`128000`。

单次验证结果：

- 使用全新标签`b01-output-128k-x01-r1`和独立缓存重跑X01；
- 两次正文调用均实际携带`max_tokens=128000`，分别返回44,526和47,277个字符，停止原因均为正常结束`stop`，没有再出现`finish_reason='length'`；
- V1：L0继续通过，L1由935降至66，L2由143降至97，合计缺陷由1078降至163；
- V2：仍不通过，但八项质量指标全部上升；问题记录数由109增至451，是因为原来整块缺失的正文、图表恢复后，评测器开始展开记录细粒度差异，不能据此判为整体退步；
- 针对输出上限传递和客户端省略`max_tokens`的测试共37项通过；尚未以这一修改状态执行全量测试。

当前结论：20K人为上限导致X01正文必然截断的问题已在一次全新运行中消失，因此暂时标注解决。`128000`仍是有限上限，不能由单例推出任意规模文档永不截断；最终结论必须以检查点B后三轮全新、无缓存运行共同确认。

验收条件：

- 默认输出上限与当前模型公开的最大输出容量一致，不再由转换器自行压低到20K；
- 输出上限经统一配置传递到所有理解任务，不出现样例专用值；
- 长文档不因单窗截断而丢弃整篇正文；
- 通用测试覆盖默认值、显式配置和不发送上限三种行为；
- 三轮全新调用不再出现该类`finish_reason='length'`失败。

### B-02　模型识别出的正文引用因缺少源位置而全部作废

**状态：暂时解决。“缺少源位置导致全部作废”的系统性阻断已消除；最终确认留待完整转换、V1、V2和三轮无缓存复验。**

已确认事实：

- 提示要求每条引用返回“原文、所在源段落、目标参考文献”。
- 三轮中模型稳定返回了引用原文和目标参考文献，但把引用原文返回成普通字符串，没有返回源段落。
- 接收程序只允许带源段落的结构，因而拒绝全部结果。
- 每轮稳定报告534条相关问题；最终候选XML中的`bibr`引用数量均为0。
- X03的43个作者—年份引用全部未完成。

根因判断：引用识别、结果格式、源文定位和XML写入之间没有接通。不能通过作者姓名、年份、括号或编号规则重新猜测引用。

处理决定（2026-08-19）：

- 引用任务使用DashScope严格JSON Schema，每个源位置必须同时返回`quote`、`record_key`、`left_context`和`right_context`，不再接受不带位置的普通字符串；
- 用`single_target_citations`表示“一段可见原文→一条参考文献”，用`compact_range_citations`表示“一段紧凑范围→多条参考文献”；两者不得占用重叠的源字符；
- 程序只在`record_key`指定的源记录内，用引文原字和两侧原文核定唯一区间；同时校验目标实体已知、多目标不重复、源区间不重叠；
- 数字制、作者—年份制、原生Word表格、制表符段落等都走同一套表示和原文核定机制，没有按样例标题、作者、年份或参考文献编号增加规则；
- 提示词使用完全虚构的正例和反例说明表示契约，最终版本为`citations-v2.7`。

针对性验证结果：

- 引用Schema、原文定位、重复引文区分、软换行与表格行地址等5项测试通过；
- `qwen3.7-plus`使用全新缓存对14例独立运行3轮，42份结果中没有再出现“`citation_quote`是普通字符串”或“缺少源记录”的原始故障；但只有9份完全通过本地位置契约，其余问题是两侧原文不精确、源区间重叠或把单目标放入多目标数组，不是结果格式缺少位置；
- 对03、04、S01只提供表格记录时，`qwen3.7-plus`连续3次都分别找到12/12、76/76、3/3个目标；放回全文后又稳定遗漏，说明源文、参考文献身份和定位机制可用，全文覆盖受当前模型能力影响；
- 不改变系统设计，仅把模型临时替换为`qwen3.8-max`重跑14例后，03、04、S01的表格目标全部与金标准一致，证明不需要为这三个样例增加专用拆分或表格规则；
- `citations-v2.7`用`qwen3.7-plus`重跑14例后返回922/1012个目标，总偏差90；`v2.6`三轮分别为923/1012、912/1012、922/1012，总偏差89、100、90。新提示词整体不差于旧版，因此按已确认的口径采纳，但没有宣称它解决了当前模型的长文表格遗漏。

已知余项与执行边界：

- 当前模型在长篇全文中仍会遗漏一部分表格引用，也会偶发返回不能唯一定位的两侧原文；
- 转换器的责任是提供完整源文、稳健表示、严格校验和可替换模型接口，不为当前模型的能力上限增加表格编号、样例范围或失败后专用拆分规则；
- 因此，B-02只暂时关闭原始的“无位置导致全部作废”阻断。是否能在完整转换中稳定写入正确`bibr`，仍要由最终三轮转换和V1/V2确认。

验收条件：

- 引用任务返回的数据能够稳定定位到唯一源区间；
- 重复文字不会被连到错误段落；
- 无唯一位置或无唯一目标时保留纯文本并明确报告；
- 数字制和作者—年份制走同一套实体关系机制；
- X03的43处只是验收样本，不进入任何生产规则。

### B-06　XML生成程序允许写出DTD不接受的父子结构

**状态：暂时解决。已消除`addr-line/ext-link`的通用生成路径；最终确认留待检查点B的三轮无缓存复验。**

已确认事实：三份结果把`ext-link`写进`addr-line`不允许出现的位置；同一文档不同轮次有时合法、有时不合法。

根因已定位：

1. Word事实层正确保留了地址行中的超链接区间和目标；
2. 语义层把地址行作为`Address.lines: RichText`传入渲染层；
3. 原渲染器把`addr-line`当作通用富文本槽位，使用`preserve`投影；`rich()`遇到Word超链接就生成`ext-link`；
4. JATS Publishing 1.3的正式DTD规定：`address`可直接包含`ext-link`、`email`、`uri`，但`addr-line`的内容模型是`%simple-text;`，该模型不包含链接元素；
5. 因此这是“语义槽位没有执行JATS封闭内容模型”的渲染契约缺口，不是邮箱、网址或某个样例的识别问题。

处理决定（2026-08-19）：

- 在渲染层建立与JATS正式`%simple-text;`内容模型对应的统一投影入口，而不在邮箱、网址或样例上写条件；
- 该投影保留源文字、允许的强调格式、上下标及受支持的行内对象；Word超链接在该槽位中只投影可见原文，不生成DTD禁止的链接外壳；
- 已经成为语义实体的`ExternalLink`、`CrossReference`、`EmailInline`等不得静默降级；如果被放入`%simple-text;`槽位，在写XML前明确报错；
- `addr-line`只声明自己使用这个JATS标准投影，不再包含任何内容判断；
- DTD终检继续独立保留，用于发现其他内容模型缺口，不用本次投影替代DTD。

验证结果：

- 虚构通用夹具证明：带Word超链接的地址行可见文字逐字不变，粗体和斜体保留，`addr-line/ext-link`为0，地址片段通过DTD；不允许的语义内联类型均在写XML前失败；
- 直接使用S03、X04原docx中曾触发失败的`doc/p11`源节点复现渲染：分别包含1个和2个Word超链接，修复后可见文字逐字一致、非法嵌套为0、DTD均通过；

- 使用全新缓存`b06-simple-text-r1`对S03、X04完成一轮真实模型转换：两份候选都通过DTD，`addr-line/ext-link`均为0；X04实际生成10个`address`，因此完整覆盖了本次通道；S03本轮模型未生成`address`，其原失败节点由上一条确定性复现覆盖；

### B-09　作者关系与跨任务归并存在系统缺口；原“多领域共同回退”假设不成立

**状态：分析完成，尚未修改转换器。原问题已按根因拆开，待逐项讨论确认。**

#### 结论先行

原B-09把作者、表格、正文、文后声明和交叉引用并成了一个“系统性回退”，这个判断过宽，不能作为修改依据：

- X03是外部探针，不属于10个计分样例；原文把两种范围混在了一起。
- 10个计分样例的V1作者缺陷由基线19条稳定升至105/101/111条，确有跨样例的系统缺口。
- V1章节缺陷由10条变为12/14/13条，新增差异主要集中在01，不能称为正文层级普遍回退。
- V1文后声明由0条变为20/20/18条，但只集中在02、05、S03及一轮04；其中02属于B-07，05和S03根因不同。
- V1表格缺陷由42条变为78/57/62条，但V2表格问题记录反而由4313条变为4156/3601/4168条。V2中的表格属性差异由3665条降至3047条，同时元素缺失由147条升至616条，说明有改善也有回退，不能概括为同一方向。
- 关系F1的大幅下降主要来自B-02已经证明的“正文引用全部作废”，不得在B-09中重复修复。
- V2问题记录只是细粒度差异数，不是总分；以上数字只用于定位，不用于跨领域相加判断质量。

因此，B-09不是一个可以对应一次代码修改的问题。继续把这些现象捆绑处理，只会形成按评测器逐条补洞的专家系统。真正成立的共同根因如下。

#### A. 作者关系：内部实体身份与印刷标记被错误地混为一体

这是B-09中最明确、覆盖面最大的系统问题。

1. 当前封面响应以`affiliation_labels`表示作者指向哪个单位；组装时又必须先把单位自身的可见`label_quote`唯一落锚，才能建立“标签→内部ID”映射。于是印在稿件上的`1`既充当可见内容，又充当内部身份。
2. 02、03、04、S02的单位编号虽然模型返回正确，但同一单位行中邮编等内容也含相同数字，短编号不能独立唯一落锚；单位标签随即消失，所有指向该标签的作者—单位关系也被过滤。三轮稳定缺失的24条单位关系由此产生。
3. 05更直接地证明设计本身不闭合：作者名旁印有`1/²`，两条单位行本身没有编号。单位实体仍然存在、作者关系也能判断，但当前表示要求单位必须有可见标签才能被引用，因此原则上无法表达这份合法稿件。
4. 最佳修复不是放宽字符串匹配，也不是为数字编号写规则，而是彻底分离两件事：单位使用稳定的内部索引/ID作为关系目标；`label_quote`只表示单位行上确实印出的文字，可以为空；作者名旁的标记只作为该关系的可见内容。内部关系不再依赖显示编号是否存在、是否唯一。

同一身份混淆也存在于通讯关系：

- 当前`correspondence_quotes`只是若干孤立摘抄，没有“这一条通讯块对应哪些作者”的关系；组装程序只有在全篇恰好组装出一个通讯实体时才连接作者。01和S05各返回两个物理摘抄，所有通讯关系因此同时丢失。
- 一条逻辑通讯信息可以跨多个物理段落，也可以对应多位作者；一位作者也可能有多个邮箱。当前`email_quote`是单值，S02的两个邮箱无法完整表达，而语义模型实际已经允许邮箱列表。
- 最佳修复是让通讯信息成为有内部身份的逻辑实体：每个实体包含按源顺序排列的多个内容摘抄、作者索引和各个可见标记出现位置；作者、通讯实体、邮箱和地址之间通过显式关系连接，不再依据“全篇只有一个”猜目标。

此外还有两类投影问题，不能混入关系判断：

- 三轮有38至42个ORCID稳定输出为裸号码，而金标准要求规范URI。模型已经识别出号码，错误发生在语义值到JATS的投影层。应将“ORCID号码→规范URI”实现为有来源记录的标准化变换，而不是在提示词中要求模型补前缀，也不能无记录地拼字符串。
- 地址差异包含真实地址、单位地址、通讯段内容和作者直连地址四种语义位置。当前响应虽有`author_indexes/affiliation_indexes`，但组装只消费作者索引，且提示没有把“通讯段中的地址文字”与“应嵌入contrib的地址实体”分清。修复时必须让物理地址出现与其语义所有者显式连接，禁止按标题、作者名或位置补关系。

封面任务还有一个贯穿以上问题的契约漏洞：提示声明`author_quote`必须是带`quote/node_hint`的对象，但三轮真实结果仍大量是裸字符串；`front_pass`没有在首次调用中启用机械契约校验，事后重问也可能接受仍未闭合、只是失败数较少的结果。应对整个封面响应使用严格结构和统一校验，不能只为某个字段加特判。

#### B. 文后声明：S03是归并覆盖，05是出版配置缺口，02属于B-07

S03的模型结果已经正确列出作者贡献、资助、披露和伦理声明，最终XML却全部缺失。逐层证据为：

- 正文任务把`doc/p17`、`doc/p27`、`doc/p29`、`doc/p31`等明确标为`declaration`，并给出种类、标题及内容节点。
- 封面任务把`doc/p1`至`doc/p49`整段列为`front_nodes`，还把作者贡献信息误放入`author_note_quotes`。
- 全局分歧裁决最终选择`front`；组装只消费最终主角色，于是已经识别出的声明被完整丢弃，且没有产生“具体结构被粗范围覆盖”的阻断项。

这证明归并层缺少一条通用保证：一条已经落锚的具体结构不能被较粗的范围归属无痕抹去。修复不能简单规定“正文永远胜过封面”，因为两路都可能错；正确做法是：

1. 收紧封面任务的职责和契约，`front_nodes`中的每个节点必须有具体封面字段证据，不能把`body_start_node`之前的连续范围当作封面事实。
2. 归并时保留“粗范围归属”和“具体实体归属”的证据类型；裁决若否定一个已落锚实体，必须给出可核验的源证据和明确拒绝记录。证据仍不足时阻断交付，不能静默删除。
3. 不建立声明标题词表，不按文档位置设优先级，也不为S03添加分支。

05并不是同一问题。其伦理、资助、致谢和利益冲突段落在源稿中没有印刷标题；金标准标题属于出版模板生成文字。`BackSection.kind`已明确预留“由显式出版配置选择模板标题”的能力，但当前`PubConfig`和配置注入没有实现这部分。若要对齐，应扩充可审计的出版配置并登记每个生成标题的配置键；不得在渲染器中硬编码标题，也不得让模型编造源稿中不存在的文字。

02缺少glossary属于B-07的“语义结构未完整传到XML”，不在B-09重复处理。
