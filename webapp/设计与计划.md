# word2jats Web 应用 · 设计与分阶段执行计划

> 这是执行规格。用户已全权授权我实现，只做验收。**执行铁律**：从易到难、先能跑能用再完善到接近生产；**每个阶段结束必须 pytest 全绿 + 提交一个能跑能用的版本**，绝不在半成品状态堆叠下一阶段——任何时候都要有一个可用版本兜底。量力而行，不好高骛远。

## 一、本质（第一性原理）

同时干两件本质不同的事：
1. **去掉脚本门槛**：不懂命令行的人，给一个 Word → 拿到 JATS。
2. **让结果可信可读**：原始 JATS XML 对期刊编辑是天书；本项目核心主张是"只判结构、正文一字不改"，若只吐 XML 则该主张成黑箱。所以**把"合法性 + 内容忠实(没编造/没漏词)"摆到明面、让人亲眼看见没改坏原文**——这是本工具区别于所有同类工具(SciSpace/SciELO/PMC 都不暴露编造/漏词)的立身之本。

## 二、用户与要解决的问题

- 主要：期刊编辑/排版（IMR Press 场景），非开发者。要：传 Word→等→拿合法 JATS+图片→确认忠实→下载。
- 次要：评委现场演示（决赛现场演示评分）——亲手试、亲眼看它跑通且可信。

## 三、硬约束（读代码 + 调研，非猜测）

| 约束 | 由来 | 强制 |
|---|---|---|
| 转换是阻塞 10–60s 的云端大模型调用(IO 密集) | `convert()` 调 dashscope | 异步：提交→task_id→轮询→取结果；调用甩线程池不卡服务 |
| 需 API key、每次转换真花钱 | 方法必需 LLM | key 放服务端；磁盘缓存让同文件重传秒回免费 |
| 产物是包：JATS XML + 外部化图片文件 | `convert()` 写 XML+导图 | 下载给 zip；渲染要能显示图片 |
| 已有 `stats`+校验(DTD/n_fab编造词/n_lost漏词/各计数/耗时) | `ConvertResult` | 结果界面直接用 |
| 浏览器原生 XSLT 正被移除(Chrome ~2026-11) | 调研(官方公告) | JATS→HTML 渲染放**服务端**(用已有 lxml 跑 NCBI 公有领域样式表) |

## 四、架构

```
浏览器(静态前端 HTML/CSS/原生JS)
   │ 上传 docx(+可选 DOI/期刊)
   ▼
FastAPI 单服务(Python, 进程内直接调 convert(), 不重写管线)
  POST /convert    建任务→丢线程池后台跑→立即回 task_id
  GET  /status/id  阶段/进度(轮询)
  GET  /result/id  渲染HTML + 校验 + stats(JSON)
  GET  /download/id XML+图片+校验报告 打成 zip
  GET  /figure/id/name 结果图片(供渲染视图引用)
  服务端持 API key; 任务状态先用进程内字典(单机够用, 升级路径 Redis+ARQ)
   ├ 渲染: lxml 跑 NCBI jats-html.xsl → 期刊样式 HTML
   └ 磁盘缓存: 同文件重传命中、秒回免费
```

## 五、技术选型（调研背书，见 git 历史里的两份调研）

- **FastAPI + 轻量前端(原生 JS/HTML/CSS)**。理由：Gradio/Streamlit"一眼 demo"过不了"真工具"关；Flask 同步阻塞、长任务+并发要手工补队列。FastAPI 对 上传流式/长任务甩线程池/轮询进度/吐 zip/前端外观零限制 每项都有一等公民支持。
- 异步实现模式：路由声明成普通 `def`(FastAPI 自动进线程池) 或 `await run_in_threadpool(convert, opts)`；进程内 `{task_id: {status,stage,progress,result}}`；前端每 1–2s 轮询 `/status`。
- 渲染：`lxml.etree.XSLT(NCBI jats-html.xsl)`（公有领域，需 vendor 进 `webapp/vendor/`）；图片 src 指到 `/figure/id/name`。原始 XML 视图另做缩进+高亮。
- 依赖：新增 fastapi + uvicorn + python-multipart(上传)；lxml 已有。写进 requirements/pyproject。

## 六、`convert()` 接口备忘（执行时照这个包）

```python
from word2jats.pipeline import ConvertOptions, convert
opts = ConvertOptions(docx_path=<上传临时文件>, out_dir=<每任务独立目录>,
                      journal_id=<可选>, doi=<可选>)
res = convert(opts)   # 阻塞 10-60s
# res.xml_path, res.article_id, res.validation(DTD/JATS4R), res.stats:
#   authors/affiliations/keywords/abstract_sections/body_sections/
#   references/refs_structured/figures_exported/tables/formulas/xrefs/
#   llm/verify{n_fab,n_lost,dtd_ok}/elapsed_sec/checks
```
key 从 `.env` 的 `DASHSCOPE_API_KEY` 读（服务端）。

## 七、分阶段执行计划（从易到难，每阶段能跑能用 + 提交）

### Phase 1 — 能跑能用（最薄端到端）★先做
- FastAPI 单服务 + 一个上传页。上传 docx(+可选项)→异步提交拿 task_id→轮询粗进度(转换中+实时秒表)→完成后下载 zip(XML+图片) + 页面显示原始 XML。服务端持 key、进程内任务字典、convert() 甩线程池。
- **验收**：本地一条命令起服务；浏览器传一篇样例 docx，几十秒拿到合法 JATS 的 zip；有 pytest 集成测试(TestClient 传 docx→得合法 XML、DTD 通过)。
- 收尾：测试绿 + 提交。

### Phase 2 — 可信可读（差异化主角）
- 结果分页：渲染视图(服务端 NCBI XSLT，默认)/原始XML(高亮)/校验(错误·警告·提示分级)/结构摘要(stats 指标卡)/内容忠实(n_fab/n_lost 面板+占原文百分比+大白话判定)。顶部状态条(合法性 chip + 忠实一句话 + 耗时)。
- **验收**：传样例后能看到期刊排版渲染视图(图片正常)、DTD 状态、结构摘要、忠实指标。
- 收尾：测试绿 + 提交。

### Phase 3 — 完善到接近生产
- 真阶段进度条：给管线加轻量阶段钩子(解析→理解→渲染→校验)上报 stage(顺带满足"转换过程可视化"那项交付)。
- 原文 vs 输出 diff 视图：高亮标出"多出/编造"与"漏掉/丢失"片段(最硬的"没改坏原文"证据，同类工具都没有)。
- 错误处理：坏文件/转换失败/缺 key 都给人话提示、**服务绝不崩**。
- 部署：一条命令起 + 可选 Dockerfile + 运行说明文档。
- 收尾：测试绿 + 提交。

## 八、明确不做（划界，防摊大饼）

不做：账号登录、批量多文件、在线编辑 JATS、历史记录数据库、多副本横向扩容。均有升级路径，现在不做。
