## 摘要

word2jats 面向学术期刊生产中的 Word 结构化加工环节，将作者提交的 `.docx` 论文转换为符合 **JATS Journal Publishing DTD 1.3** 的 XML，并将文中图片外部化后与 XML 一并打包交付。系统覆盖题名与章节层级、作者及单位关联、ORCID、摘要、关键词、图、表、Word 公式、参考文献、出版声明和交叉引用等主要结构。

方案采用“**大模型判断结构，程序回填原文并确定性生成 JATS**”的技术路线。Word 原文首先被解析为保留文字、内联格式、图片和公式的中间表示，每个源块具有稳定索引；大模型只返回源块的结构类别、层级和字段边界；正文、题名、题注等内容再由程序按照索引从源文件取回。该设计利用大模型处理弱样式、跨模板排版和参考文献边界等语义问题，同时避免让模型直接改写或补写学术正文。

配套原型提供在线 Web、本地 Web、命令行和 Docker 运行方式。转换完成后可查看期刊样式预览、原文核对、内容清单、合规检查和完整 XML，并下载由 XML 与图片组成的 ZIP 交付包。JATS 1.3 DTD 随原型内置，输出无需联网获取标准文件即可完成合法性校验。

## 1. 赛题需求与方案定位

### 1.1 Word 与 JATS 之间存在语义鸿沟

Word 文档主要记录文字及其版式。题名、作者、单位、摘要、章节、图表和参考文献虽然在页面上可以被人理解，但在底层文件中往往只是样式、字号、缩进、表格和普通段落的组合。同一种论文结构可能采用不同排版，同一种排版也未必表示相同语义。

JATS（Journal Article Tag Suite）则要求将论文结构显式编码为 XML。例如，作者需要与单位建立可计算的关联，正文需要形成层级清楚的章节树，公式需要转换为 MathML，图像需要通过外部文件引用，参考文献需要尽可能拆分为作者、题名、来源、年份和卷页等字段。DTD（文档类型定义）进一步规定了元素是否允许出现以及元素之间的合法嵌套关系。

因此，本赛题不是简单的文件格式转换，而是从“以版式为主的 Word”到“以语义为主的 JATS”的结构映射问题。

### 1.2 方案目标

| 目标 | 要求 | 对应设计 |
|---|---|---|
| 结构识别 | 从不同 Word 排版中识别稳定的论文语义 | 综合 OOXML 物理信号与大模型语义判断 |
| 内容忠实 | 结构化过程中不改写、翻译或概括学术正文 | 源块索引回填、字段子串校验、图像与公式占位 |
| 标准合规 | 输出满足 JATS Journal Publishing DTD 1.3 | 确定性渲染、内置 DTD、出口合法性检查 |
| 功能完整 | 覆盖赛题要求的主要论文模块 | front/body/back 分区识别与统一语义模型 |
| 可运行 | 提供可直接核验的程序和示例输入 | Web、CLI、Docker、多阶段结果展示 |
| 可维护 | 便于更换模型、扩展期刊和增加新结构 | 解析、理解、语义、渲染、验证分层 |

### 1.3 输入与输出边界

系统输入为 `.docx` 学术论文，并接收期刊代码和可选 DOI。系统输出包括：

- 一份 JATS Journal Publishing 1.3 XML；
- 从 Word 提取的外部图片文件；
- XML 与图片组成的 ZIP 交付包；
- 文章结构统计、DTD 校验结果和结构检查结果；
- 供人工复核的期刊样式预览与原文核对信息。

系统负责识别和标记源稿已有内容，并按期刊配置补充固定的期刊级元数据。系统不承担论文润色、翻译、事实补写或根据图片猜测文字的任务。

## 2. 技术路线选择

### 2.1 规则与端到端生成均存在明显短板

| 路线 | 优点 | 主要问题 |
|---|---|---|
| 纯规则转换 | 结果确定、速度快、容易校验 | 依赖固定样式和模板；面对全篇 Normal 样式、跨段参考文献和弱版式信号时适应性不足 |
| 大模型直接生成 XML | 能利用上下文理解复杂语义 | 模型同时控制文字与标签，可能改写内容、遗漏段落或产生不合法结构；结果难以稳定复现 |
| 本方案 | 大模型处理语义判断，程序控制原文和 XML 语法 | 需要设计受约束的中间协议，并对模型判断建立回退与验证机制 |

本方案不让规则独自承担全部语义识别，也不让模型直接负责整篇 XML 生成，而是将两者限定在各自更适合的环节。

### 2.2 三项设计原则

1. **原文与结构分离。** 原文由解析层保存，模型只描述“哪个源块是什么”，不承担普通正文生成。
2. **语义判断与 JATS 语法分离。** 大模型输出结构 JSON，JATS 元素由程序按照固定规则构造。
3. **生成与验证一体化。** 每次转换都执行内容核对、结构自洽检查和 DTD 校验，问题直接呈现在结果页。

### 2.3 总体处理流程

```text
输入 .docx
   │
   ▼
OOXML 解析
段落、run、样式、编号、表格、图片、OMML 公式
   │
   ▼
内容流序列化
稳定 [idx] + 版式提示 + 图片/公式占位符
   │
   ▼
语义理解
front / body / references 三个专门任务
   │
   ▼
SemanticDoc 组装
按 idx 取回原文、格式、图片和公式
   │
   ▼
JATS 确定性渲染
front / body / back + 图表公式 + 交叉引用
   │
   ▼
内容核对 + 结构检查 + JATS 1.3 DTD 校验
   │
   ▼
XML + 外部图片 + ZIP 交付包
```

## 3. 核心技术实现

### 3.1 OOXML 解析保留原始内容与内联格式

`.docx` 本质上是 OOXML 压缩包。解析层读取正文、样式、编号和关系文件，将文档转换为有序的段落、run、表格、图片和公式对象。

Word 会因粗体、斜体、上标、下标或字体变化把连续文字拆成多个 run。如果直接按 run 进行语义识别，一个完整单词或作者单位角标可能被割裂。系统在结构判断前组合连续文字，同时保留原 run，以便生成 JATS 时恢复 `<bold>`、`<italic>`、`<sup>` 和 `<sub>` 等内联格式。

原生 Word 表格保留行、列和单元格结构；图片通过关系 ID 读取原始媒体字节；OMML 公式保留其 XML 节点，交由公式模块转换。

### 3.2 稳定源块索引约束模型输出

解析后的每个段落或表格被序列化为带稳定编号的内容流，例如：

```text
[18] «bold,center» Abstract
[19] Objective: ...
[36] «style:Heading 1» 1. Introduction
[52] ⟦IMG#3⟧
[53] Figure 1. Study flow chart
```

内容流同时提供有限的版式提示，包括粗体、斜体、居中、Word 样式、编号列表和表格形状。模型根据上下文判断结构，但输出必须引用 `[idx]`，而不是重新生成该段文字。

图片和公式仅以 `IMG#n`、`MATH#n` 占位符进入模型上下文。模型只能判断它们与题注、段落的位置关系，无法读取或转写其中内容，从输入层面排除“看图猜字”。

### 3.3 三个专门任务降低复杂度

语义理解被拆分为三个边界明确的任务：

| 任务 | 识别内容 | 输出重点 |
|---|---|---|
| front | 文章类型、题名、作者、单位、通讯作者、ORCID、日期、摘要、关键词 | 源块位置、作者字段、单位关联、正文起点 |
| body | 章节层级、普通段落、图、表、公式、出版声明 | 章节树、题注位置、对象占位符、声明区间 |
| references | 参考文献条目及其内部字段 | 条目范围、作者、题名、来源、年份、卷期页、DOI |

参考文献数量过多时自动分段处理，避免单次输入过长。书籍和书籍章节增加专门的字段识别，用于编辑者、出版社、出版地和版次。

所有模型任务均要求严格 JSON 输出。字段值必须来自源文；组装阶段再次检查短字段是否为原文子串，异常字段被清空或降级，不直接进入最终 XML。

### 3.4 SemanticDoc 隔离语义理解与标准输出

模型返回的 JSON 不直接转换成 XML，而是先组装为独立语义模型 `SemanticDoc`。该模型统一表示作者、单位、摘要、章节、图、表、公式、声明和参考文献，并携带从源文件取回的原始 run 和媒体对象。

`SemanticDoc` 的作用是建立稳定接口：上游可以更换模型或调整识别策略，下游可以调整 JATS 映射规则，两者互不依赖。模型无法通过输出任意标签改变 XML 结构，渲染器也不需要重新判断段落语义。

### 3.5 JATS 由程序确定性构造

渲染层按 JATS 的固定骨架生成文档：

- `<front>`：期刊元数据、文章标识、题名、作者、单位、摘要和关键词；
- `<body>`：章节、段落、图、表和公式；
- `<back>`：声明、致谢和参考文献。

作者与单位、正文与图表、正文与参考文献之间通过 `id` 和 `rid` 建立交叉引用。元素 ID 统一生成并检查唯一性；只有目标存在时才建立引用，避免产生悬空 `xref`。

期刊名、ISSN、出版者和固定许可信息从本地期刊配置读取，不由模型推测。新增期刊时可扩展配置，而不需要改动核心处理流程。

### 3.6 图片、表格、公式和参考文献处理

**图片。** 图片从 Word 媒体包提取后直接写入输出目录，不重新编码；JATS 使用 `<graphic xlink:href="...">` 指向外部文件。图题文字从原 Word 段落取回。

**表格。** 原生 Word 表格按单元格网格转换；制表符分隔的文本表可重建为表格；整张以图片存在的表保持为外部图片，不执行文字猜测。

**公式。** Word 中的 OMML 公式通过原型内置的 `OMML2MML.XSL` 转换为 MathML，并按原位置生成 `<inline-formula>` 或 `<disp-formula>`。仅以图片存在的公式不执行 OCR。

**参考文献。** 字段识别可靠时生成结构化 `<element-citation>`；字段不完整或边界不可靠时保留整条原文，以 `<mixed-citation>` 输出。该回退优先保证内容可追溯，不为追求字段齐全而补造数据。

### 3.7 出口验证形成交付闭环

每次转换结束前执行三类检查：

1. **内容核对**：比较源 Word 与输出 XML 中的文字，报告可能新增和可能遗漏的词项，供人工复核；
2. **结构自洽**：检查 ID 唯一性、交叉引用目标、图片文件、公式表示和表格结构；
3. **标准合法性**：检查 XML、DOCTYPE 和命名空间，并使用随原型提供的 JATS Publishing 1.3 DTD 离线校验。

Web 结果页将检查结论分为“可交付”与“待确认”。DTD 或高等级结构检查不通过时不会隐藏问题，完整诊断和 XML 原文仍可查看。

### 4.2 交付结果同时面向机器与人工

JATS XML 用于后续出版系统、数据库交换、全文检索和长期保存；外部图片与 XML 一起组成完整数据包。与此同时，Web 工作台提供期刊样式预览和原文核对，使编辑人员无需直接阅读 XML 也能检查图表、章节和正文是否完整。

这种双重输出避免把“通过 DTD”误当成“内容一定正确”。标准校验负责判断结构是否合法，人工预览和核对负责判断语义是否符合原稿，两者共同构成交付依据。

## 5. 方案创新点

| 创新点 | 技术机制 | 实际作用 |
|---|---|---|
| 带索引的受约束语义映射 | 模型输出源块索引、类型和字段边界，正文按索引回填 | 保留模型语义理解能力，同时切断模型直接改写普通正文的路径 |
| 内容与结构双通道 | IR 保存原文与格式，结构 JSON 只保存判断结果 | 结构判断错误不会自动变成文字改写，便于单独修正识别规则 |
| 图片与公式占位协议 | 模型只接收对象编号，不接收图像字节或公式转写结果 | 避免 OCR 或视觉猜测引入不存在的学术内容 |
| 语义模型与 JATS 渲染解耦 | `SemanticDoc` 作为稳定接口，JATS 由程序构造 | 模型可替换、标准映射可维护，输出结构不受模型自由格式影响 |
| 结构化失败的保真回退 | 参考文献字段不可靠时保留整条原文 | 将失败方向控制为“结构粒度降低”，而不是补造字段 |
| 面向编辑的验证闭环 | DTD、结构检查、原文核对和预览在同一结果页呈现 | 将算法输出转化为可审查、可签收的出版交付物 |

核心创新不在于单独使用大模型，而在于重新划分模型与确定性程序的职责：模型解决“这段是什么”，程序解决“原文是什么”和“JATS 应如何合法表达”。

## 6. 工程实现与可运行原型

### 6.1 技术栈与代码结构

原型采用 Python 3.12。`python-docx` 与 `lxml` 负责 Word/XML 处理和 DTD 校验，Pillow 负责图片识别与预览转换，FastAPI/Uvicorn 提供 Web 服务，模型通过 OpenAI 兼容接口调用。

```text
可运行原型/
├── src/word2jats/
│   ├── parse/          Word/OOXML 解析
│   ├── understand/     内容流、语义理解与组装
│   ├── semantic/       SemanticDoc 语义模型
│   ├── render/         front/body/back 确定性渲染
│   ├── build/          图片、公式、JATS 元素和交叉引用
│   ├── validate/       DTD 与结构检查
│   ├── verify/         内容核对
│   ├── llm/            模型适配与磁盘缓存
│   └── resources/      JATS 1.3 DTD、XSLT、期刊配置
├── webapp/             Web 后端、前端和预览资源
├── 示例输入/           可直接用于验收的 Word 文件
├── README.md           运行说明
├── requirements.txt    依赖清单
├── pyproject.toml      Python 项目元数据
└── Dockerfile          容器运行定义
```

### 6.2 Web 工作台降低验收与使用门槛

Web 服务直接调用与命令行相同的转换管线，不维护另一套转换逻辑。文件提交后返回任务 ID，后台执行转换，前端轮询进度并依次展示“读取 Word—识别结构—生成 JATS—合规检查”等阶段。

结果页包含：

- **成品预览**：将 JATS 服务端渲染为期刊样式 HTML；
- **原文核对**：展示输出来源覆盖和源文保留情况，以及需要人工确认的词项；
- **内容清单**：列出作者、单位、关键词、章节、图表、公式和参考文献数量；
- **合规检查**：展示 DTD 和结构检查结论；
- **XML 源文件**：供技术人员查看完整 JATS；
- **交付包下载**：下载 XML 与外部图片组成的 ZIP。

主要 API 包括转换提交、任务状态、结果、预览、图片和下载接口；大文件支持分片上传与断点续传。

### 6.3 成本、复现与安全控制

模型响应按请求内容写入本地磁盘缓存。相同输入、期刊和 DOI 再次转换时可复用已有响应，减少重复调用费用，并固定已经获得的模型判断结果。默认使用 `qwen3.7-plus`，模型适配层也支持其他 OpenAI 兼容服务。

API Key 仅由服务端从 `.env` 读取，不进入浏览器或转换结果。图片访问执行路径边界检查；上传文件设有大小限制；用户可见错误不包含服务器路径和异常堆栈。Docker 构建时不复制 `.env`，密钥通过运行参数注入。

## 7. 质量保证与验证结果

### 7.1 标准合法性由运行时直接验证

JATS 1.3 DTD 及其实体文件完整包含在原型中。每次转换生成 XML 后立即执行离线 DTD 校验，并检查精确 DOCTYPE、命名空间、ID 唯一性和交叉引用目标。评审可在 Web“合规检查”页或命令行输出中直接查看结果，无需依赖额外报告。

使用赛题提供的 10 份 Word 样例进行回归转换，10 份输出均通过 JATS Journal Publishing 1.3 DTD。该结果说明输出满足标准语法和内容模型要求；DTD 通过不等同于所有语义字段均达到人工标注水平，因此系统仍保留预览、内容清单和原文核对环节。

### 7.2 配套示例可复核主要处理链路

原型内置 `示例输入/初始文件.docx`。按推荐参数转换后，结果页应识别并展示以下主要结构：

| 核验项 | 预期结果 |
|---|---:|
| 文章号 | HSF49106 |
| 作者 / 单位 / 关键词 | 4 / 2 / 4 |
| 正文章节 | 5 |
| 图 / 表 | 4 / 10 |
| 参考文献 | 27 |
| 交叉引用 | 60 |
| DTD 校验 | 通过 |

该示例同时覆盖文件上传、结构识别、图片外部化、表格转换、参考文献结构化、交叉引用、服务端预览和 ZIP 下载。具体耗时受网络状况、模型队列和运行环境影响，通常约为 1—2 分钟。

### 7.3 质量判断采用“机器检查 + 人工复核”

机器检查能够确定 XML 是否格式良好、是否符合 DTD、引用是否悬空、图片是否存在，但不能完全替代对章节归属、题注边界和参考文献字段的业务判断。原型因此不以单一分数代替质量结论，而是将合法性、结构统计、内容差异和成品预览同时提供给评审或编辑人员。

这一质量策略与实际出版加工一致：自动化负责识别、生成和发现问题，人工负责确认少量有歧义的语义边界。

### 8.3 本地 Web 运行

环境要求为 Python 3.12 和可访问模型接口的网络。解压后在 `可运行原型` 目录执行：

```bash
python3.12 -m venv .venv

```

浏览器打开 <http://127.0.0.1:8000>，使用以下参数：

- 输入文件：`示例输入/初始文件.docx`
- 期刊：`HSF`

```bash
PYTHONPATH=src .venv/bin/python -m word2jats convert \
  "示例输入/初始文件.docx" \

  --doi 10.31083/HSF49106 \
```

输出目录包含 `HSF49106.xml` 和从 Word 提取的图片，终端同时显示文章结构统计与校验结果。

浏览器打开 <http://127.0.0.1:8000> 即可使用。

## 9. 原创性与第三方资源边界

核心处理链路、源块索引协议、三段语义理解、SemanticDoc、JATS 渲染、交叉引用、内容核对、验证编排、Web 工作台和模型适配均为本项目实现。

项目使用公开标准资源和通用基础库，边界如下：

| 资源 | 用途 | 与核心方案的边界 |
|---|---|---|
| JATS Journal Publishing 1.3 DTD | 输出合法性校验 | 标准文件，不参与语义识别 |
| `OMML2MML.XSL` | OMML 转 MathML | 通用公式格式转换资源 |
| NCBI JATS 预览 XSLT/CSS | Web 端成品预览 | 仅用于显示，不改变交付 XML |
| python-docx、lxml、Pillow、FastAPI 等 | 文档、XML、图像和 Web 基础能力 | 通过公开接口组合使用 |
| 云端或本地大语言模型 | 返回受约束的结构判断 | 可替换推理后端，不直接构造 JATS 或普通正文 |

第三方预览资源的来源说明随原型保留，标准资源、第三方资源和核心代码在目录中分开存放。

## 10. 已知边界与后续扩展

1. **列表结构尚未专门输出。** Word 编号已被解析并用于语义提示，列表文字能够保留；当前仍按段落生成，后续可在 `SemanticDoc` 中增加列表对象并映射为 `<list>/<list-item>`。
2. **纯图片公式不转写。** 无 OMML 的图片公式不执行 OCR，避免错误识别改变数学含义。后续若引入公式 OCR，需要增加置信阈值和人工确认。
3. **弱信号结构存在歧义。** 无样式、无编号的提示框、小标题、复杂图题和跨列表头可能存在多种合理结构，需要通过结果页复核。
4. **模型服务是必要依赖。** 网络、余额或模型响应异常会影响首次转换；磁盘缓存只能复用已经处理过的相同请求。
5. **当前 Web 原型面向单机验收。** 任务状态保存在进程内存中，服务重启后不保留，不具备多机调度和用户权限体系。生产部署可替换为持久化任务队列、对象存储和数据库。
6. **输入格式限定为 `.docx`。** 旧版 `.doc`、PDF 和扫描件不在当前范围。

上述边界不影响原型对赛题核心流程的演示和核验，也明确了从竞赛原型向生产系统演进时需要补充的能力。

## 11. 结论

word2jats 已形成从 Word 解析、语义结构判断、JATS 1.3 确定性渲染、图片外部化、内容与结构验证到 Web 交付的完整可运行链路。

方案的核心价值在于以受约束的大模型解决跨模板语义识别问题，同时将原文控制权和 JATS 语法控制权保留在确定性程序中。配套原型能够直接接受 Word 输入、产生 XML 与图片交付包，并通过 DTD、结构检查、原文核对和成品预览支持评审验收与编辑复核。
